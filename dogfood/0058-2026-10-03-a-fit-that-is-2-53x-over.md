# 0058 — `--max-tokens` reports a fit for content its ratio was never measured on

| | |
|---|---|
| **Bead** | `asc-squ` |
| **Surfaced** | 2026-10-03 |
| **Surfaced by** | `asc explore note_cjk --page --json --max-tokens 1000`, against a scratch project of CJK entries, while building `--chars-per-token` |
| **Entry type(s)** | `note_cjk` (project-defined, scratch; the fixture is a copy of this repo's `attempt` starter shape) |
| **Severity** | P2 — the flag's own claim is false, but only for content the tool was never calibrated on, and the report names the assumption it rests on |
| **Status** | fixed in the `asc-squ` work (the ratio is now caller-settable); the *shape* is recorded here |

## What was found

`--max-tokens` is a ceiling claim, and for non-Latin content it is not one. Run at the shipped ratio
of 2, the flag reports `estimated_tokens` inside the budget and `dropped: 0` — "everything you asked
for fits" — about bytes that measure **2.53x** over that budget when counted at the ratio the same
corpus was measured at. The report does carry `chars_per_token: 2`, so the assumption is disclosed;
what was absent was any way to change it. A caller reading the report cannot tell a fit from a
2.53x overrun without doing arithmetic the flag exists to do for them.

## How it surfaced

**Someone was looking, and for something else.** The CJK fixture was built to test whether
`--chars-per-token` reaches the fit — a question about the new flag. What the fixture exposed was a
defect in the *shipped* path, which nothing in this workstream had been auditing: the default arm was
supposed to be the control, and instead it was the finding.

The mechanism generalizes past the arithmetic. **A calibration constant is a claim about a corpus, and
a claim about a corpus is false everywhere the corpus differs.** `CHARS_PER_TOKEN = 2` is documented as
*"below the smallest ratio measured for ascend's own output"* — the measurement is real and the doc is
honest, but `--max-tokens` applies the constant to whatever store the caller pointed it at. The gap
between "measured on this content" and "applied to that content" is where the false green lives, and
it is the same gap `dogfood/0057` records one layer up, where a cost figure measured on one scope was
quoted as a number for another.

## The metric

Scratch project: `asc init`, one type with a single `text` property, 8 entries whose `note` is 44
characters of U+6F22. Both arms below are the real binary, same store, same budget.

```
--- shipped arm (no --chars-per-token): exit 0
   rows          : 8
   trim          : {'max_tokens': 1000, 'estimated_tokens': 786, 'dropped': 0, 'chars_per_token': 2}
   bytes on stdout, measured at the CALLER's ratio 0.79 : 1990
   bytes on stdout, measured at the tool's ratio 2      : 786

--- corrected arm (--chars-per-token 0.79): exit 2
Error: --max-tokens is too small for this output: the smallest possible one in
this output format -- 1 entry -- is about 1035 tokens. Raise --max-tokens to at
least that, or ask for a narrower scope so there is less to fit.
```

The shipped arm: `786 <= 1000` reported, `dropped: 0`, and the bytes it wrote measure **1990** at the
ratio CJK was measured at. **1990 / 1000 = 1.99x its budget; 1990 / 786 = 2.53x its own reported
size.** The corrected arm, asked the identical question, refuses honestly and names the figure.

The ratio **0.79 is not this record's measurement** — it is `docs/evidence/EV-13.md`'s, taken with
three real tokenizers (`tiktoken cl100k_base`, `tiktoken o200k_base`, `@anthropic-ai/tokenizer`), and
it is the number `asc-squ`'s own accept criterion names. No tokenizer is a dependency of ascend, so
the end-to-end fixture measures code points and applies EV-13's ratio to them; that is a borrowed
ground truth and is stated as one rather than re-derived.

n = 1 fixture, 8 entries, 1 type. Under `MIN_N` (20, `packages/analysis/src/proportion.ts:50`): this
is **an anecdote about a ratio**, not an estimate of how often it bites. What is not an anecdote is
the arithmetic — `2 / 0.79 = 2.53` is exact for any corpus at that ratio, whatever its size.

## The pattern

**A shipped default that is disclosed but not overridable is a defect wearing the costume of a
documented limitation.** The tool did the honest thing twice: it measured the constant, and it printed
the assumption on every report. What it did not do was let the caller act on either. Disclosure is not
a mitigation when the only remedy is to stop using the flag.

The narrower instance: **a value on a report that nothing can change.** `chars_per_token` rode on
every `trim` block from the day the budget shipped, and `EV-13`'s note says it is there *"so a caller
who has measured their own corpus ... can divide `estimated_tokens` by this and multiply by that"* —
manual correction, by design. That design was a reasonable stopgap and it is why this was findable at
all; the finding is that a stopgap outlived the reason for it, and the evidence that it had was
sitting on every report the whole time.

## Why nothing else would have caught it

Nothing else did, and the reasons are specific rather than lucky:

- **The suite's oracle is the tool's own ratio.** `explore-budget.test.ts` measures with
  `Array.from(text).length / 2` — the same constant the estimator used. Every honesty assertion in
  that file, including the one that exists precisely to catch a false green, agreed with the bug to
  the token. Two implementations of one assumption is not two implementations of one invariant, and
  that file's own doc comment calls the second implementation the point.
- **The corpus cannot produce the fixture.** Re-measured 2026-10-03 across this repo's store: 6,885
  records, 110,050 string values, **0 of every non-Latin script** (see `IMPLEMENTATION_PLAN.md`,
  Stage E14). A test built from real records cannot be CJK, so the gap is invisible to any test that
  insists on real data — the same collision `dogfood/0047` records from the other side.
- **A review cannot see it**, because nothing is wrong on any single line. The constant is correct
  for the corpus it was measured on, the doc says so, and the report discloses it. The defect is in
  the composition, and the composition is what a reader skips.

The one thing that *would* have caught it is a fixture whose ground truth comes from outside the
tool, which is what this record's fixture is. That is an argument for testing calibration constants
against an external measurement rather than against themselves, not an argument that this series
found something a test could not.

## Consequences and constraints

- **Entries are immutable** (enforced by trigger), so this is not a cleanup task in the store. It is
  also not *in* the store: the defect is in a rendering path, which is free to change.
- **The fix is caller-side, and that is the honest boundary.** `--chars-per-token` lets a caller
  supply the right number. It does not make the default right, and nothing here claims a caller will
  know to pass it — `EV-16` measured availability as not-adoption, and the same doubt applies to this
  flag. The mitigation is disclosure plus a way to act, which is strictly more than was there before.
- **The `--dump` manifest carried the same defect and got the same fix**, because `chars_per_token`
  there describes the files on disk rather than the fit. Left alone it would have stated one
  assumption while its `tokens` rested on another.
