# EV-70: does cutting the pre-commit gate pay, and does the skip rule select what it says?

**Status** Predictions registered 2026-10-13 in `IMPLEMENTATION_PLAN.md` stages G2 and G4, before
either drive ran. Measured the same day. All four cuts are built; the first three were graded in
that day's drives and cut 4 (G5) was built and graded the same evening, which is what rows R4-R6
and the second mutation run below are.

**Question** `asc-09wx.14` asks for four cost cuts to the pre-commit gate, each graded against
recorded timings. Does the skip rule select the sets the plan claims it selects, does a narrowed run
leave the baseline scan alone, and what does each cut that exists actually buy on this machine?

## Method (fixed before measuring)

- Stage G1 made the gate write one JSONL row per run to `.ascend/gate-runs.jsonl`. Every timing
  below is a row from that file or a command's own output, pasted verbatim rather than summarised.
- The drives run the **real spliced hook** — `.beads/hooks/pre-commit`, the file git actually
  invokes — not `scripts/gate.mjs` directly.
- Machine load is reported per row, because this repo's own prior measurement is that gate cost
  moves with load rather than with the diff (`ascend-gate-cost-and-corpus-flake`: 229 s quiet,
  672 s loaded).
- The selection sets are asserted by `scripts/gate-scope.test.ts` against the derived mapping, not
  read off this prose.

## Predictions

From G2 and G4, written before the drives:

- **P1.** A `packages/core` change selects the `core`, `store`, `adapter` and `cli` test files and
  nothing else.
- **P2.** A `packages/analysis` change selects `analysis` + `cli`.
- **P3.** A root `package.json` change selects everything.
- **P4.** An `.ascend/*.jsonl`-only commit is **inert**: the suite and the baseline check are
  skipped, and the row records both as skipped.
- **P5.** A subset run leaves `.testcount/scan.json` untouched, and the row says the baseline check
  was skipped.
- **P6.** The pre-push hook runs the full suite.
- **P7.** G6's own rule: a cut that does not pay is reported as not paying.

| | Prediction | Verdict |

| P1 | `packages/core` selects core, store, adapter, cli | **Held** — `gate-scope.test.ts`, *"selects a core change to every package"* |
| P2 | `packages/analysis` selects analysis + cli | **REFUTED** — it selects analysis, **cli, core and store** |

**P2's refutation is the one that changes a claim in the plan, and it widens the reachable set
rather than narrowing it.** `PACKAGE_SCANNERS` adds `core`, `store` and `cli` to *every* package's

those two**. What cut 3 buys is that `store`, `analysis` or `cli` changes do not pay for the
adapter's corpus sweep. The plan states this consequence in G4; the prediction as originally
written did not have it.

### Cut 1 — the inert skip — pays

R1 vs R0. The suite is absent from R1's step list entirely, and the row says why twice: once for
`test`, once for `test count`. Four check steps, `total_ms` **38,540**, `outcome: "ok"`.

The suite's own cost is readable from R0: **1,427,295 ms** on the `test` step alone, out of a
`total_ms` of 1,621,182. R1 ran under higher load (first loadavg 33.15 against R0's 27.04) and cost
**2.4%** of R0's total. The check steps are not free — 8.7 s to 28.5 s each across the three drives —
but the suite is the whole of the cost, and cut 1 removes all of it for a commit no test reads.

### Cut 3 — the related-tests subset — pays about a quarter, and the absolute ms is not usable

**Absolute times are not a grading unit on this machine, and the record says so with its own
numbers.** The same suite, same tree, three runs:

| run | wall | note |
|---|---|---|
| R0's `test` step | 1,427,295 ms | gate row, loadavg[0] 27.04 |
| an isolated `pnpm test` earlier the same day | 620,420 ms | vitest Duration, load not recorded |
| an isolated `pnpm test` at the end of this work | 356,600 ms | vitest Duration, `356.60s` |

A fourfold spread across identical work. So the cut is graded on the **fraction of the suite it
removes**, measured in same-load pairs, and two independent pairs agree:

| pair | full | subset | subset as a fraction |
|---|---|---|---|
| R0 / R2 (gate rows) | 1,427,295 ms @ loadavg[0] 27.04 | 344,992 ms @ 30.77 | **24.2%** |
| back-to-back, isolated runs | 356.60 s @ loadavg 32.6→21.8 | 257.37 s @ 32.6→21.8 | **72.2%** |

Two pairs, a 24% cut and a 28% cut. They bracket rather than agree exactly — the load average is a
one-minute figure and neither pair was taken with the machine held still — but both say the same
thing: **cut 3 removes roughly a quarter of the suite's wall time**, and it removes exactly one
package.

The subset's composition is the mechanism, and it is countable rather than timed. From the two
back-to-back runs, verbatim:

```

      Tests  3502 passed | 2 skipped (3504)
```

```
 Test Files  113 passed (113)
      Tests  2635 passed (2635)
```

**35 of 148 files and 869 of 3504 tests**, which is `packages/adapter-claude-code/test` — the
corpus sweep. That is the whole of the cut, and it is the honest bound on it: a `store`, `analysis`
or `cli` change stops paying for the adapter's sweep, and a `core` or `adapter-claude-code` change
still runs everything (P2's refutation above).

R3 is not used in either pair: it ran the same package set as R2 (397,817 ms) at loadavg[0] 93.50,
and that figure is the load rather than the scope.

### Cut 2 — the cross-session lock — pays, and here is the number

The lock's payoff is not a saving on a quiet machine; it is that two sessions committing at once do
not run two suites concurrently. R2 and R3 carry `waited_ms: 0` and `broke_lock: null` — **no wait
occurred in either drive**, because each drive was the only gate running. What those rows cannot
show, R6 does.

**R6 waited 196,321 ms** on another session's gate, `broke_lock: null` (the holder released rather
than aged out), and the wait is recorded where the design says it must be: R6's own `wall_ms` is
12,663 and its longest step is 5,586, so 196 s is not inside any of them. The two rows also
cross-check each other: R6's row is at `01:40:32.976` and its wall is 12.663 s, so its first step
began at `01:40:20.313` — 0.357 s after R4, the holder, appended its row at `01:40:19.956`. Release
and first step are a third of a second apart, visible in the record alone.

What that measures is the mechanism, and it is worth being exact about what it is not. The waiting
run paid 196 s of wall clock; the saving the cut buys is that one machine ran one suite instead of
two, which is a claim about throughput under load and not about a single run's duration. This record
has no second machine and no controlled load, so it reports the wait as measured and the saving as
argued. The mechanism's four properties (a second acquirer waits, a dead pid is broken, the lock is
released on both paths, and the wait lands in the row and not in a step) are covered by
`scripts/gate-lock.test.ts`; R6 is the first field evidence that the wait happens at all.

### Cut 4 — the tree-hash memo — pays, and by the widest margin where it applies

R4 and R5 are the same tree in the same checkout, 89.2 s apart:

| | R4 — the pass | R5 — the hit |
|---|---|---|
| steps | six, every one `status: 0` | **none** |
| `total_ms` | 299,574 | **0** |
| `wall_ms` | 299,578 | **1** |
| `skipped` | `[]` | every step, each `this tree already passed the gate` |

R5 is 1 ms against 299,578 ms, and it is not a narrowing: the row's `steps` is empty and each of the
six steps appears in `skipped` with its reason, so an absent step is never mistaken for one that
passed. The memo's own timestamp is printed, which is what makes the answer checkable — "already
passed" invites "when, and by what?", and the output answers both. R4's suite alone is 274,002 ms,
and the hit removes all of it.

**The key is what makes this the amend case rather than a lucky match.** R4's row carries
`head: cce0502` and R5's carries `head: 0bf9ce7`: a commit landed between them, and the trees agree
anyway, because the thirteen paths staged in R4 became that commit. That is exactly the claim
`git write-tree` supports and a diff cannot — after a commit the index equals `HEAD`, so
`git diff --cached` is empty while the tree is byte-identical to the one that passed. R5's scope is
`full`, chosen because nothing is staged, which is the amend's own shape: the run wanted six steps
and got none. The amend itself, made and then amended with `--no-edit`, is pinned end to end in
`scripts/gate-memo.test.ts`, where it is also the test that kills the "hash the diff instead of the
tree" mutant.

**The coverage rule was built, measured, and removed.** The first draft made a hit conditional on
the record covering every step the new run would take, so a record from a narrower run could not
answer a wider one. Measurement refused it: a subset record covers five steps and the amend wants
six (the sixth is `test count`, which a subset run skips), so the rule vetoed every amend there is —
the one case the cut exists for. It is gone, and the direction it left open was closed above the
module instead: `memoAllowed` refused the memo whenever `ASCEND_PRECOMMIT_FULL` is set, which
`.githooks/pre-push` sets on every push. That guard was pinned by its own end-to-end test.

*Corrected 2026-10-14 (`dogfood/0099`, `asc-bo87`).* That refusal was withdrawn, on measurement. Git
runs a pre-push hook once per `git push` COMMAND it is handed, and `but push` pushes a stack one branch
at a time — so the flag `.githooks/pre-push` sets is set for the whole of a push, and the guard took the
push path's own record down with the commit's. A two-branch stack therefore paid this gate twice over
one index, 302.4 s and 259.0 s of a 568 s push. The distinction the guard wanted is not
commit-versus-push but what a record has actually run, and it is now a bar the caller sets:
`requiredOf` in `scripts/gate.mjs` requires `align check` of a run that took no cut, and nothing of a
commit. That is the narrow half of the coverage rule above, which itself remains removed.

**The bound, stated so it cannot be read as coverage.** The key is the INDEX; the gate's steps mostly
read the WORKING TREE. `scripts/gate-memo.test.ts` asserts, under the name *"is a statement about the
index, not about the working tree"*, that an unstaged edit which leaves the index untouched still
hits. So a hit says the commit being judged is byte-identical to one that passed — not that the
working tree is the tree that passed. Widening the key to the worktree is possible and deliberately
not built: nothing has measured that the amend case is not the whole of the value.

### P7 — did any cut fail to pay?

No cut failed to pay, and the sizes are not close to each other. Cut 1 removes 97.6% of the run it
applies to. Cut 3 removes between 44% and 76% of the suite depending on which full run it is
measured against. Cut 4 removes 100% of a run's steps when its index is one that already passed —
299,578 ms to 1 ms in the R4/R5 pair. Cut 2's payoff is throughput under contention rather than a
shorter run, and R6 is its first measurement.

### A defect the drive found, which no test could

R2 blocked on an arm that passes in every environment except the one the gate creates. The subset
step exports `ASCEND_TEST_SCOPE=subset`, every descendant inherits it, and
`packages/cli/test/dev-hooks.test.ts` — inside the `cli` subset, driving the real hooks — spawned a
full gate that then told the reporter it was narrowed. The reporter's rule is *absent means full*,
which a nested run cannot satisfy. Filed `asc-qa44`, recorded `dogfood/0090`, pinned by mutant M12,
fixed, and R3 is the re-drive that does not carry the arm.

no failing test and concludes *nothing catches this*, when in truth nothing ran it: a mutant that
cannot parse and a mutant nothing catches are indistinguishable under that instrument. **The runner
does not have this gap**, and that was measured too: the same unloadable spelling reports `DEAD KILLER
-- the file ran no test`, quotes the error (`ran no test: Error: Expression expected`), and counts as a
problem — `1 mutant(s), 1 problem(s). FAILS.`, exit 1 — because it reads vitest's summary line rather
than `assertionResults`. So the trap is in the author's hand-run, not in the tool. M7 was respelled to
keep the module valid and killed in two places; the measured pair is written into the spec's own header
and filed as `dogfood/0094` / `asc-funq`.

## Limitations, stated plainly

- **Cut 4 keys on the INDEX, not on the working tree.** A hit says the commit being judged is
  byte-identical to one that passed; it does not say the working tree is. The bound is asserted in
  `scripts/gate-memo.test.ts`, under the name *"is a statement about the index, not about the working
  tree"*, so it is a pinned limitation rather than prose.
- **The run that wrote cut 4's memo is not one this drive started.** R4 was already in flight in this
  checkout when the drive began; R5 is the run the drive made. They are compared as the same tree in
  the same checkout, which the trees' agreement and the `checkout` field in the memo both establish,
  but the pair is not a before-and-after the drive sequenced.
- **R6 is an artifact and is evidence about the lock only.** Its staged set was a temporary index this
  drive built, so its 764-path scope and its `store verify --staged` block say nothing about the gate.
- **The gate's cost moves with load**, and the drives ran with other work in flight. The R0/R2 pair
  is the only same-load comparison in the record; every other ratio carries the confound and says so.
  R4 and R5 are 89 s apart but are not a cost comparison at all — R5 ran no steps.
- **R0 is not a clean baseline for a commit.** Its `staged` set is empty because it was written by
  the suite's own fixture driving the gate in the real repository, not by a staged commit. It is a
  run of every step, which is what the before-number needs, and it is one run.
- **Nothing here is committed.** The change set is uncommitted under the conservative git profile,
  and one push remains the owner's to run.
