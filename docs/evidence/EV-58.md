# EV-58: do commit-time features a live session can compute predict a fix, on n8n?

**Status**      Measured 2026-10-13 for `asc-vsqm`. Predictions and the bar were in the bead's notes
                before the feature script existed; not sealed by sha256. The `risers_count` table
                was added after the first run was read and is exploratory.

**Question**    The owner's direction: git and issue signals arrive too late to propose a
                betterment in time. If a property of a change can be computed at the moment of
                the edit or commit, and that property predicts a later fix, the slow corpus can
                teach a live rule. Do any such properties predict `EV-57`'s outcome?

## Method

`EV-57`'s 15,398 eligible commits and its outcome (a fix rewrites one of the commit's lines within
30 days). Five features, each computable in a live session from file events and the local repo:

- `no_test_alongside`: adds source lines outside test files and touches no test file.
- `large`: more than 200 added source lines.
- `hot_file`: touches a source file changed 5 or more times in the previous 30 days.
- `first_touch`: the author has never before changed any of the commit's source files.
- `cross_package`: touches two or more directories under `packages/`.

Size is a mechanical confound (more lines, more to fix), so each risk ratio is a Mantel-Haenszel
ratio stratified by tercile of added lines and by change type; `large` is stratified by type only.
Learned on 2022 to 2025 (9,185 commits), confirmed on 2026 (6,213), and again on the 2,262
agent-marked commits of 2026.

**The bar, fixed beforehand:** stratified risk ratio at least 1.5 with prevalence between 5% and
60% in the learning years, and at least 1.3 in 2026 and among agent-marked commits.

## Predictions

P1 `no_test_alongside` does not reach 1.5. P2 `hot_file` does. P3 the raw rate rises across size
terciles, top over bottom at least 3. P4 `first_touch` does not reach 1.5. P5 whatever reaches 1.5
holds at 1.3 in 2026 and on agent-marked commits. P6 at most one feature clears the whole bar.

## Decision

**The bridge holds on its first test: three properties a live session can compute predict a later
fix, and they predict it at least as well for agent-marked commits.**

1. **Together they grade risk.** A commit with none of the three is fixed 4.9% to 8.2% of the
   time; with all three, 40.8% to 49.4%. On agent-marked commits of 2026 the range is 4.9% to
   42.8%, and 17.2% of them carry all three.
2. **"No test alongside" is not a signal here.** After size it is 1.0. A rule that nudges for a
   missing test file would have fired on half the learning-years commits for nothing.
3. **Transfer from human to agent work was the open assumption, and on this repo it held.**
4. **This predicts; it does not show a nudge would help.** A session told "this change is large,
   in a busy file and spans packages" may be unable to do anything but take more care. Whether
   that changes the outcome is a question for the holdout, not for this corpus.

Three weaknesses to carry forward:

- **`hot_file` may partly restate the outcome.** A busy file has more later commits, so more
  chances that one of them is a fix rewriting a line. Size strata do not remove that.
- **Precision is modest for one feature alone**: 26% to 34%, against a base of 16% to 18%.
  The count of features is the usable form, not any single one.
- **Terciles are a coarse control for size**, and `cross_package` cleared by the narrowest margin.

Next: compile the three-feature count into a handler and replay it over our own transcripts for
its trigger rate, before any nudge is written; and repeat this on a second repo, since a rule
learned and confirmed in one repository is still one repository.

## Confidence

**High** for the counts. **Medium** that the three features carry real signal beyond size: the
ratios are stable across three samples, and the weaknesses above are untested. **Low** that a
live nudge built on them changes anything. One repo; blame's limits from `EV-57` apply.
