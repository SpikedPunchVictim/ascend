# EV-48: is a session's `timestamp` a sound order across streams, and where does a reviewer's finding sit relative to the edit it concerns?

**Status**        Measured 2026-10-10 for `asc-gtnu.7`, `derive_version` 11. Four measurements, all
                  read-only, predictions written into each script's header **before** it ran. One
                  prediction confirmed decisively, one refuted, and the run turned up a property of
                  the derived type that neither script predicted. The direction result (measurement
                  4) is the weakest of the four and is reported with its limits rather than as a
                  finding.

**Question**      `asc-gtnu.7` refuses a cross-stream `before:` because "the event before this
                  trigger" across two streams has no defined order, and it gates its cheapest
                  remedy — *"an ordering key that is total across streams"*, derived from `ts` — on
                  one thing it names explicitly: **"a measurement of intra-session cross-stream skew
                  is the prerequisite."** The bead also sets its own reopen condition, added from
                  `asc-gtnu.8`/EV-28: build only once there is *"a session in which a reviewer
                  reports on an implementer's live edits … and a real reviewer's finding-to-edit
                  distance is measured."* This record answers both, and answers a third question the
                  first two turned out to depend on.

**Method**        Two throwaway probes under `spike/review-join/`, each carrying its own
                  pre-registered predictions in its own header, each reading `~/.claude/projects`
                  and the local store without writing or copying anything.

                  1. **`skew.mjs`** — for every session with a `subagents/` directory, match each
                     `agent-<id>.jsonl` to the `Task` tool_use that spawned it (through the
                     `agentId` named in the *first* tool_result that references it) and to that
                     Task's own result. **P1:** every subagent's first event is stamped at or after
                     its spawn. **P2:** every result is stamped at or after the subagent's last
                     event. **P3:** the startup gap is small on the wall clock.

                  2. **`backward.mjs`** — join each `review_finding` to the main stream's
                     `Edit`/`Write` on the file that finding names, and measure the distance from
                     the finding's `occurred_at` to the nearest edit on each side. **P1:** most
                     findings resolve. **P2:** the nearest edit is *before* the finding — the
                     backward shape the bead's title asserts. **P3:** the backward gap is small.

                  The `agentId` join is deliberately conservative: an `agentId` is mentioned again
                  later in a transcript (*"Use SendMessage with to: 'a…'"*), and a resumed subagent
                  keeps **appending** to its own file, so taking the last mention maps a stream's
                  last event against a timestamp from days afterwards. Only the first result whose
                  `tool_use_id` is a Task spawn the stream itself made is used. Getting this wrong
                  the first time produced a −2-day outlier; the fix moved the counts by 4 of 1514,
                  which is itself the evidence that measurement 3 is about the data and not the
                  join.

**P1 is confirmed: 0 of 1,514.** Not one subagent in the corpus is stamped before the Task that
spawned it. The startup gap is p50 2.0 s and p99 42.8 s — child-process latency, which is what P3
predicted. **The two files share a clock, so `ts` is a sound cross-stream ordering primitive within
one session.** The prerequisite the bead named is discharged, and option 1's stated blocker is
gone.

## Measurement 3 — P2 is not skew, and it is the more interesting result

P2 is violated in 99.7% of pairs by a median of −734 s. Since P1 establishes one clock, this cannot
be skew, and the worst case says what it is instead:

```
most negative teardown: -175105218 ms  (a35f6ba323080e5eb, b1504bbe-72f8-4161-b8df-497e2b269024)

file:   …/b1504bbe-…/subagents/agent-a35f6ba323080e5eb.jsonl
events: 492   first: 2026-10-07T20:07:04.469Z   last: 2026-10-09T20:45:30.006Z
largest gap: 109593606 ms  [ '2026-10-07T21:15:03.744Z', '2026-10-09T03:41:37.350Z' ]
distinct parentUuid: 404
promptIds: 11
```

One `agent-<id>.jsonl`, **492 events over two days, 404 distinct parent events, 11 distinct
prompts, and a single 1.27-day gap.** A subagent's file is not bounded by the Task that spawned it:
it accumulates every **resume** of that agent, and `SendMessage` re-invokes an agent rather than
starting one. So *"the stream"* is an agent's whole lifetime, not one Task invocation — which is a
fact about the corpus that the bead's option 2 (interleave the streams of a session) assumed away.
Interleaving `b1504bbe`'s streams means interleaving multi-day agent lifetimes, not session-scoped
tasks, and any handler that treats a stream as a unit is treating 11 episodes as one.

**This measurement was not asked for.** Both probes were pointed at the ordering question, and
neither predicted it. It is filed as `asc-n793` rather than acted on here, because what is missing
is not a fix — `asc-6ola.12` built the stream model as *one normalized stream per (session_id,
agent_id)* deliberately, so a two-day stream is the design and not a bug in it. What is unmeasured
is what assumes a Task result *ends* a stream, and that is a question for the consumers
(`subagent.outcome`, `skill_activation`, the derived `session.end` boundary) rather than for this
record.

```

   ... and a strictly-before edit exists:    52 of 61 (85.2%)
   ... and a strictly-after edit exists:     60 of 61 (98.4%)

backward gap (finding - last edit): min 1384542  p50 18191074  p90 252468255  max 558317455  (ms)
forward gap  (first edit - finding): min 292480  p50 8108322  p90 81199410  max 84325755  (ms)

per session:
  96a5a5d3  findings  12  backward   6  median backward 59433092 ms
  b5d54754  findings  45  backward   8  median backward 2788507 ms
  df503f84  findings   4  backward   0  median backward - ms
```

**P2 is refuted.** Written before the run, it predicted the nearest edit would be *before* the
finding, which is the backward shape the bead's title asserts. The nearest edit is before for only
**14 of 61 (23.0%)** and after for 47 (77.0%).

**P1 is partly refuted too, and by more than expected.** Only 61 of 157 findings resolve at all.
34 are `saul` findings whose transcript no longer exists and can never be resolved; the remainder
name files the same session's main stream never edited.

**Why this measurement is the weakest.** Four limits, stated because the number is being used to
decide something:

- The finding's `file` is a **basename** (`migrate.ts`) while an edit carries an absolute path, so
  the join is a suffix match. Two files sharing a basename in one session would collide.
- `occurred_at` is **not a per-finding clock** — see below — so "distance from the finding" is
  really "distance from the report that contained the finding".
- n is 61 pairs over 3 sessions, and one session (`df503f84`) contributes 4 of them.
- "Nearest edit" is a proxy for the join a handler would want. A handler asking for *the code as the
  reviewer saw it* wants the last edit before, whether or not a nearer edit follows — so a
  23%/77% split does not by itself settle which join is the one to build. It does refute the claim
  that the backward direction is the *dominant* one.

## What the run turned up that neither probes predicted: a finding has no clock of its own

Investigating why 96 findings did not resolve produced a sharper fact than the direction split.
`ReportFindings` takes an array, and one call produces many findings:

```
$ asc query "SELECT session_id, COUNT(*) n, COUNT(DISTINCT occurred_at) distinct_ts FROM v_review_finding_v1 GROUP BY session_id ORDER BY n DESC" --json
{"ascend_output":3,"rows":[{"session_id":"df503f84-…","n":58,"distinct_ts":1},{"session_id":"b5d54754-…","n":45,"distinct_ts":5},{"session_id":"2563912b-…","n":34,"distinct_ts":2},{"session_id":"96a5a5d3-…","n":12,"distinct_ts":1},{"session_id":"b286a945-…","n":8,"distinct_ts":1}],"row_count":5,"coverage":{"shown":5,"total":5,"has_more":false,"percent":100}}
```

**58 findings share a single `occurred_at`.** A `review_finding`'s timestamp is the *call* instant,
not the finding's own, and the entry carries the call's identity as `tool_use_id`
(`toolu_013SMqqQVfuuVaE8oF` → 58 findings; `call_g2giq5ii` → 24; `call_50oiyvvf` → 15). The entries
are not wrong — they were genuinely reported at one instant, and that is the honest timestamp for
the event — but it means **a `before:`/`after:` on a finding is decided once for the whole batch**,
and findings cannot be ordered among themselves by time.

That matters to the bead's remedy rather than to its premise. `occurred_at` was the obvious anchor
for "the event before this finding"; it is a batch instant shared by up to 58 entries, so the
anchor has to be `tool_use_id` (the report) or the finding's `file`, not its timestamp.

## Decision

Recorded against the bead, not taken here: this record measures, and `asc-gtnu.7` is where the
mechanism gets chosen. What the numbers settle is the *shape* of the choice.

- **Option 1's blocker is gone.** `ts` is sound across streams within a session (0 of 1,514), so a
  total ordering key derived from `ts` is defensible on measurement rather than on assumption.
- **But the key does not solve the reviewer case on its own**, because the finding's own timestamp
  is batch-level. The anchor a cross-stream join would need is already on the entry — `file`, and
  `tool_use_id` — and neither is a time.
- **Option 2 got more expensive, not less.** A stream is an agent's lifetime (492 events, 11
  prompts, 2 days), so "interleave the streams of a session" is a larger operation than the bead
  describes.
- **The direction is unsettled.** The bead's premise that the join is backward is refuted as a
  *dominance* claim (23%), not as a possibility (85% of pairs do have an earlier edit).
- **The handler that wants the join is live.** `review-finding.yaml`'s header says it *"reports 0
  rows today"* (re-measured 2026-09-26) because `ReportFindings` had been called 0 times. The 157
  findings split `captured_by` 112 `parsed` (the `review-finding-table.yaml` route) and **45
  `reported`** — so the route that names the missing join is now firing against real findings, and
  all 45 are in one session, this one. That is n = 1 on ascend's own repository: the route is
  demonstrated to fire, not demonstrated to be depended on.

## Confidence

- **`ts` is a sound cross-stream order within one session — `Confirmed (empirical)`.** 0 violations
  in 1,514 pairs, with the join itself validated by the fact that fixing it moved 4 counts.
- **A subagent stream is not bounded by its Task result — `Confirmed (empirical)`.** 1,510 of 1,514
  violations with one clock, and the worst case read out in full.
- **Reviewers exist and report in batches under one timestamp — `Confirmed (empirical)`.** Counted
  from the store's own view.
- **The finding→edit join is forward-dominant — `Traced`, not confirmed.** n = 61 over 3 sessions,
  a basename-keyed join, and one session supplying 4 of the pairs. It refutes a dominance claim; it
  does not establish the opposite one.
- **A handler states that it wants this join — `Traced`.** `handlers/review-finding.yaml`'s own
  header names *"the question this handler would want to ask next — did the implementer touch this
  file before the finding"* as a *backward, cross-stream* join, and says the handler *"emits the
  finding and says nothing about what it refers to"* because Stage 3 refused it. **This sentence
  originally read "no handler consumes this join today, so the demand side is unobserved", and that
  was wrong** (corrected 2026-10-10, minutes after the entry was recorded). What is true is the
  narrower thing: the demand is *stated in the tree* and *not exercised* — the handler emits and
  stays silent, so no usage exists to measure, and the statement of intent comes from the same
  design pass that filed the bead rather than from an independent one.
- **Not measured.** Whether a *different* handler would reach for the same join — only
  `review-finding.yaml` names it, and no handler has ever run it against a real finding. And the 34
  `saul` findings are permanently unresolvable; their transcript is gone.
