# EV-29: does a derived entry's type depend on the one before it, within a session?

**Status**      Measured 2026-09-28 for `asc-ks5` (a). The question, the null, the statistics, the
                predictions and the decision rule were written into the bead's notes before any
                ordered data was read; only the per-type totals had been seen. **Three of four
                predictions hold; the one that fails is the one that said the signal is mostly
                same-type runs.** Every cross-type cell that survives correction with a non-anecdotal
                expectation is a *deficit*, which is what phases within a session produce, and the
                null used here does not control for phases.

**Question**    Within a session, does an entry's type depend on the type of the entry before it
                (order-1), beyond what that session's own mix of types explains (order-0)? Asked
                because a Markov chain over entry types is the obvious next tool, and it buys only
                parameters if the marginals already explain the pairs.

## Method

Script: `spike/order-test/order.mjs`. It reads the store only through `asc query` and prints
counts, never entry text.

- **Data.** The live store's entries with `source = 'derived:claude-code'` and no `invalidation`
  annotation, all six derived types. Grouped by `properties.session_id` and ordered by
  `properties.occurred_at`, then `id`.
- **Ties.** An adjacent pair whose two entries share `occurred_at` is excluded, from the observed
  counts and from every permutation alike. A tie is ordered by `id`, and the id embeds the type
  name, so counting ties would manufacture same-type pairs.
- **Null.** EV-19's technique: permute the type labels within each session over fixed positions.
  10,000 permutations, `mulberry32(seedOf('ascend'))` from `packages/analysis/src/random.ts`.
  Because positions are fixed, the tie mask is the same in every permutation.
- **Statistics.**
  - E[cell] is the null mean.
  - G = Σ (obs − E)² / E over the cells with E > 0, and its permutation p is
    (1 + #{G_perm ≥ G_obs}) / (1 + N).
  - G_off is the same, over the off-diagonal cells only.
  - Each cell also gets a two-sided permutation p, corrected with Benjamini-Hochberg
    (`packages/analysis/src/association.ts`).
  - A cell with E < `MIN_N` (20) is labelled an anecdote whatever its p.
- **A smoke run** with 200 permutations came before the registered run, to check that the script
  worked. Its G and p agree with the registered run to the precision its permutation count allows.
  It is reported here because it came first.

## Predictions (verbatim from the bead, frozen before measurement)

- **P1 order exists:** G has p < 0.01. Falsified if p >= 0.05.
- **P2 it is mostly burstiness:** the diagonal cells contribute more than half of G. Falsified if <= 50%.
- **P3 some cross-type order exists:** G_off has p < 0.05 (low confidence). Falsified if p >= 0.05.
- **P4 thin cells:** fewer than half of the 30 off-diagonal cells have E >= MIN_N.

**Decision rule:**
- **P1 fails:** stop, and record a decision that order carries no signal and (b) is not built.
- **G significant but G_off not:** order is same-type runs only. Stop, because (b)'s lag question
  is cross-type.
- **G_off significant:** file a bead for (b), naming the BH-surviving off-diagonal cells with
  E >= MIN_N.

## What it means

Order carries signal, so an order-0 description of a session is not the whole story. But the
signal has one shape: **entries come in same-type runs, and the types that avoid each other are
verification runs and everything else.** A session has stretches of test-running and stretches of
denials or compactions, and adjacent entries tend to come from the same stretch.

That is a claim about *phases*, not transitions. The within-session shuffle assumes that any type
is equally likely at any position in its session. A session that does its verification in one half
and its denied tool calls in the other breaks that assumption without any entry influencing the
next. So this null cannot tell "A makes B less likely next" from "A and B live in different parts
of the session". **Every surviving cross-type cell is a deficit, and a deficit is exactly what
phases predict.** No surviving cell is the excess that a predictive transition, the kind a lag
question is about, would produce.

## Limits

- **45 sessions, 36 with more than one entry.** Pooled over projects, but the null conditions on
  the session, so project mix cannot create the signal.
- **Subagent entries share their parent's `session_id`,** so a subagent's entries interleave with
  the main stream's by timestamp. Cross-stream timestamp skew is not measured here
  (`dogfood/0006` is the series record for that class).
- **Ties:** 207 of 2,891 adjacent pairs were excluded as ties. By `asc query` with `lag()` over
  the same ordering:

  | pair | ties |
  |---|---|
  | `tool_denial -> tool_denial` | 110 |
  | `review_finding -> review_finding` | 60 |
  | `tool_denial -> user_correction` | 24 |
  | `tool_denial -> verification_run` | 8 |
  | `verification_run -> verification_run` | 3 |
  | `skill_activation -> skill_activation` | 1 |
  | `context_compaction -> context_compaction` | 1 |

  All 24 `user_correction` entries tie with a `tool_denial`, because both are derived from the same
  rejected tool result. So the pair a lag question would most naturally ask about is simultaneous
  by construction, and this test cannot see it. The same construction is behind
  `tool_denial -> user_correction` showing 0 counted pairs against E = 5.79.
- **The null is exchangeability within a session.** It is the null named in advance, and the
  paragraph above is about what it cannot separate.

## Decision

The rule's third branch fired: G_off is significant, so a bead is filed for (b). Following this
record, **that bead's first step is a null that preserves phase**: a shuffle within blocks of
time or of position, or a comparison against the entries k steps away. Only a cross-type effect
that survives that null is a transition worth a lag question. If none does, (b) stops there, and
(c), a chain at the transcript layer, stays closed with it.
