# EV-24: what share of reading buys nothing, and is "read.unused" trustworthy enough to say so?

**Status**      Measured 2026-09-25 for `asc-6ola.8`. Predictions were written to the bead's notes
                (PREREG, 2026-09-24) before any read.unused count was run; the labelling rules
                were fixed in the same PREREG before any row was hand-labelled. All three
                predictions missed. The handler and the DSL constructs it forced are sound; the
                headline rate is not trustworthy as a main-stream intervention candidate.

**Question**    For `asc-6ola.8`: *"what share of reading buys nothing, and in which situations?"*
                Also the acceptance case for three DSL promotions: `window.<mode>.any`
                (per-kind watchers), `shares_token` on array fields, and `absent` +
                `until: session.end` emitting at stream end.

## Method

One handler, `handlers/read-unused.yaml`: `on: file.read`, an `absent` window with
`until: session.end`, replayed by `asc handlers check` machinery (the production normalizer and
evaluator, `derive_version` 2) over the live log through a scratch script.

"Used" was fixed in the PREREG before any count. A read is used when, LATER in the same
`(session_id, agent_id)` stream, one of:

1. a `file.changed` event carries a path equal to the read's full path;
2. a `command.run` argv element equals the read's basename, or shares a ≥ 4-char
   `[a-z0-9_]` token with it (handlerTokens, stop list applies);
3. a `search.run` whose pattern shares a ≥ 4-char token with the basename.

A re-read alone is NOT a use. Assistant text is invisible to the event log, so text-only use is
out of scope and expected as a false-positive source, measured — not patched silently. Reads
with an absent path are refused at compile time. Failed reads (the read call's `tool.use.end`
carries `is_error` true) are excluded from the denominator, counted, and reported.

Each emitted row was hand-labelled TRUE / FP / UNCLEAR under rules fixed in the PREREG
before labelling; FP rate = FP / (TRUE + FP), UNCLEAR excluded and reported. The sample is 27
emitted rows (17 main, 10 sub) plus a 10-row mirror sample of main reads the handler classified
as used, to estimate the false-negative side.

Horizon: 79 files, 105,938 events, 2026-09-12T01:07:55.847Z → 2026-09-25T00:32:21.527Z,
derive_version 2, ingest counters: records 82,690, unfinishedCalls 1, unmatchedNotifications 51.

## Predictions (bead PREREG, before measuring)

- **Q1:** unused share of main-agent reads, 25–40%. Fable review: 532/1,973 = 27.0% never
  named again in a later tool input (basename match, not re-verified). Reasoning: excluding
  re-reads as use raises it, token overlap over argv/pattern lowers it.
- **Q2:** false-positive rate on a hand-labelled sample of 25 (bead requires ≥ 20): 10–25%.
  Expected main FP source: use visible only in assistant text.
- **Q3:** non-code paths have a HIGHER unused share than code paths, by ≥ 10 points,
  mirroring EV-23's edit gap (31.7% non-code vs 10.5% code).

## What the split actually shows

The pooled 17.1% is two populations wearing one number:

- **Main-agent reads are almost never wasted BY THIS DEFINITION** — 2.0% raw — and the few
  "unused" verdicts it does emit there are majority false positives (7 of 11 non-UNCLEAR main
  rows). The dominant missed-use channel is use embodied in edits to OTHER files: read a
  module, write a different one informed by it. A same-path, same-stream definition cannot see
  that, and no amount of token tuning fixes it.
- **Waste concentrates in subagent exploration** — 27.3% raw; the labelled sub sample puts FP
  at 2/7 non-UNCLEAR, so roughly **19–20% of subagent reads are genuinely unused** even after
  the FP adjustment. A subagent's read is judged within its own stream, which is the scope the
  PREREG fixed, and that scope is right: a subagent reports back as text, so its "use" genuinely
  is its parent's problem, not its stream's.

The mirror sample is the one clean positive: the handler emitted 0 false negatives on 10
main reads known to be used, so the low main rate is not undercounting in the direction that
would flatter it.

## Against Fable's 532

Denominator close (1,988 vs 1,973); numerator not comparable (340 vs 532), and the difference
cannot be traced — Fable's method was never recorded. A basename-only match (Fable's) finds
FEWER uses than token matching, which would push Fable's number UP, not down; the remaining gap
is unexplained. As with EV-23, the lesson is that an unrecorded method cannot be audited.

## Limits

- **One project, one operator** — n = 1 at the project level; no claim about other projects.
- **Single rater, and the rater wrote the handler.** All labels are mine; there is no second
  rater and no κ.
- **Current-session rows judged with privileged knowledge.** Several labelled rows are reads
  from this very session, whose in-flight use I know in a way the replay does not; the label
  rules forced some of these to UNCLEAR for exactly that reason.
- **Assistant text is invisible.** Text-only use is structurally an FP here; 3 of the 7 main
  FPs are exactly that.
- **Sub sample is small.** 10 rows, 7 non-UNCLEAR; the "roughly 20%" figure carries that
  sample's width, and the sub FP rate rests on 2 FPs.
- **Failed reads.** 6 among triggers, 1 emitted (main), excluded from denominators.

## Decision

The three DSL promotions are accepted: each was forced by a real handler (the spike rule),
all four mutations of the new compile/runtime paths were killed by named tests, and the
`absent` + `until: session.end` semantics behave as specified on a 1,988-trigger replay. A
false-green was found and fixed during acceptance — replacing the accept loop's kind check with
the compiled match silently let a `tool.use.start` event satisfy a `check.run` window; the
fixture replay caught what the unit corpus did not discriminate, and the kind check is now part
of the compiled match itself.

`read.unused` as defined is **rejected as a guidance-candidate rate for the main stream**:
2.0% raw, majority-FP at the tail, and the FP class (use embodied in edits to other files) is
not fixable by token tuning. The measurable signal worth carrying forward is **subagent
exploration waste (~20% adjusted)**, and the open question the labels raise is whether
assistant text — invisible to the event log but present in the transcripts — belongs in the
"use" definition at a different layer. That decision goes back to `asc-6ola.8` and the parent
`asc-6ola`.
