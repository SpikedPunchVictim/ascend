# EV-33: what does the REAL index build path cost, and was EV-32's proxy a fair stand-in?

**Status**        Measured 2026-09-29 for `asc-i5tj.2`. **The question was named in advance** — EV-32
                  closed with *"the real build path must be re-timed once it exists"* — but **no
                  numeric prediction was registered**, so this is a measurement and not a test of a
                  hypothesis. n=2: one real corpus and one synthetic 10× replication, the same pair
                  EV-32 used. **The headline is a correction: EV-32's guess that the proxy was an
                  upper bound is wrong, by about 1.2×, and one of EV-32's absolute numbers is not
                  reproducible on this machine today (63.19 s where EV-32 recorded 40.27 s for the
                  identical proxy on the identical corpus shape).** Everything EV-32 decided on those
                  numbers still holds; one thing it could not have seen does not.

**Question**      EV-32 chose the architecture — persist the index, check it with a content hash,
                  rebuild wholesale, no incremental machinery — and said plainly that its timings went
                  through `asc import` as a *proxy*, with a known bias, because the JSONL store did not
                  exist yet. It guessed the proxy was *"plausibly more work than a from-scratch index
                  build"* and therefore an **upper bound**, and marked the guess as a guess. The build
                  path now exists (`packages/store/src/jsonl-index.ts`, `buildIndex`/`openIndex`). So:
                  what does it actually cost, is the proxy the upper bound EV-32 guessed, and does the
                  answer change any decision made on the proxy's numbers?

## Method

**Two paths, one corpus, one machine, one day.** The only way to compare a proxy against the real
thing is to remove every variable except the code, so both arms ran back to back on 2026-09-29 against
the same bytes.

- **The real path:** `buildIndex(root, dbPath, { now })` from `packages/store/dist`, timed in-process
  with `process.hrtime.bigint()`, and separately under `/usr/bin/time -p` for a user/sys split.
- **The proxy:** `asc import <flat corpus>` from `packages/cli/dist/bin.js`, into a freshly `asc init`ed
  directory, under `/usr/bin/time -p` — the same command shape EV-32 timed.
- **The corpus is this project's own store**, exported with `asc export`: 10,299 lines / 7.84 MB —
  17 `type`, 6,387 `entry`, 7 `scheme`, 3,888 `annotation`. EV-32's was 10,240 lines / 7.77 MB of the
  same store a day earlier, so the two are comparable and neither is a fixture.
- **The 10× point is synthetic replication**, and deliberately the SAME replication EV-32 described:
  fresh sha256-derived ids, `recorded_at`/`created_at` shifted 1–10 days earlier so copies interleave
  rather than append in a block, definitions emitted once. Result: 102,774 lines / 71.13 MB, 63,870
  entries, 38,880 annotations — against EV-32's 102,193 lines / 71 MB and 63,290 entries. **The flat
  file the proxy read and the tree the real path read were emitted from the same replication pass, so
  the two arms cannot differ by their input.**

**Two clocks, reported separately, because they measure different things.** `time -p` times the whole
process, which for the real path includes laying the JSONL tree out on disk; the in-process numbers
time `buildIndex` alone. A tree layout is not something a command does on every open — it is the
migration E12.4 owns — so the build-only number is the one the design depends on, and the process
number is given for comparability with EV-32.

**The layout scales the file count, which is the point of running at 10×.** 22 record files at 1×;
39 at 10×, because `entries/` rolls at 5,000 records per file. So the 10× arm exercises the rollover
and multi-file traversal rather than one large file pretending to be a tree.

**A harness bug worth recording, because it looked exactly like a product bug.** The first 10× flat
file was written with raw `JSON.stringify` over parsed lines, and `asc import` refused it: *"line 1 has
no such field 'document'"*. A `CorpusLine` is NESTED in memory (`{kind:'type', document:{…}}`) and
FLAT on the wire; `serializeCorpus`/`orderedLine` is what renders the wire form. A one-line probe
(`parseCorpus` → `serializeCorpus` on a flat type line) showed the codec round-trips correctly, which
located the fault in the harness rather than the product. Had the probe not been run, this would have
been filed as an ascend defect.

## What the numbers decide

**1. The proxy was NOT an upper bound; it is about 1.2× cheaper than the real path.** EV-32 wrote
*"plausibly more work than a from-scratch index build ... so 3.02 s is likely an upper bound"*. Measured
on identical input, `/usr/bin/time -p` user time is 38.1 s (proxy) against 45.4 s (real) at 10×, and the
real path's margin is stable across two runs of each — 45.40 and 45.39 against 38.20 and 38.07. So the
bias EV-32 stated was real but pointed the other way, and the reason is identifiable: `asc import`
streams a flat file, while the real path reads a **partitioned tree** and parses 102,774 lines into
`CorpusLine` objects before replaying them. The guess cost nothing — EV-32 flagged it as a guess and
the decisions it supported were the correct ones — but the direction of the error is now a matter of
record rather than a matter of opinion.

**2. EV-32's ABSOLUTE 10× number is not reproducible here, and the gap is larger than the proxy's
bias.** Running EV-32's own proxy on the same corpus shape today gives 63.19 and 67.98 s where EV-32
recorded **40.27 s** — a 1.6× drift for code that did not change. So a cross-day comparison of
real-vs-proxy would have attributed roughly 1.6× to the code path and 1.2× of it to the machine. Only
the same-day, same-corpus arm pair above can separate them. **The unstated corollary for the rest of
this plan: no EV number measured on a previous day is a usable comparison for a new one** unless it is
re-measured in the same session, which is why both arms were re-run rather than cited.

**3. Rebuild-on-open stays out — more firmly than EV-32 could argue.** 2.97 s is not a per-command cost
and ~75 s is not a per-anything cost. The index must persist and be rebuilt only when its inputs change.

**4. NEW, and the one thing EV-32 could not have seen: a rebuild must never happen silently inside a
read.** `openIndex` on a fingerprint miss calls `buildIndex` with no signal, no progress and no
warning. At EV-32's 3.02 s that is a slow command. At the measured ~75 s it is a command that looks
hung, and a user who ran `asc query` — a read — would sit through it with no output and no way to know
whether to wait or kill it. The cache-hit path is 0.05 s, which is exactly why this was invisible in
every measurement taken at 1×: the cost of the miss and the cost of the hit are both fine in isolation,
and the defect is the *silence*, not either number. This is a design input for E12.3 (the read layer)
and must be settled before the index is on a read path: either the build becomes an explicit command a
read will not run, or a rebuild announces itself before it starts.

**5. The per-record cost of a wholesale rebuild is not a constant, and the growth is in the STORE, not
in the index module.** CPU per record roughly doubles between 6,387 and 63,870 entries (0.30 → 0.60 ms
in the proxy; 0.30 → ~0.71 ms in the real path), so the real path inherits it rather than causing it —
which locates it in the write path both arms share: B-tree insertion, the FTS triggers and the
generated views. EV-32 derived 1.33× growth from its two points; today's two points give 2.0×. A
rebuild therefore costs *more than linearly* per record, which argues the same way as decision 3 and
additionally means any future estimate must be extrapolated from a point near the target size rather
than scaled from 1×.

**6. The content-hash fingerprint stays the right call, and is cheaper than EV-32 thought in-process.**
0.01 s at 7.84 MB and 0.04 s at 71.13 MB with a warm page cache (0.20–0.24 s cold), against EV-32's
0.05/0.24 measured by invoking a hasher as a process. The decision — a content hash over an mtime
heuristic — is unchanged and now rests on an in-process number for the path that actually runs. **The
cache-hit cost a command pays is 0.05 s at 10×**, which is the whole justification for the design.

**7. The index is 2.86× its JSONL at both sizes** — 22.4 MB and 203.1 MB against EV-32's 22.1 MB and
205.9 MB. Consistent, and worth stating because it is the storage a checkout pays for a file it may
delete.

## What this does NOT measure — and where it is still weakest

- **Writes were not re-measured.** EV-32's "0.19 s end-to-end at both sizes" is carried forward
  untouched and is still a proxy's number.
- **n=2 is still one real corpus.** The second point is the same project's store replicated, so it
  exercises size and file count, not a genuinely different corpus's shape or property distribution. A
  second project's store would be the honest n=2 and has not been measured.
- **The 10× spread is wide and unexplained: 73.8 s to 97.8 s across five runs of identical work**, with
  the three slowest in one process after a 5 s tree layout. The direction (real ≈ 1.2× proxy) survives
  because the *user* times are stable to 0.2% across runs, but no single wall-clock figure in this
  record should be quoted to better than ±15%.
- **The 1.6× drift from EV-32's numbers is unattributed.** Page cache, thermal state and free disk are
  all candidates and none was controlled. There is no second machine in this measurement to separate
  "this machine today" from "this machine on 2026-09-28".
- **Nothing here measures the read-time contradiction check** (`asc-2ezs`) or the merge guard
  (`asc-98e1`), both of which add work to paths not yet built — unchanged from EV-32's caveat.
- **`openIndex` was exercised on one miss shape** (the index file absent). A miss caused by a *stale*
  fingerprint — the branch-switch case the content hash exists for — was not timed at scale; it runs
  the same code, but "runs the same code" is an argument, not a measurement.

## Since this was recorded (2026-09-29, same session)

The defect this record surfaced — `openIndex` rebuilding on a fingerprint miss with no signal, ~75 s at
10× — was settled the same day as `asc-i5tj.3.1`: **a read never builds.** `openIndex(root, dbPath)` now
refuses with an `IndexStaleError` naming `asc index build`, and `buildIndex` is reachable only from that
command. So the last caveat above ("`openIndex` was exercised on one miss shape") describes a code path
that no longer exists on the read side: the cost of a rebuild became a property of a command a caller
typed, and the cost of a read is the fingerprint hash plus one SELECT — **0.05 s at 10×**, the cache-hit
number measured in section 6. Nothing above is retracted and the build timings are unchanged in
substance; what changed is who can reach them.
