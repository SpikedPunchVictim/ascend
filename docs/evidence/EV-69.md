# EV-69: once the beads index is delivered, do sessions run `bd recall`?

**Status** Predictions registered 2026-10-13 in the notes of `asc-09wx.7`, before any handler was
run or any `bd recall` call counted. Measured the same day. **Not gradeable yet**, as predicted:
no working session has started under the new hook.

**Question** On 2026-10-13 the SessionStart hook stopped printing every beads memory in full and
began printing an index that says to run `bd recall <key>` (EV-54, EV-55). EV-55 graded delivery
(3 of 43 keys to 43 of 43) and left use resting on one probe per arm. Do working sessions that
receive the index run `bd recall`, where sessions that received the full text did not?

## Method (fixed before measuring)

- **Rows:** three handlers in `handlers/`, replayed with `asc handlers check` over this project's
  transcripts: `beads-recall` and `beads-memories` (one row per call) and `beads-delivery` (one row
  per SessionStart delivery of the beads context, in either form).
- **Unit:** one Claude Code session, all its streams.
- **Arm:** `index` if every beads delivery in the session is `.claude/bd-prime-hook.mjs`, `full` if
  every one is `bd prime`. A session with both, or neither, is excluded and counted, and so is the
  measuring session.
- **Outcome:** the session ran `bd recall` at least once. Secondary: `bd memories`, calls per
  session, keys recalled and whether each names a stored key.
- **Statistic:** share of sessions per arm with a Wilson interval. An arm under 20 sessions is an
  anecdote and is not graded.

### Decided while measuring

- **EV-55's four probe sessions are excluded by id** (`b88730c6`, `e507eb45`, `94e9f65c`,
  `cd3a6cdf`). That measurement launched them with prompts written to test this, and they are
  already reported there. The registration excluded "the session that built the hook" and did not
  name these; without the exclusion the index arm would be two sessions, both of them probes.
- **The handler match was tightened before any arm was read.** `head: bd` with
  `argv: contains recall` matched 37 rows, most of them `bd create "... recall ..."`, because argv
  is split on whitespace inside quotes. The handlers now require `bd` immediately followed by the
  word, and the grader keeps rows whose argv starts with the command.

## Predictions

- **P1.** In the full arm under 10% of sessions ran `bd recall`.
- **P2.** The index arm has fewer than 20 sessions today, so the comparison is not gradeable yet.
- **P3.** The index arm's share is higher than the full arm's (direction only).
- **P4.** In the full arm, `bd memories` was run in more sessions than `bd recall`.
- **P5.** At least half of the recalls in the index arm name a key the index printed.

## Decision

1. **The instrument is in place and the grade is not.** The handlers are in `handlers/` and the
   grader in `spike/beads-recall/`; the same command regrades it later. `asc-09wx.17` holds the
   regrade.
2. **Before the change, nobody ran `bd recall`**: no call in 8 working sessions or in 310 delivery
   segments over a month. Half of those sessions did search with `bd memories`. Recall was not a
   weak habit to strengthen; the index has to create it.
3. **The session is the wrong unit for this project.** One month produced 14 sessions with a beads
   delivery, so 20 index-arm sessions is months away. The regrade should register the delivery
   segment as its unit, with the session as the cluster.
4. The only index-arm evidence from real work is one long-running session that ran `bd recall`
   in 2 of its 13 index segments, three calls on one key. That is an anecdote in the expected
   direction.

## Confidence

**High** that `bd recall` was unused before the change, within this project. **None** for the
effect of the index: there is no index arm. This is one project and one owner, and nearly every
session was driven by the same person.
