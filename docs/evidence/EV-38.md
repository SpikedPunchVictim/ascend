# EV-38: can a build and a writer run at once, and does the index stay honest if they do?

**Status**        Measured 2026-09-30 for `asc-tyl7` **(P1)**. The question was named in advance by the
                  bead, which also named the experiment — *"two processes, one building while one
                  writes, asserting the index is either current-and-complete or refused"* — and the
                  three candidate fix shapes. **No prediction was pre-registered**, which is the
                  limitation this record is least able to talk its way out of: the bead named the
                  question and the method, not the answer. n = 1 corpus, and it is this repository's
                  own `.ascend/` tree. **The headline is that the invariant the bead asked about does
                  NOT hold: ~4% of races publish an index that reports current while silently missing
                  the writer's record, and that omission is permanent.**

**Question**      `asc-tyl7`: `buildIndex` publishes by `renameSync` and takes no lock on the index it
                  replaces, while the write path *builds before writing* (EV-35, `asc-i5tj.4.1/b3`),
                  which puts a build on the write path for the first time. Can a build and a writer
                  overlap, and if they do, is the resulting index either current-and-complete or
                  refused — the invariant the bead states?

**Where it came from**  Verifying `asc-i5tj.6` and fixing `asc-pwv7` in the same subsystem, which
                  made the question of what else can go wrong between a build and a writer cheap to
                  ask. Nobody was looking for this; the bead predicted the experiment, and the
                  experiment found a defect shape the bead's own description does not have.

## Method

Two real processes against a **copy** of this repository's own `.ascend/` tree (10,463 lines, 22
record files); the real tree was never touched.

- **The writer** is a separate `node` process calling the real `writeLines` — the write path the
  bead's scenario names — appending **one** valid entry line to `entries/note-…/0001.jsonl` at a
  chosen moment. It spins on the clock, so the moment is the moment.
- **The build** is the real `buildIndex`, called in the parent at a known instant.
- Each trial gets a **fresh copy** of the tree carrying an index already built for it, so it starts
  current — the state a project is in after any previous build.
- Classification reads the published `index.db` itself: `meta.index_fingerprint` off the file, the
  writer's `id` counted in `entries`, and `treeFingerprint(root)` recomputed after everything has
  settled. `stored !== tree` is **stale**; `stored === tree` with the record absent is
  **FALSE-GREEN**.
- Timing is the independent variable, and it is measured rather than assumed: each trial reports the
  append's actual offset from the build's start.

## Measurement 1 — the two traversals a build makes (n = 5, p50)

```
lines: 10463
readRecordTree  min 126.3  p50 134.6  max 144.8
treeFingerprint min 5.5    p50 6.1    max 6.2
buildIndex      min 3052.6 p50 3161.8 max 3849.5
```

`buildIndex` reads the tree and then **re-reads the same files** to hash them. That second traversal
is the whole defect: the two describe different instants, and the build publishes them as one.

## Measurement 2 — where the window is, by delaying one append

One trial per offset, writer fires once. The outcome is bracketed by the trials either side of it.

| Append lands at (ms into a build) | Outcome | Trials |
|---|---|---|
| 19 | ok | 1 |
| **26 – 177** | **FALSE-GREEN** | **8 of 8** |
| 194 – 3310 | stale | 10 of 10 |

The window is `[when the build's first traversal finished the appended file, when its second
traversal read it]` — the note file is 4th of 22 in `recordFiles`' order, which is why the lower edge
sits near 20 ms and the window is as wide as ~165 ms.

## Measurement 3 — the rate when nobody is aiming (n = 24)

```
trials 24 {"stale":23,"FALSE-GREEN":1}
false-green offsets: 178
```

**4.2% false-green, 95.8% stale.** The window is 165 ms of a ~3.9 s build = **4.2%** — the
independent-variable sweep and the random run agree to a tenth of a percent, which is the only reason
either number is worth quoting.

## Measurement 4 — the false-green is permanent, and a read does not notice

On a false-green trial (`delay 60`, offset 75, build 4174 ms):

```
{"delay":60,"offset":75,"build":4174,"outcome":"FALSE-GREEN","writerSawStale":false,
 "stored":"726853d1126dc3dc","tree":"726853d1126dc3dc"}

after the raced build : missing record present = 0  (entries 6549)
  a read succeeds     : yes
after one later write : missing record present = 0  (the later one = 1, stale=false)
  index still current : yes
```

The published fingerprint equals the tree's, so `openIndex` **succeeds**. One further ordinary write —
which reports `stale=false`, inserts its own record, and leaves the index current — does **not**
repair the omission, because every write replays only its *own* lines. The record is absent until
somebody runs a full rebuild. This is the severity-zero shape: an instrument that reports current
while being short.

## Measurement 5 — the other branch degrades the safe way

```
s900   -> IndexStaleError: the index ... is not current for this tree
s2400  -> IndexStaleError: the index ... is not current for this tree
f60    -> READ SUCCEEDS (index claims current)
```

When the append lands outside the window the build's `renameSync` replaces `index.db` while the
writer holds the old inode, so the writer's replay is discarded. The index that remains is **stale**,
and a read refuses — a rebuild, not a wrong answer. **`writeLines` returned `stale: false` in this
branch too**, so the writer reported an index update it never made. That is a wrong *report* rather
than a wrong answer, and it is the second, smaller defect this measurement found.

## The mechanism, stated once

`buildIndex` does:

```
const lines = readRecordTree(root);        // traversal 1
const fingerprint = treeFingerprint(root); // traversal 2, of the same files
```

An append between them is **absent from `lines`** (what is replayed) and **present in `fingerprint`**
(what is stamped). The build then publishes a database certifying a tree it does not contain. The
window is not a race *between* the processes so much as a time-of-check/time-of-use gap *inside* the
build; the second process only makes it observable.

## The class this belongs to, and the member NOT measured

The shape is *a fingerprint taken in a second traversal from the data it certifies*, and it appears
three times. Two of them are **argued, not measured**, and are labelled so:

- **`buildIndex` — measured here.** Publishes a durable artifact that is wrong.
- **`openIndex` — argued, not measured.** Hashes the tree, then reads the stamp. A tree that moves
  between them makes one read answer from an index that was current a moment ago. That is a
  point-in-time answer rather than a published artifact, and a read is unavoidably *as of* a moment,
  so the author's judgement is that this is not the same defect. **This judgement is not measured**,
  and it is the weakest claim in this record.
- **`writeLines` — argued, not measured.** Fingerprints, *then* appends, so two concurrent writers can
  produce the same permanent omission: the second stamps the post-both tree while replaying only its
  own lines. This is a two-writer race, distinct from the bead's, and it is **not** covered by the
  fix this measurement justified.

## Limitations, plainly

- **n = 1 corpus.** One tree, one machine, one filesystem. The mechanism is a gap between two
  traversals, so its *existence* is structural, but the **window's width is this tree's** — 165 ms of
  a 3.9 s build. A smaller tree has a proportionally smaller absolute window; the ratio is not
  measured across sizes.
- **The writer is `writeLines`.** The six CLI write sites call `writeProducedLines`, which builds
  before taking its lock and re-checks inside it. That path is **reasoned about, not measured here**,
  and the reasoning says the orphan branch is reachable there too (its in-lock re-check reads the
  stamp through its own handle, which is the old inode).
- **4.2% is 1 of 24.** The random-timing rate is one trial. Its agreement with the 165/3900 window is
  the support for that number, not the trial count, and the true rate under a busy writer that
  appends repeatedly is **not measured** — it should be higher, since more appends mean more chances
  to land in the window.
- **No false-green was produced by an unmodified `asc index build` invocation.** Every trial called
  `buildIndex` in-process and the writer through the store API. The CLI adds argument parsing and a
  process launch, which move the timing but not the mechanism.
- The stale branch's *cost* is not measured: how often a user would meet it, or how long they would
  spend on "run `asc index build`" before it worked.

## What follows from it

The owner took the fix shape from the options this measurement justified: **one traversal**, so a
build's fingerprint describes exactly the lines it replays (removing the window by construction
rather than by a lock), plus **the writer reporting honestly** when its replay went to a replaced
inode. The two shapes this measurement *rejected*, with the evidence: a lock file (closes both
branches, but a build would block every `asc record` for its whole duration — ~75 s at 63,870
entries, EV-32), and building under `BEGIN IMMEDIATE` with no rename (no orphan possible, but atomic
publish is lost and the write lock is held for the whole build).

**Built 2026-09-30, in the working tree** (`asc-tyl7`, E12.7 Stages 1–3). `buildIndex` now reads the
tree and fingerprints it in one traversal (`readRecordTreeAndFingerprint`, the per-file fold
single-sourced so the two cannot drift), with the fingerprint's **value unchanged** — verified on this
repo's own tree, where the old formula and the new code both give `1ba57791e9469e44…`, so no existing
index is invalidated. `indexAtPathCarries` then asks the stamp **by path** after a writer closes its
handle: `writeProducedLines` refuses, `writeLines` reports `stale: true`. Two things building it
established that this record did not, both now in the plan and in the code:

- **The orphan needs the sidecars removed first.** A bare `renameSync` over `index.db` does *not*
  discard the write — its `-wal` stays at the path and is recovered onto whatever sits there, which is
  `dogfood/0044`'s mechanism seen from the other side — so a stamp comparison cannot see it, and a
  `-wal`-preserving rename is the case the by-path check does **not** cover. It is the same mechanism
  `dogfood/0044` records, which is why no fifth dogfood record was written for it.
- **The `writeLines` member is reachable, and the interleaving is now written out** rather than
  asserted: `replayInto` (`jsonl-index.ts:690-702`) stamps in the same transaction as the replay, so
  the stamp left behind is the last replayer's. Still **not measured** — no two-process trial was run
  for it — and left unfixed, because `writeLines` has no caller outside tests and the real path's
  version of that race produces a build, which the one-traversal fix closes.
