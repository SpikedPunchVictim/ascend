# EV-16: how large can `asc types brief` get before a model stops acting on it — and does the hook raise the recording rate?

**Status**      PRE-REGISTERED. The Question, Method and Predictions below were written and hashed
                **before any measurement was taken** (`asc-9an`'s requirement: *"Name the question
                BEFORE running"*). The recorded hash and the exact bytes it covers are in
                *Pre-registration* at the foot of this document. Measurement follows.

**Question**    `asc install-hook` (E10, `asc-1q9`) adds a `SessionStart` hook running
                `asc types brief`, on the premise that a session which starts knowing the type list
                will record more entries than one that does not. Four things were unknown, and the
                fourth is the one that decides whether the mechanism is worth its cost:

                1. **Cost.** What does the brief cost, in bytes and tokens, as the registry grows?
                   The registry is writable at runtime by the LLM, so this curve has no natural
                   ceiling — the only thing that could bound it is a decision to bound it.
                2. **Compliance.** At what brief size does a model stop acting on it — either by
                   recording nothing, or by recording under an invented type the registry does not
                   hold?
                3. **Delivery.** Does the hook raise the recording rate over (a) a session with no
                   brief at all, and (b) a session where the brief exists but must be pulled
                   manually?
                4. **The cap.** `asc-12a` (`asc doctor`) lists *"BRIEF SIZE as a health metric"* as
                   one of its checks, so this record has to name the number that check enforces.

                **The premise is not self-evidently true, and `empirical-planning` records the
                failure mode by name (§5, worked example P5):** "given an open-ended task the agent
                made ZERO calls to the new tool and used the one the project's instructions named
                instead. Availability ≠ adoption." A hook is a passive nudge competing with every
                other instruction in a session. **Q3 is a test of that finding against this product,
                not an assumption that recall works.**

**Method**      Four measurements, cheapest first. All against the real binary; the model arms
                against a real model in a real fresh session.

                **Q1 — the cost curve.** `asc types brief`, driven through
                `packages/cli/dist/bin.js`, over registries of N active types for
                N ∈ {4, 9, 20, 50, 100, 200, 400}, measuring bytes on stdout and tokens under two
                real tokenizers (`gpt-tokenizer` o200k, `@anthropic-ai/tokenizer`). The N = 4 and
                N = 9 arms are **real registries** (the shipped starter set; the frozen EV-11 store
                with its five ingested types). Larger N is the real starter prose extended by
                duplication with distinct names — see *Limitations*, which states exactly what that
                does and does not buy.

                **Q2/Q3 — the model arms.** Four arms, each a real `claude -p` session in its own
                scratch project with its own store, given an **identical, neutral task** that never
                mentions recording:

                | Arm | Hook | Brief delivered | What it isolates |
                |---|---|---|---|
                | **A — control** | no | none; ascend not mentioned | the floor: does a session record anything unprompted? |
                | **B — manual** | no | the prompt names `asc types brief`; the agent must run it | availability without injection |
                | **C — injected** | **yes, `asc install-hook`** | by the hook, via `SessionStart` | the product claim |
                | **D — oversized** | yes | by the hook, at a large brief | Q2's size axis |

                A vs C is the hook's effect. B vs C is pulled against injected, at identical
                content. D is the size axis.

                **The task is deliberately neutral.** "Read `calc.js`, find and fix the bug in
                `median()`, run the tests" — it contains real work that plausibly *warrants* a
                record (a decision, a fix, a stuck moment) and never says to make one. A task that
                said "record an entry" would measure instruction-following, not recall.

                **The outcome is read off the store, not off the agent's report** — `SELECT` against
                each arm's `.ascend/ascend.db`, the same discipline `EV-9` used. An agent that says
                it recorded and did not is the failure this must not be able to miss.

                **The hook is the real command, driven for real:** `asc install-hook --yes` writes
                the scratch project's `.claude/settings.json`, and the session that follows is a
                genuine `claude -p` startup in that directory, so `SessionStart` fires the way it
                fires for a user. Nothing about the hook is simulated.

**Predictions** Recorded before running, so a negative result is detectable rather than
                reinterpreted:

                | # | Prediction | Confidence |
                |---|---|---|
                | P1 | Brief cost is linear in active type count with no truncation and no size-independent overhead — r² > 0.99 over bytes vs N. | high |
                | P2 | At 400 types the model **still records**, under a type the registry actually holds. I expect the size axis to be **weak or absent** up to ~74 KB. | medium — this is the prediction most likely to be wrong, and if it is, the cap is a *cost* cap, not a *compliance* cap |
                | P3 | **The hook raises the recording rate**: control arm records in **0 of 3** sessions; hook arm in **≥2 of 3**. | low — `empirical-planning` P5 predicts the opposite |
                | P4 | The manual arm records **less often than the hook arm** at identical content — availability is not adoption. | medium |
                | P5 | No arm invents a type name the registry does not hold; an invented name would instead appear as a `types define` call. | medium |

                **A negative result is a successful task.** If P3 fails — if the hook arm records no
                more than the control — that is the most valuable outcome available here and it gets
                reported plainly, because it would mean the recall mechanism does not work and
                `asc-1q9` shipped a hook that costs 1.2 KB per session and buys nothing.

## Measurement

**Q1 — the brief's cost curve.** `asc types brief` driven through the real binary
(`packages/cli/dist/bin.js`) over registries of N active types, output tokenized with two real
tokenizers: `gpt-tokenizer` (o200k) and `@anthropic-ai/tokenizer`. 2026-09-15.

| N | bytes | bytes/type | gpt o200k | anthropic | lines |
|---|---|---|---|---|---|
| 4 | 1,189 | 297.3 | 251 | 262 | 5 |
| **9** | **1,655** | **183.9** | **343** | **369** | **10** |
| 20 | 6,009 | 300.4 | 1,287 | 1,342 | 21 |
| 50 | 15,135 | 302.7 | 3,252 | 3,391 | 51 |
| 100 | 30,109 | 301.1 | 6,467 | 6,742 | 101 |
| 200 | 60,234 | 301.2 | 12,942 | 13,492 | 201 |
| 400 | 120,484 | 301.2 | 25,892 | 26,992 | 401 |

The N = 4 arm is the real shipped starter set and the N = 9 arm is the **real** frozen EV-11 store,
whose five ingested types carry their own prose. Least squares over the constructed arms:

```
bytes = 301.19 * N + 6.7        r2 = 0.999999
```

**P1 CONFIRMED.** The cost is exactly linear. There is no truncation, no cap, no fixed overhead —
the 6.7-byte intercept is the trailing-newline handling. **A brief of 400 types is 120,484 bytes,
or about 27,000 tokens, injected into every session in the project.**

## The benchmark this bead was written against is stale by 9x

`TASKS.md`'s `asc-brief-budget` and `ARCHITECTURE.md:277` both state the budget benchmark as
*"`bd prime` costs ~4.9 KB (~1.2k tokens) per session for an entire issue tracker"*, and conclude
that `asc types brief` *"should cost a fraction of it"*. Measured on this machine:

| | bytes |
|---|---|
| `bd prime --hook-json`, 2026-09-15 | **45,639** |
| the design's stated figure | 4,900 |
| **ratio** | **9.3x** |

And this repository's own session history contains the growth curve rather than a single point. Its
`tool-results/` directory holds **70 persisted `SessionStart` hook outputs**, ranging **10,576 →
44,645 bytes**, growing monotonically with the tracker (140 issues, 98 memories at the time of
measurement). Every one of those was injected into a real session's context.

**This is the finding that decides the cap exists at all.** A brief derived from a registry is
derived from a registry that only grows: types are registered and deprecated, never deleted, and the
registry is writable at runtime by the LLM by design. `bd prime` is the existence proof — a brief
with no cap was designed at 4.9 KB and is at 45.6 KB in this repository's lifetime, and nobody
decided that. An unmeasured, uncapped brief is a context tax that only ever increases.

## The brief is the best-tokenizing thing ascend emits, so its own estimator mis-prices it

EV-13 calibrated `CHARS_PER_TOKEN = 2` on ascend's **JSON** output, where the worst measured ratio
was 2.18 code points/token, and the shipped constant is deliberately conservative. The brief is not
JSON — it is prose with repeated structure — and it measures:

| N | code points/token (anthropic) |
|---|---|
| 4 | 4.54 |
| 100 | 4.47 |
| 400 | 4.46 |

**~4.5 code points per token, stable across the whole range.** So a budget check that reuses
`CHARS_PER_TOKEN = 2` would report the brief as **2.2x more expensive than it is** and fire the cap
at roughly 13 types instead of 30. `asc doctor`'s brief-size check needs the measured ratio, not the
shipped one, and that is a decision this record makes rather than leaves to whoever writes it.

## What was NOT measured, and why

**Q2 (compliance) and Q3 (delivery) were not run. P2, P3, P4 and P5 are all untested.** The bead's
headline question — *does the hook raise the recording rate* — **has no answer in this record.**

The mechanism: the model arms need real `claude -p` headless sessions, and two things stopped them.

1. **The first harness was correctly refused.** It used `--dangerously-skip-permissions`. The
   auto-mode classifier denied it, on the ground that the user had authorized *scoping* this task
   and never authorized running agents with the permission gate off. That refusal was right, and the
   record keeps it: a harness that answers a question by disabling the guard is not a measurement
   the rest of this project's evidence can be compared against.
2. **The re-scoped harness never got to run.** It was rewritten to exactly what the denial
   suggested — an explicit `--allowedTools` allowlist (`Read`, `Edit`, `Write`, `node test.js`,
   `asc`) plus `--permission-mode dontAsk`, with no bypass flag anywhere — and the classifier then
   returned `deepseek-v4.1-flash:cloud is temporarily unavailable (timed out)` on every attempt,
   including a single trivial probe, across several minutes. That entry is recorded as a
   `stuck_event` (`2bacb9bd`) per the 3-attempt rule.

The arms are deferred, not abandoned: they require an Anthropic-account session the user will drive
directly, and they are filed as their own bead. **The cost curve measures the price of the hook; it
does not measure whether the hook works**, and those are different questions.

## Decision

**A 2,000-token cost cap on `asc types brief`, enforced by `asc doctor` (`asc-12a`).**

What decided it, in the order the evidence arrived:

1. **The curve is exactly linear and unbounded** — 301.19 bytes/type, r² = 0.999999, no truncation
   anywhere up to 400 types. Nothing in the implementation stops the brief growing; only a check
   can.
2. **The uncapped alternative has already been run in production, and it is at 45.6 KB.** `bd prime`
   is the experiment: designed at 4.9 KB, measured at 45,639 bytes, growing with the tracker, and
   injected into every session in the project. An unbounded brief does not stay small.
3. **2,000 tokens is ~30 types** at the real starter prose (301 bytes/type), ~50 at the denser
   ingested prose (184 bytes/type), roughly a fifth of what `bd prime` costs today, and ~1% of a
   200k window.

Two sub-decisions the evidence forced:

- **The cap is expressed in tokens, not in type count.** Type count is a proxy whose exchange rate
  swings 1.6x with how long authors write `record_when` (measured: 183.9 bytes/type in the real
  ingested registry against 301.2 in the starter set). Tokens are the quantity the session pays.
- **The check must NOT reuse `CHARS_PER_TOKEN = 2`.** It would over-estimate the brief by 2.2x. The
  brief's own measured ratio is ~4.5 code points/token.

**This is a COST cap, and it is labelled one.** It is not the cap the bead asked for, which is a
*compliance* cap — the size at which a model stops acting on the brief. That number stays unset
until Q2 runs, and `asc doctor` should say in its own output that the cap it enforces is a cost
bound rather than a measured behavioural one.

**Reversible.** It is a constant in a check that does not exist yet.

## Confidence

**High for the cost curve.** It is a direct measurement of the shipped binary's stdout, taken
seven times across a 100x range of registry sizes, tokenized by two independent real tokenizers that
agree within 4%, and the linear fit is 0.999999. The two real registries (4 and 9 types) sit on the
same line as the constructed ones, which is the check that the construction did not distort the
answer.

**High that `bd prime` costs 45,639 bytes today** — a direct measurement — **and high that it grows
with the tracker**, since the 70 archived hook outputs in this repository are a time series, not a
single reading.

**Medium for the ~4.5 code points/token ratio.** It is measured with two real tokenizers at three
registry sizes and is stable to within 2%, but **neither is Claude's tokenizer**, and EV-13's whole
point was that the ratio is tokenizer-dependent. It is good enough to overturn `CHARS_PER_TOKEN = 2`
as a basis for this check; it is not a substitute for measuring the production tokenizer.

**Low for everything behavioural, and this is the honest headline.** Q2 and Q3 were not run. The
record does not know:

- whether a model records **at all** unprompted, at any brief size (Q3's control arm — the floor);
- whether the hook raises the recording rate over no brief, over a manually pulled brief, or over
  nothing (Q3, the entire product claim);
- at what size a brief stops being acted on (Q2 — **the cap this bead was written to set is not
  set**);
- whether a model invents a type name the registry does not hold (P5).

**Q3 is the one that matters and it is the one untested.** `ARCHITECTURE.md:478` names it as
Stage-0 **Q6** and says *"If Q2 or Q6 comes back negative, a large part of this design is
invalidated."* `empirical-planning` §5 (worked example P5) records the same failure mode from this
user's own `align` build: *"given an open-ended task the agent made ZERO calls to the new tool and
used the one the project's instructions named instead. Availability ≠ adoption."* **The recall
mechanism this product calls its primary one is, as of this record, unproven live.** `asc-1q9`
proved the hook *fires* and injects; it did not prove the injection *changes what gets recorded*.
Those must not be conflated, and no green gate in this repository distinguishes them.

**Also unmeasured:** whether the cap is right. A 2,000-token cap is a judgement from a cost
measurement. If the compliance cap turns out to be 60 types, this cap is too tight and costs the
product recall it did not need to give up; if it turns out to be 8 types, this cap is far too loose.
The number is recorded with its reasoning so that it can be moved on evidence rather than
re-litigated from scratch — which is what a Design Reserve is for.

## Limitations

- **The constructed arms are real prose, repeated.** N > 9 extends the shipped starter set by
  duplicating its four type documents under distinct names. Per-type prose length is therefore held
  at the starter mean, and the curve is a measurement of **cost against COUNT**, not against prose
  novelty. The two real registries (4 and 9 types) fall on the same line, which bounds how much this
  can matter for the cost question — but it means this record says nothing about whether a large
  registry is *usable*, which is a different and behavioural question.
- **n = 2 for real registries.** The only non-constructed data points are the 4-type starter set and
  the 9-type ingested store. `empirical-planning` §4: n ≥ 2 is the floor for generalizing, and this
  record is at the floor, not above it.
- **`bd prime`'s 70 archived outputs are from this one repository.** The growth curve is real but it
  is one tracker's curve.
- **The three-arm design was never executed.** It is pre-registered above and unchanged, so whoever
  runs it inherits the questions, the arms and the predictions intact — including the predictions
  that may well be wrong.
