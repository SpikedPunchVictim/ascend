# EV-16: how large can `asc types brief` get before a model stops acting on it — and does the hook raise the recording rate?

**Status**      PRE-REGISTERED. The Question, Method and Predictions below were written and hashed
                **before any measurement was taken** (`asc-9an`'s requirement: *"Name the question
                BEFORE running"*). The recorded hash and the exact bytes it covers are in
                *Pre-registration* at the foot of this document. Measurement follows.

**Question**    `asc install-hook` (E10, `asc-1q9`) adds a `SessionStart` hook running
                `asc types brief`, on the premise that a session which starts knowing the type list
                will record more entries than one that does not. Four things were unknown, and the
                fourth is the one that decides whether the mechanism is worth its cost:

                1. **Cost.** What does the brief cost, in bytes and tokens, as the registry grows?
                   The registry is writable at runtime by the LLM, so this curve has no natural
                   ceiling — the only thing that could bound it is a decision to bound it.
                2. **Compliance.** At what brief size does a model stop acting on it — either by
                   recording nothing, or by recording under an invented type the registry does not
                   hold?
                3. **Delivery.** Does the hook raise the recording rate over (a) a session with no
                   brief at all, and (b) a session where the brief exists but must be pulled
                   manually?
                4. **The cap.** `asc-12a` (`asc doctor`) lists *"BRIEF SIZE as a health metric"* as
                   one of its checks, so this record has to name the number that check enforces.

                **The premise is not self-evidently true, and `empirical-planning` records the
                failure mode by name (§5, worked example P5):** "given an open-ended task the agent
                made ZERO calls to the new tool and used the one the project's instructions named
                instead. Availability ≠ adoption." A hook is a passive nudge competing with every
                other instruction in a session. **Q3 is a test of that finding against this product,
                not an assumption that recall works.**

**Method**      Four measurements, cheapest first. All against the real binary; the model arms
                against a real model in a real fresh session.

                **Q1 — the cost curve.** `asc types brief`, driven through
                `packages/cli/dist/bin.js`, over registries of N active types for
                N ∈ {4, 9, 20, 50, 100, 200, 400}, measuring bytes on stdout and tokens under two
                real tokenizers (`gpt-tokenizer` o200k, `@anthropic-ai/tokenizer`). The N = 4 and
                N = 9 arms are **real registries** (the shipped starter set; the frozen EV-11 store
                with its five ingested types). Larger N is the real starter prose extended by
                duplication with distinct names — see *Limitations*, which states exactly what that
                does and does not buy.

                **Q2/Q3 — the model arms.** Four arms, each a real `claude -p` session in its own
                scratch project with its own store, given an **identical, neutral task** that never
                mentions recording:

                | Arm | Hook | Brief delivered | What it isolates |
                |---|---|---|---|
                | **A — control** | no | none; ascend not mentioned | the floor: does a session record anything unprompted? |
                | **B — manual** | no | the prompt names `asc types brief`; the agent must run it | availability without injection |
                | **C — injected** | **yes, `asc install-hook`** | by the hook, via `SessionStart` | the product claim |
                | **D — oversized** | yes | by the hook, at a large brief | Q2's size axis |

                A vs C is the hook's effect. B vs C is pulled against injected, at identical
                content. D is the size axis.

                **The task is deliberately neutral.** "Read `calc.js`, find and fix the bug in
                `median()`, run the tests" — it contains real work that plausibly *warrants* a
                record (a decision, a fix, a stuck moment) and never says to make one. A task that
                said "record an entry" would measure instruction-following, not recall.

                **The outcome is read off the store, not off the agent's report** — `SELECT` against
                each arm's `.ascend/ascend.db`, the same discipline `EV-9` used. An agent that says
                it recorded and did not is the failure this must not be able to miss.

                **The hook is the real command, driven for real:** `asc install-hook --yes` writes
                the scratch project's `.claude/settings.json`, and the session that follows is a
                genuine `claude -p` startup in that directory, so `SessionStart` fires the way it
                fires for a user. Nothing about the hook is simulated.

**Predictions** Recorded before running, so a negative result is detectable rather than
                reinterpreted:

                | # | Prediction | Confidence |
                |---|---|---|
                | P1 | Brief cost is linear in active type count with no truncation and no size-independent overhead — r² > 0.99 over bytes vs N. | high |
                | P2 | At 400 types the model **still records**, under a type the registry actually holds. I expect the size axis to be **weak or absent** up to ~74 KB. | medium — this is the prediction most likely to be wrong, and if it is, the cap is a *cost* cap, not a *compliance* cap |
                | P3 | **The hook raises the recording rate**: control arm records in **0 of 3** sessions; hook arm in **≥2 of 3**. | low — `empirical-planning` P5 predicts the opposite |
                | P4 | The manual arm records **less often than the hook arm** at identical content — availability is not adoption. | medium |
                | P5 | No arm invents a type name the registry does not hold; an invented name would instead appear as a `types define` call. | medium |

                **A negative result is a successful task.** If P3 fails — if the hook arm records no
                more than the control — that is the most valuable outcome available here and it gets
                reported plainly, because it would mean the recall mechanism does not work and
                `asc-1q9` shipped a hook that costs 1.2 KB per session and buys nothing.

## The benchmark this bead was written against is stale by 9x

`TASKS.md`'s `asc-brief-budget` and `ARCHITECTURE.md:277` both state the budget benchmark as
*"`bd prime` costs ~4.9 KB (~1.2k tokens) per session for an entire issue tracker"*, and conclude
that `asc types brief` *"should cost a fraction of it"*. Measured on this machine:

| | bytes |
|---|---|
| `bd prime --hook-json`, 2026-09-15 | **45,639** |
| the design's stated figure | 4,900 |
| **ratio** | **9.3x** |

And this repository's own session history contains the growth curve rather than a single point. Its
`tool-results/` directory holds **70 persisted `SessionStart` hook outputs**, ranging **10,576 →
44,645 bytes**, growing monotonically with the tracker (140 issues, 98 memories at the time of
measurement). Every one of those was injected into a real session's context.

**This is the finding that decides the cap exists at all.** A brief derived from a registry is
derived from a registry that only grows: types are registered and deprecated, never deleted, and the
registry is writable at runtime by the LLM by design. `bd prime` is the existence proof — a brief
with no cap was designed at 4.9 KB and is at 45.6 KB in this repository's lifetime, and nobody
decided that. An unmeasured, uncapped brief is a context tax that only ever increases.

## The brief is the best-tokenizing thing ascend emits, so its own estimator mis-prices it

EV-13 calibrated `CHARS_PER_TOKEN = 2` on ascend's **JSON** output, where the worst measured ratio
was 2.18 code points/token, and the shipped constant is deliberately conservative. The brief is not
JSON — it is prose with repeated structure — and it measures:

| N | code points/token (anthropic) |
|---|---|
| 4 | 4.54 |
| 100 | 4.47 |
| 400 | 4.46 |

**~4.5 code points per token, stable across the whole range.** So a budget check that reuses
`CHARS_PER_TOKEN = 2` would report the brief as **2.2x more expensive than it is** and fire the cap
at roughly 13 types instead of 30. `asc doctor`'s brief-size check needs the measured ratio, not the
shipped one, and that is a decision this record makes rather than leaves to whoever writes it.

## Why Q2 and Q3 sat unmeasured for six days, and what unblocked them

The bead's headline question — *does the hook raise the recording rate* — had no answer in this
record until 2026-09-21. Three things blocked it, and the first two are kept here because a record
of what a measurement cost is part of the measurement.

1. **The first harness was correctly refused.** It used `--dangerously-skip-permissions`. The
   auto-mode classifier denied it, on the ground that the user had authorized *scoping* this task
   and never authorized running agents with the permission gate off. That refusal was right, and the
   record keeps it: a harness that answers a question by disabling the guard is not a measurement
   the rest of this project's evidence can be compared against.
2. **The re-scoped harness met a classifier outage.** Rewritten to exactly what the denial
   suggested — an explicit `--allowedTools` allowlist plus `--permission-mode dontAsk`, no bypass
   flag anywhere — it then drew `deepseek-v4.1-flash:cloud is temporarily unavailable (timed out)`
   on every attempt including a trivial probe. Recorded as `stuck_event` `2bacb9bd` per the
   three-attempt rule.
3. **The record believed no Anthropic account was reachable here.** Read from
   `~/.claude/settings.json`: empty `env`, no `apiKeyHelper`, `default_model: kimi` pointing at
   Ollama Cloud with a literal placeholder key. That reading was correct about the `kimi` route and
   wrong about the effective one. The same file also sets `model: fable[1m]`, which takes
   precedence. Two bounded probes both billed `claude-fable-5-1` and `claude-haiku-4-5` with
   `provider: "firstParty"`, and the 1,000,000-token context window reported for `fable-5-1`
   corroborates the `[1m]` suffix rather than coinciding with it (`evidence_record` `4bbbdbdd`).

**The generalizable part: the configuration file said one thing and the run said another, and only
the run is evidence.** `modelUsage` on the result envelope names what was actually billed, and that
is the field to read whenever a question turns on which model answered.

The arms below therefore pin `--model` explicitly rather than inheriting whatever `model:` says on
the day. A rate with no model beside it is not a finding.

## Q3 — the hook does not raise the recording rate

Five arms, three sessions each, `claude-haiku-4-5-20251001`, every session in its own `mkdtemp`
project with its own store and `asc` shimmed onto `PATH` to exec the built binary. The task is
byte-identical across all five and never mentions recording: *"Read calc.js, find and fix the bug in
median(), then run the tests."* The outcome is read off the store by SQL after the session ends,
never off the agent's report — EV-9's discipline.

| arm | condition | brief delivered | recorded | `asc` calls | tests |
|---|---|---|---|---|---|
| A | control, no hook | none | **0 of 3** | 0 | 3 of 3 passing |
| B | prompt names `asc types brief` | none | **0 of 3** | 0 | 3 of 3 passing |
| C | hook, 1,353 bytes | in full, verified | **0 of 3** | 0 | 2 of 3 passing¹ |
| D | hook, 121,753 bytes | **truncated** | **0 of 3** | 0 | 3 of 3 passing |
| E | hook emits a pointer to a file² | read by 1 of 3 | **0 of 3** | 0 | 3 of 3 passing |

¹ Arm C rep 1 fixed both `median()` defects correctly, then reached for `Bash(npm test)` — outside
the grant and write-class — was denied twice, and reported success without running the tests. Its
recording outcome is unaffected; it ended without recording like the rest.

² Arm E is **not pre-registered**. It was proposed after the fact, as a fix for the truncation
defect found in arm D, and is marked as an extension in the harness source so it can never be read
as part of the sealed design.

**P3 FAILS.** It predicted the control records in 0 of 3 and the hook arm in **≥2 of 3**. The
control half is confirmed exactly. The hook half is refuted: 0 of 3, with the brief verified
delivered in full.

The pre-registration named this outcome in advance and said what it would mean:

> **A negative result is a successful task.** If P3 fails — if the hook arm records no more than the
> control — that is the most valuable outcome available here and it gets reported plainly, because
> it would mean the recall mechanism does not work and `asc-1q9` shipped a hook that costs 1.2 KB
> per session and buys nothing.

That is the finding. The measured cost in this configuration is 1,353 bytes per session.

**The stronger form is what the tool calls show: across all 15 sessions, not one invoked `asc` in
any form.** This is not a model that considered recording and declined, nor one that recorded under
the wrong type. Five different availability conditions — absent, named in the prompt, injected by
hook, injected oversized, and actively read from a file — produced the same zero.

**P4 is confirmed on its own side and cannot fail on it.** It predicted the manual arm records less
often than the hook arm; arm B is at the floor, so it can only tie. The sharper reading is that
naming `asc types brief` in the prompt did not even produce curiosity: no arm B session ran it.

**P5 holds trivially.** No arm invented a type name, because no arm named a type at all.

## The brief never reached the model in arm D, and the check that said it had

Arm D was expected to be a formality. It cost **$0.1430** against arm C's **$0.1398** — for a brief
90× larger. A 121,753-byte brief is roughly 30,000 tokens, and 30,000 tokens cannot enter a context
for free. Cache-creation totals per session:

| arm | brief | cache-creation tokens, summed per session |
|---|---|---|
| A | none | 42,939 / 50,802 / 40,358 |
| C | 1,353 bytes | 51,576 / 52,741 / 43,146 |
| D | 121,753 bytes | 52,561 / 43,199 / 44,954 |

Arm D is indistinguishable from the control that has no hook at all.

**The check that had certified the brief was present would have returned the same answer in the case
where the model received almost none of it.** Arms C and D were read as "the hook fired" because the
brief's prose appears in the session stream. It does — inside a
`{"type":"system","subtype":"hook_response"}` event, which is the CLI reporting what the hook
*printed*. Presence there proves the hook ran and says nothing about whether its output reached the
model, which was the claim resting on it.

`spike/ev16-brief-canary.mjs` replaces that check with evidence a stream match cannot fake. A type
whose **name is a nonce** is registered **last**, so a truncated brief loses it first; `Bash` is
withheld so the answer cannot come from running `asc types brief`; and the verdict is read **only
from assistant text blocks**, because the nonce appears in the `hook_response` event either way.

A first canary run returned a false negative against a loosely worded prompt — *"answer from what
you already know"*, which the model read as a question about conversation history. Re-run with *"At
the start of this session, were you given a list of entry types?"* it returned true. The prompt was
the instrument, and the first phrasing was a defect in it.

## Q2 — the brief stops working because it stops being delivered

Q2 asked at what size a model stops acting on the brief. The answer is that below roughly 10 KB it
acts on it and records nothing anyway, and above roughly 10 KB it never receives it. One session per
row, nonce registered last, `briefReachedContext` true means the nonce was recovered verbatim:

| filler types | brief bytes | delivered |
|---|---|---|
| 0 | 1,465 | yes |
| 4 | 2,669 | yes |
| 15 | 5,980 | yes |
| 22 | 8,087 | yes |
| 25 | 8,990 | **yes** |
| 30 | 10,495 | **no** |
| 100 | 31,565 | no |
| 400 | 121,865 | no |

Three different byte counts appear in this record for "400 types" and they are three different
briefs, not a discrepancy: **120,484** is Q1's pure constructed registry, **121,753** is arm D's
(the starter set plus filler), and **121,865** is the canary's (filler plus the nonce type
registered last). Each is the measured stdout of the brief that run actually used.

**The delivery ceiling is between 8,990 and 10,495 bytes** — a factor of 1.17. 8 KiB was tested and
excluded. No round figure is quoted: 10,000 and 10,240 were not separated, so neither is written
down as though they had been.

Each truncated session reported the truncation in its own words — *"the full output was too large to
display completely"*, *"The preview is truncated"* — and each named the same ~2 KB of types. That is
what distinguishes a truncation from a model abbreviating a long list, and it is why `false` at
10,495 bytes is a measurement rather than an artifact of how much a model felt like typing.

**The host already implements a fallback, and it was not taken.** The 121,865-byte session said,
verbatim:

> I can see from the startup hook output preview that there are entry types, but I can only see the
> beginning of the list… The full output is 119KB and was saved to a file, but the preview only
> shows the first ~2KB.

So oversized hook output is not discarded: it is persisted to a file, and the model is told both
that the file exists and that what it is reading is a preview. That is the pointer design, supplied
by the host, for free — and the session did not open the file. It is the same 2-of-4 behaviour arm E
measured, observed independently and before arm E was designed. **A pointer the model is given is
not a pointer the model follows**, whoever supplies it.

**This is not a usage error.** `docs/en/hooks#sessionstart` documents both channels:

> Your hook can return `additionalContext` as a string. […] Exit 0 with plain-text stdout also
> works; Claude Code treats stdout as context Claude can see. On events like this where plain text
> is context, the two channels are equivalent, so use whichever is clearer in your script.

Tested at 121,865 bytes, the equivalence extends to truncation — both lose the brief and the model
names the same six types:

| channel | reached the model | cache-creation | cost USD |
|---|---|---|---|
| plain stdout | no | 21,796 | 0.0269 |
| `hookSpecificOutput.additionalContext` | no | 21,796 | 0.0269 |
| pointer to a file | **yes** | 94,236 | 0.1088 |

**The ceiling is undocumented.** The docs state no size limit for either channel, so a hook author
has nothing to design against, and the failure is silent at every layer that could catch it: the
hook exits 0, `asc types brief` prints everything, and the stream's `hook_response` event carries
the full text even when the model received about 2 KB of it. Filed as `asc-3q7`.

**ascend's own brief is 3,476 bytes today** (`asc types brief | wc -c`, this repository). At the
301.19 bytes/type measured in Q1, roughly twenty more registered types cross the ceiling in silence.

## Arm E — reading the brief rather than merely having it

The pointer design keeps the hook's output tiny and spends it on an instruction naming a file that
holds the full brief. It fixes the ceiling completely: at 121,865 bytes the nonce registered last
was recovered verbatim, and nothing large crosses the truncating channel at any registry size. The
tokens are not saved but moved and made honest — 94,236 cache-creation against 21,796, about 4×,
paid on demand instead of silently lost.

What it does not do is change the recording rate.

| rep | read the brief file | files read | recorded |
|---|---|---|---|
| 1 | no | `calc.js` | 0 |
| 2 | **yes** | `brief.txt`, `calc.js`, `test.js` | 0 |
| 3 | no | `calc.js` | 0 |

**Rep 2 is the session that matters.** It read the entire brief on its own initiative, before
opening the file the task named, then did the work correctly and recorded nothing. Until that
session, every zero in this record had a kind explanation available: the brief was *present* but not
*attended to*, the way a system prompt is technically available. Rep 2 attended to it deliberately.
That explanation is gone.

**The pointer is not reliably followed: 2 of 4 sessions** on this task, counting one further session
run through the canary harness. An earlier reading of "follows it unprompted" rested on a single
session and was overstated.

## Decision

**A 2,000-token cost cap on `asc types brief`, enforced by `asc doctor` (`asc-12a`).**

What decided it, in the order the evidence arrived:

1. **The curve is exactly linear and unbounded** — 301.19 bytes/type, r² = 0.999999, no truncation
   anywhere up to 400 types. Nothing in the implementation stops the brief growing; only a check
   can.
2. **The uncapped alternative has already been run in production, and it is at 45.6 KB.** `bd prime`
   is the experiment: designed at 4.9 KB, measured at 45,639 bytes, growing with the tracker, and
   injected into every session in the project. An unbounded brief does not stay small.
3. **2,000 tokens is ~30 types** at the real starter prose (301 bytes/type), ~50 at the denser
   ingested prose (184 bytes/type), roughly a fifth of what `bd prime` costs today, and ~1% of a
   200k window.

Two sub-decisions the evidence forced:

- **The cap is expressed in tokens, not in type count.** Type count is a proxy whose exchange rate
  swings 1.6x with how long authors write `record_when` (measured: 183.9 bytes/type in the real
  ingested registry against 301.2 in the starter set). Tokens are the quantity the session pays.
- **The check must NOT reuse `CHARS_PER_TOKEN = 2`.** It would over-estimate the brief by 2.2x. The
  brief's own measured ratio is ~4.5 code points/token.

**This was labelled a COST cap, and Q2 has since given it a second, independent justification.**
The cap the bead asked for was a *compliance* cap — the size at which a model stops acting on the
brief. Q2 found there is no such size, because the failure happens a layer earlier: the brief stops
being **delivered** between 8,990 and 10,495 bytes. At the 4.5 code points/token measured above,
2,000 tokens is about 9,000 bytes, which falls inside that bracket. The cap chosen from cost
arithmetic lands on the delivery ceiling by arithmetic coincidence, and two unrelated arguments now
point at roughly the same number.

**Sub-decision added after Q2: the cap's justification changes, its value does not.** It should be
enforced as a *delivery* bound, not a cost bound, because exceeding it silently destroys the brief
rather than merely making it expensive. `asc doctor` should say so in its own output. The 2,000-token
figure is kept rather than re-derived from 8,990 bytes, because 8,990 is the last size measured to
work and not the threshold itself — quoting it as a limit would be quoting a bracket edge as a
measurement.

**The compliance cap remains unset, and Q2 says it may not exist.** No brief size produced a
recording in any arm, so there is no size at which compliance degrades — there is no compliance to
degrade. That is a finding about the mechanism, not a gap in this record.

**Reversible.** It is a constant in a check that does not exist yet.

## Decision added by Q3 — what the hook is for

**Do not ship the SessionStart brief as a recall mechanism, and do not remove it either.**

P3's failure is about *recall*: the brief does not cause a model to record. It says nothing about
the brief's other job, which is to make a model that has *already decided* to record pick the right
type and fill the right fields — the job `asc-1q9` actually verified. This record does not measure
that job, and conflating the two is exactly the error `asc-1q9` invited.

What follows for the product is that **recall needs a second mechanism, and EV-16 does not know what
it is.** The candidates this record can rule on:

- **A bigger brief: ruled out.** Arm D, and the ceiling that made it meaningless.
- **A more available brief: ruled out.** Arm E rep 2 read the whole thing voluntarily and recorded
  nothing.
- **Naming the tool in the prompt: ruled out.** Arm B, 0 of 3, with no session curious enough to run
  the command it was handed.
- **A prompt that asks for a recording: not tested, and now the obvious next arm.** Every arm here
  used a task that never mentions recording, which was deliberate — it measures unprompted recall.
  The result is that unprompted recall is zero, which makes *prompted* recall the first thing worth
  measuring next, and it is a different question from the one sealed above.

**Reversible.** Nothing ships or unships on this; it redirects where the next measurement goes.

## Confidence

**High for the cost curve.** It is a direct measurement of the shipped binary's stdout, taken
seven times across a 100x range of registry sizes, tokenized by two independent real tokenizers that
agree within 4%, and the linear fit is 0.999999. The two real registries (4 and 9 types) sit on the
same line as the constructed ones, which is the check that the construction did not distort the
answer.

**High that `bd prime` costs 45,639 bytes today** — a direct measurement — **and high that it grows
with the tracker**, since the 70 archived hook outputs in this repository are a time series, not a
single reading.

**Medium for the ~4.5 code points/token ratio.** It is measured with two real tokenizers at three
registry sizes and is stable to within 2%, but **neither is Claude's tokenizer**, and EV-13's whole
point was that the ratio is tokenizer-dependent. It is good enough to overturn `CHARS_PER_TOKEN = 2`
as a basis for this check; it is not a substitute for measuring the production tokenizer.

**High for the delivery ceiling's existence, medium for its exact bracket.** That a brief above
roughly 10 KB does not reach the model is established by eight sessions, by two channels failing
identically, by the pointer design succeeding on the same payload, and by the truncated sessions
reporting the truncation in their own words and naming the same ~2 KB of types. The bracket itself
is one session per point, so a per-point flake would move an edge; the 1.17x width is a statement
about how far the bisection was taken, not a confidence interval.

**Medium-high that the hook does not raise the recording rate, and the reason is not the sample
size.** Per arm, n = 3 — an anecdote against `MIN_N = 20` (`packages/analysis/src/proportion.ts:50`),
and it is named as one. What carries the weight is that five different availability conditions
produced the identical outcome, that the outcome is a floor (zero, not a low rate), and that the
strongest form is stronger than the prediction: no session invoked `asc` at all. Raising n cannot
turn 0 of 15 into a rate; it can only narrow an interval around zero.

Three things would still change the conclusion, and none is a sample-size question:

- **A different model.** Everything here is `claude-haiku-4-5-20251001`. A larger model may weigh an
  injected instruction differently, and this record cannot say.
- **A different task.** The task is a small, closed bug fix whose success criterion is a passing
  test. Nothing in it is surprising enough to be worth recording, so a model that correctly judged
  "nothing here meets `record_when`" would produce exactly this data. **This is the strongest
  competing explanation and it is not excluded.** Arm E rep 2 weakens it — that session read the
  full `record_when` prose and still recorded nothing — but weakening is not exclusion.
- **A prompt that asks for a recording.** Untested by design; see the decision above.

**Still unmeasured: whether a model invents a type name the registry does not hold.** P5 holds
trivially because no arm named a type at all, which is a pass with no information in it. The
question stays open and needs an arm where recording actually happens.

**What `asc-1q9` proved and what it did not, now separated by measurement rather than argument.**
`ARCHITECTURE.md:478` names this as Stage-0 **Q6**: *"If Q2 or Q6 comes back negative, a large part
of this design is invalidated."* `empirical-planning` §5 records the same failure mode from this
user's own `align` build: *"given an open-ended task the agent made ZERO calls to the new tool and
used the one the project's instructions named instead. Availability ≠ adoption."* That is now
reproduced here, on this product, under conditions including one where the agent read the tool's own
documentation first. `asc-1q9` proved the hook fires and injects. It did not prove the injection
changes what gets recorded, and the injection does not.

**Also unmeasured: whether the cap is right for the reason it was originally given.** Q2 replaced
the cost argument with a delivery argument that happens to land on the same number, which is
reassuring and is not confirmation — the two arguments share no evidence, but neither was derived
from a measurement of what a model can actually *use*, and that measurement no longer looks
obtainable, because nothing was used at any size.

## Limitations

- **The constructed arms are real prose, repeated.** N > 9 extends the shipped starter set by
  duplicating its four type documents under distinct names. Per-type prose length is therefore held
  at the starter mean, and the curve is a measurement of **cost against COUNT**, not against prose
  novelty. The two real registries (4 and 9 types) fall on the same line, which bounds how much this
  can matter for the cost question — but it means this record says nothing about whether a large
  registry is *usable*, which is a different and behavioural question.
- **n = 2 for real registries.** The only non-constructed data points are the 4-type starter set and
  the 9-type ingested store. `empirical-planning` §4: n ≥ 2 is the floor for generalizing, and this
  record is at the floor, not above it.
- **`bd prime`'s 70 archived outputs are from this one repository.** The growth curve is real but it
  is one tracker's curve.
- **n = 3 per arm, against `MIN_N = 20`.** Every per-arm rate in this record is an anecdote by this
  project's own threshold, and is named as one. The conclusion rests on five arms agreeing at a
  floor, not on any single arm's count.
- **One model, one task, one prose style.** `claude-haiku-4-5-20251001`, a closed bug fix with a
  test-based success criterion, and one hand-written brief. Each is a fixed factor, not a varied
  one.
- **The bisection is one session per point.** A single flaky point would move a bracket edge. The
  points either side of the boundary were not repeated.
- **Arm E is post-hoc.** It was designed after the truncation defect surfaced, is marked as an
  extension in the harness, and is reported separately from the sealed arms. It is evidence about
  the pointer design; it is not evidence produced under pre-registration.
- **The store is the outcome, but "did not record" is not "decided not to record."** The measurement
  reads entries out of SQLite, which is the right instrument for whether recording happened and a
  silent one about why. No arm produced reasoning about recording that could be read, because no arm
  mentioned it.


## Reproducing the model arms

`spike/ev16-arms.mjs` runs all five arms. Each session gets its own `mkdtemp` project with `calc.js`,
`test.js`, a fresh store, a real `asc init`, and a shim on `PATH` that execs
`packages/cli/dist/bin.js`, so `asc` behaves as installed without one being installed. Arms C, D and
E run `asc install-hook --yes` for real and patch only the hook's *command*, leaving the structure
the CLI wrote untouched — so the hook's output is the sole variable between them. Outcomes are read
by SQL against the session's own store after it exits.

`spike/ev16-brief-canary.mjs` is the delivery check and the bisection harness. `EV16_SIZES` takes
filler-type counts, `EV16_CHANNEL` selects `stdout`, `json` or `pointer`, and `EV16_PROMPT` overrides
the question — the first phrasing produced a false negative and the override exists so the
instrument can be varied without editing the harness.

Both need `EV16_MODEL` set and a first-party Anthropic route; read `modelUsage` off each result
envelope to confirm what actually billed rather than trusting `model:` in settings.
