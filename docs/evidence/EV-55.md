# EV-55: does a budgeted beads SessionStart hook deliver the memories, and are they then used?

**Status**      Measured 2026-10-13 for `asc-2ygy`. Predictions were written into the bead's notes
                before either arm ran and before the fix existed; they were not sealed by sha256.
                The unprompted probe was added after the quiz's before arm was read.

**Question**    `EV-54` found `bd prime` prints every memory in full, about 48KB, which the harness
                will not inline: 309 deliveries reached the model as a 2KB preview. If the hook
                prints an index under the cap instead, does the whole index arrive, and does a
                session then use a memory it was not asked about?

## The change

`.claude/settings.json` ran `bd prime --hook-json` at SessionStart. It now runs
`.claude/bd-prime-hook.mjs`, which prints the beads core rules and one line per memory (the key
and the start of its text), shrinking the lines until the output fits 8,000 bytes, the cap
`BRIEF_CAP_BYTES` in `packages/cli/src/brief-text.ts` already sets for ascend's own brief. The full
text of a memory is one `bd recall <key>` away. On a failure it prints one line saying the index
could not be built.

## Method

One headless `claude -p` run per arm and per prompt, in this checkout, with `Read` and
`Bash(bd:*)` allowed. The before arms ran with the old hook, the after arms with the new one.

- **Delivery** is read from each run's own transcript: the SessionStart attachment record for the
  beads hook, its byte length, whether it is a `<persisted-output>` preview, and how many of the
  43 memory keys it names.
- **Quiz.** Three direct questions whose answers are in `kysely-rejected`,
  `pagination-order-key` and `invisible-character-hygiene`, none of them in the first 2KB of
  `bd prime`.
- **Unprompted probe.** Two design questions that do not mention memories or beads: how to page
  the entries table, and which query builder to add to the store. A recorded decision exists for
  each. An answer is correct when it matches the recorded decision.

## Predictions

- **P1.** Before: the delivery is a persisted preview naming at most 3 of the 43 keys.
- **P2.** After: inline, at most 8,000 bytes, naming all 43 keys.
- **P3.** The quiz's before arm scores at most 1 of 3 and its after arm at least 2 of 3.

## Decision

**Keep the change.** Delivery is fixed and that part is a measurement: the index arrives whole
where a 2KB preview arrived before.

The quiz showed the old hook's failure was never that the memories could not be found. A session
asked a direct question went and got them. The failure is the case nobody asks about, and the
probe is the only evidence on it: with the old hook the session made no tool call and recommended
the library this project measured and rejected; with the index it recalled the decision unasked.

**That probe is two questions in one run per arm, an anecdote under `MIN_N`.** It is the expected
direction and no more. A graded answer needs the same probe over at least 20 sessions per arm.

A consequence for writing memories: a session now sees about the first 120 characters of each.
A memory that opens with a bead id and a date spends its summary on them. The rule belongs first.

## Confidence

**High** for delivery: read from the transcript records of four runs, and the before figure
matches the 309 deliveries in `EV-54`.

**Low** for use: one run per arm, one model, questions chosen by the author of the fix, and the
summary width that fits the cap happens to keep the pagination rule inside the visible line.

**Limitations.** The four headless runs are now transcripts under this project and will be
ingested as sessions. The cap is the bracketed figure `brief-text.ts` documents, not a located
limit. As memories are added the lines shrink, and past roughly 180 keys some stop being listed.
Other projects on this machine still run `bd prime --hook-json`.
