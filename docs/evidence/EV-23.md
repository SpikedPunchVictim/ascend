# EV-23: how often does an edit reach the next prompt with no check run after it?

**Status**      Measured 2026-09-24 for `asc-6ola.7`. Predictions were written to the bead's notes
                before any count was run. They were not sealed by hash; the bead history is the
                record of their order. Q1 missed its predicted range, Q2 landed inside it, and
                Q3 had the right direction but too small a gap.

**Question**    For `asc-6ola.7`: *"how often does an edit reach the user untested, and how long
                does verification take when it happens?"* It is also the acceptance case for the
                handler DSL's `window` + `absent` semantics.

## Method

Two handlers in `handlers/`, replayed by `asc handlers check` (the production normalizer and
evaluator, `derive_version` 1):

- `edit-unverified.yaml`: `on: file.changed`, `window: { until: prompt.submit, absent: { on:
  check.run } }`.
- `edit-verified.yaml`: the same window with `first: { on: check.run }`, emitting the edit's
  `ts` and the first check's `ts` and runner.

The definitions were fixed in the pre-registration:

- **Unit:** one `file.changed` event. A MultiEdit with k edits counts as k units, and a failed
  edit emits none.
- **Window:** one `(session, agent)` stream, running until the next `prompt.submit`.
- **Verified:** any `check.run` in the window, whatever its verdict or verdict_state.
- **Unclosed:** an edit whose stream ends before another prompt is unclosed, excluded from
  the denominator and reported.

Latency and the code-path split are computed from the emitted rows by a scratch script (analysis
happens downstream, not in the handler).

Frozen corpus: `spike/replay`'s copy, this project only, 77 files, 100,138 events,
2026-09-12T01:07:55.847Z to 2026-09-23T06:46:31.270Z.

## Predictions (bead notes, before measuring)

- **Q1:** the unverified share of closed edits is 15–25%. For comparison, the Fable review
  reported 572/3,046 = 18.8%, not re-verified.
- **Q2:** among verified edits, the edit-to-first-check latency has p50 in 30–120 s and p90 in
  150–600 s. Fable reported p50 61.6 s and p90 261.7 s.
- **Q3:** restricted to `.ts .tsx .js .mjs .cjs` paths, the unverified share is lower than for
  all edits, by at least 5 points.

What the split actually shows is the non-code side: 31.7% of edits to paths without a code
extension reach the prompt unchecked (what those paths are was not broken down), against 10.5% for code.

## Against Fable's 572

The denominator matches exactly: 3,046 triggers, the same as Fable's. The numerator does not
(411 against 572), and the difference cannot be traced, because Fable's method was never
recorded. Two candidate causes were measured, and neither explains it:

- **Unclosed edits.** Counting all 52 as unverified gives 463, not 572.
- **`prettier --write` counted as a check.** Dropping those runs before the handler sees them
  gives 437/2,991 = 14.6%:

  ```
  as derived: unverified 411/2994 = 13.7% (code paths 266), triggers 3046, unclosed 52
  prettier --write dropped: unverified 437/2991 = 14.6% (code paths 282), triggers 3046, unclosed 55
  ```

  That check is itself a defect, recorded as `dogfood/0015` and `asc-6ola.15`. Its effect on this
  question is 0.9 points.

## Limits

- **One project, one operator.** This is n = 1 at the project level, so no claim about other
  projects follows.
- **Subagent edits.** An edit in a subagent stream lands in `unclosed` when no later prompt
  arrives in that stream; how many of the 52 are subagent edits was not measured. A check run by a subagent does not verify its parent's
  edit.
- **"Verified" means a check ran.** It does not mean the check covered the edited file, or that
  it passed.
- **Units.** MultiEdit counts once per sub-edit. No MultiEdit appears in these rows; the tool
  split is Write 629 and Edit 2,365.

## Decision

`edit-unverified` works as a derived event, and the window + `absent` semantics are accepted: the
partition identity holds on the real corpus and on the fixture. The intervention candidate is
**non-code edits** (about a third reach the prompt unchecked), not code edits. That goes to the
checklist trigger design in `asc-6ola.1` and `asc-6ola.11`.
