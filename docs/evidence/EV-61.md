# EV-61: how often would a size-and-churn rule fire on our own session commits?

**Status**      Measured 2026-10-13 for `asc-oo8z`. Design and predictions were in the bead's
                description before the replay ran; not sealed by sha256. Two things were added
                after reading the first run and are marked below: the join by time, and the
                repository-side rate.

**Question**    `EV-60` confirmed two commit-time features on public repositories. Before any nudge
                is written: can they be computed for the commits our own sessions make, and how
                often would a rule on them fire?

## Method

**The trigger is a handler**, replayed with `asc handlers check --all-projects` (hash
`3eedd37070549aa5a87affca0ca26027bac8cf27cbf34d8d868b64e3345bfad9`). It lives in the session
scratchpad; nothing was added to `handlers/` and no hook was installed.

```yaml
# EV-61: the moment a session commits. The trigger for a size-and-churn rule; a script grades it.
on: command.run
description: A session ran git commit.
where:
  head: { eq: git }
  argv: { contains: commit }
emit:
  id: '${id}'
  argv: '${argv}'
```

Events carry no sizes, so a script grades each trigger. Everything is read-only: the transcripts,
and `git log --all --numstat` in the repository at the call's `cwd`.

- **Join.** As registered: the `[branch sha]` line git prints in the tool result. **Added after the
  first run**, because 3,663 of 4,224 triggers printed no sha (the sessions commit with `-q`): the
  repository's commits whose commit time falls between the call's start and its result, taken only
  when their number equals the call's quiet commits.
- **Features**, as `EV-60`: added source lines (30 files or fewer), and the most changes any of the
  commit's source files had in the prior 30 days.
- **Thresholds a live session could compute**: the 90th percentile of each over the repository's
  eligible commits in the 180 days before the commit; fewer than 50 such commits is "no threshold
  yet". **Fire**: either number above its threshold.
- **Repository side, added after the first run**: every eligible commit each repository holds
  inside the transcript window, graded the same way with no join, to see whether the join biases
  the rate.

## Predictions

P1 at least 60% of triggers in ascend resolve to a commit. P2 across all projects fewer than 50% do.
P3 the fire rate is between 10% and 25%. P4 the churn flag fires on under 10%. P5 at least half the
sessions with a graded commit hold a fire. P6 in ascend at least a third of size fires are mostly
`.jsonl` data.

## Decision

**The rule can be computed, and as defined it would fire too often and on numbers far outside
where it was learned. Do not write the nudge yet.**

1. **Our repositories are not in the range the rule was confirmed in.** The 90th percentile of
   added lines is 634 to 1,632 here, against 229 on nx and 78 on nest. The busiest-file threshold
   is 13 to 52 changes in 30 days, against 6 on nx. "Relative" keeps the rate bounded; it does not
   say a top-decile commit here carries the risk a top-decile commit there did.
2. **The churn flag is not a decile.** It fires on 21.9% because churn keeps rising against its
   own trailing 180 days, so a threshold from the past is always behind. Size behaves: 6.6%.
3. **The burden**: 2.03 fires per active day, and uneven: median 2 per session, 36 in the busiest.
   Both flags together: 1.7% of commits.
4. **The replay join is poor and the live path does not need it.** 43% of triggers resolved; the
   rest are quiet commits in fixtures and temporary repositories, commits run in the background,
   and commits no branch holds any more. A hook at commit time has the commit in hand. The join
   did not bias the rate: 26.8% joined, 26.1% from the repository side.
5. **Over half of what sessions commit has no source lines**: 984 of 1,816 joined commits were not
   eligible. The rule is silent on those by construction.
6. **There is no outcome to check it against here.** None of these repositories types its commits,
   so `EV-57`'s fix definition cannot be applied, and whether the flags predict anything in our
   own work is unmeasured.

The `grizzly-*` repositories share history (their thresholds and counts are near-identical), so
the repository-side total counts some commits several times; the per-repository rows stand alone.

Next, in order: an outcome that needs no commit types (any later commit rewriting the lines within
30 days, checked on n8n against the typed definition); then record the two numbers passively at
commit time, with no nudge; then the holdout.

## Confidence

**High** for the counts and for the thresholds. **Medium** for the fire rate as the rate a live
rule would have: the join lost 57% of triggers, and the repository side agrees with it.
**Unknown** whether the flags predict anything in these repositories. One user, one machine,
49 days.
