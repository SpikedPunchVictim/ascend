## Method

Three inspections, all local, all read-only. Each is a *negative* measurement — "looked here, the
thing is not here" — which is only meaningful when the place looked is the place it would be:

- **Installed applications.** The names a JetBrains merge tool or GitHub Desktop would install as:
  every JetBrains IDE (they share one platform merge UI) plus GitHub Desktop, checked in
  `/Applications` and `~/Applications`.
- **Spotlight**, so a bundle outside those two directories is not missed: a sweep for
  `kMDItemKind == "Application"` matching GitHub Desktop / JetBrains / IntelliJ.
- **Per-user support directories.** A client that has ever run leaves one. Its absence is evidence
  beyond the app bundle's absence, because it covers "installed elsewhere and launched".

And the one piece of positive reachability evidence, for the surface that is *not* an installed app:

- **`gh auth status`**, for what the GitHub arm's credentials can actually do. The token is redacted
  here; only the account and scopes are reported.

## Pre-registration

Written 2026-10-04, **before any of the three surfaces has been driven**. Falsifiers given with each,
because a prediction without one is an opinion.

**P-A — GitHub's web conflict editor is NOT clean, and the driver buys nothing on this path.**
Driven on the `base-union` fixture, the PR shows *Resolve conflicts* and the editor presents
`records.jsonl` **with conflict markers already in it** — because the file the editor edits is
GitHub's own plain 3-way merge result, and GitHub's server never runs the driver (EV-31: six cells,
union base indistinguishable from the plain control). GitHub's own documentation confirms the
affordance and the button set: the editor is for *"simple competing line change conflicts"*, it
presents the file for the human to *"delete the conflict markers"*, and its choices are *"keep only
your branch's changes, keep only the other branch's changes, or make a brand new change."* A naive
click on either one-sided choice yields **4 records, every line parsing, no markers, one append gone** —
the loss shape exactly.

*Falsified by:* the editor declining to open for a `.jsonl` file, or the file it presents being
**marker-free** (which would mean GitHub resolved with the driver, contradicting EV-31's server-side
result and reopening that record).

**P-B — GitHub Desktop and JetBrains are clean on `base-union`, and for the opposite reason.**
Both delegate the merge to the `git` binary, which honours the driver (EV-42), so on `base-union`
**no conflict is ever raised** and their merge UIs are never entered. They are clean by never being
reached, not by resolving well. Their UIs would still lose an append if handed a conflict — which is
what the control base is for.

*Falsified by:* either client reporting a conflict on `base-union`. **On `base-plain` all three are
predicted to conflict and a naive accept to lose an append** — that is the control, and it is predicted
to behave as the command-line control already does.

## Decision

**All three surfaces: UNMEASURED, never `0`, and this bead closes with them unmeasured.** The record
of *why* is the deliverable; the surfaces themselves are untouched, and the reachability table above is
what makes a later run cheap.

What follows for the layout decision, which is what the whole EV-31→EV-43 series exists to serve:

- **The corrected bound must not be repeated.** GitHub's refusal on `base-union` is evidence that the
  hand-resolution path is **opened**, not that it is closed. Any summary of this series that reads
  "bounded by EV-31" is wrong and should be replaced with EV-31's own sentence.
- **The one surface where the driver provably buys nothing is also the one surface that cannot be
  reached from here.** That is the honest state: not "bounded", not "clean", but *known to be reachable
  and unmeasured*, with a falsifiable prediction now on record for it.
- **What catches that loss, if it happens, is already built.** A one-sided in-editor resolution
  produces well-formed JSONL with records missing — no markers, nothing unparseable — so it is caught
  by `asc-98e1`'s **lost-id** half of the guard and by nothing else. That half exists and runs in this
  repository's own gate (E15 / `asc-9flv`). This record adds no requirement to it.

## Confidence

**High** that these three surfaces are unreachable from this machine. Two independent negative checks
agree for the two installed-app surfaces (bundle directories **and** Spotlight, with the same two
commands returning VS Code and Chrome as a positive control), the per-user support directories that a
launched client leaves behind are also absent, and `gh`'s four scopes are API/git scopes with no web
session among them.

**High** on the correction: EV-31 states it in its own words, quoted verbatim in Status. The bound that
was replaced is contradicted by a record in this same series.

**Low on everything about the surfaces themselves — by construction.** This record predicts; it does
not know, and it must not be cited as though it did. **P-A chains two inferences** — that GitHub offers
the editor on a conflicted PR (from GitHub's documentation, not from this machine) and that the file it
presents is marker-bearing (from EV-31's server-side result) — and a two-inference chain is exactly the
kind of claim this series has watched break twice, in P2 and P3 of `asc-3ow4`, both by reasoning from
documented behaviour the implementation does not follow.

**Unmeasured and not predicted here:** whether GitHub's editor refuses files past a size or complexity
threshold — its documentation states the limits for neither, and the fixture's file is 8 lines.
