# EV-40: is the forge's web conflict editor reachable, and does a naive resolution lose records? (`asc-kq2f`)

**Status**        Measured 2026-10-03 for `asc-kq2f`, against **Forgejo 10.0.3** in a throwaway
                  Docker container (`codeberg.org/forgejo/forgejo:10`,
                  `sha256:99b6c15a1bc98e623103a83a04023662a93fd035dac4f0a856d781afa9d71095`, the
                  same build `EV-31.md` used) driven by a real browser.

                  **The surface the question named does not exist in this version.** Forgejo 10.0.3
                  has no web conflict editor: the route 404s, the PR page offers no resolution
                  control, and the binary contains no such handler. Recorded as **NOT REACHABLE —
                  surface absent**, which is not `0`. `EV-31.md` left this surface UNMEASURED; this
                  record replaces that with a measured absence.

                  Unchanged and still **UNMEASURED, never 0**: GitHub's own web conflict editor,
                  GitHub Desktop, JetBrains, and VS Code.

**Question**      Named before running, from the bead:

                  **Q1.** `EV-31.md` measured the server-side PR **merge button** and found every
                  cell refuses loudly. A refusal means the only way such a PR lands is a human
                  resolving by hand. **Does the web conflict editor honour `merge=union`?**

                  **Q2.** Specifically: drive that editor to a **naive resolution** (accept one
                  side), then read `records.jsonl` back **from the server**. Success is 5 records
                  with `ra0` and `rb0` both present, no markers, no duplicates.

                  **Q3.** The failure being hunted is **not** markers. A one-sided resolution leaves
                  *well-formed* JSONL with the other side's appends silently gone — every line
                  parses, no markers, the file simply holds fewer records. That is the shape
                  `asc-98e1`'s lost-id comparison exists to catch and the shape a
                  markers/unparseable check passes.

                  Each surface is recorded **clean / 0-lost** or **UNMEASURED** — never as `0`.

## Method

Fixture `spike/git-layout/union-fixture.sh` — two bases differing **only** in `.gitattributes`
(`base-union`: `records.jsonl merge=union`; `base-plain`: the attribute absent), each with branches
`a-*` and `b-*` appending one record from its own base. Command-line git on that exact shape is
already measured clean-on-union / conflicted-on-plain, so any conflict below isolates the client.

Harness `spike/git-layout/union-forge-editor.mjs` (+ `union-forge-editor-drive.mjs`): stages a cell
over the Forgejo REST API, then hands the conflicted PR to a browser. The browser arm is
**`puppeteer-core` 25.12.0 driving the system Chrome** (`/Applications/Google Chrome.app`) —
`puppeteer-core` deliberately downloads no browser, so the arm adds a driver and no download. It is a
**devDependency, accepted explicitly into `.align/baseline.json`** for
`security.manifest.new-dependency` — an owner decision, recorded in the baseline rather than left as
an unaccepted violation. That rule exists so a new dependency is something somebody chose, and the
baseline entry is where the choice is written down; it never reaches a shipped artifact, being a
devDependency. The arm is checked in because this record's central claim is an **absence**, and a
later Forgejo may grow the editor — at which point this is the thing that would notice.

**Every reading of `records.jsonl` is taken from the server** through the contents API after the
action, never from the client's own report. That is the whole point: the failure under test is a
file that parses cleanly while missing records.

## Measurement

### Q1 — the server-side result reproduces on a fresh container

`EV-31`'s finding restated on this container, both bases, read back from the server:

```
=== union
  PR a #11: MERGED -- merged
  main after PR a : 4 records, ra0 present, rb0 ABSENT, markers none, unparseable lines 0
  PR b #12: mergeable=false
  pr-b branch     : 4 records, ra0 ABSENT, rb0 present, markers none, unparseable lines 0

=== plain
  PR a #13: MERGED -- merged
  main after PR a : 4 records, ra0 present, rb0 ABSENT, markers none, unparseable lines 0
  PR b #14: mergeable=false
  pr-b branch     : 4 records, ra0 ABSENT, rb0 present, markers none, unparseable lines 0
```

`mergeable=false` on **`base-union`** is the load-bearing cell: the tree declares
`records.jsonl merge=union`, command-line `git` merges it clean to 5 records, and Forgejo still
reports a conflict. The forge does not honour the attribute — agreeing with `EV-31`. Nothing is
lost, because nothing is written: PR b stays open and `pr-b` keeps its own record.

### Q2 — there is no web conflict editor to drive

Five independent checks, all against the running container. The first is what the arm hit:

**Q2a — the route does not exist.** `EV-31`'s context carried the belief that *"the Gitea family's
conflict editor lives at `/pulls/:index/conflicts`."* It does not:

```
GET http://localhost:3301/probe/union-probe/pulls/10/conflicts -> 404 final .../pulls/10/conflicts
GET http://localhost:3301/probe/union-probe/pulls/10/diff      -> 404 final .../pulls/10/diff
```

**Q2b — the PR page offers no resolution control.** The conflicted PR renders its conflict section
with **zero links**; the only affordance is a collapsed block of command-line instructions:

```
--- merge-section text ---
This pull request has changes conflicting with the target branch.
records.jsonl
View command line instructions

--- every link inside .merge-section ---
[ { "tag": "details", "t": "View command line instructions" } ]
```

A 404 is weak evidence on its own — a route can be gated. The remaining three checks rule that out.

**Q2c — the binary contains no such route or handler.** Forgejo ships as a single Go binary, and its
symbol table is **intact** (the control symbols below are all present), so absence is meaningful:

```
control symbols:                    conflict-resolution symbols:
  PullRequestMerge       11           /conflicts              0
  CompareAndPullRequest   5           ConflictEditor          0
  MergeStyle             29           conflicts.tmpl          0
  /pulls/{index}          1           conflict_editor         0
```

The binary knows the `/pulls/{index}` group and every conflict *reporting* token
(`has_conflicts`, `conflicted_files`, `merge_conflict`, `merge_conflict_summary`) — and no editor.

**Q2d — no configuration switch disables it.** `[repository]` and `[ui]` in `/data/gitea/conf/app.ini`
hold no conflict key, and the image's defaults add none. There is no feature to switch off.

**Q2e — no user-facing affordance exists for one.** A resolve control needs strings; the binary has
none. `accept_current`, `accept_incoming`, `accept_both`, `use_ours`, `use_theirs` and
`resolve_conflict` all count **0**. The two `theirs` hits are `json:"theirs"` (a GitLab-API-compat
field) and `theirs | possessive pronoun` (a spell-check dictionary entry); the `resolve` hits are
DNS resolvers and GitLab's `merge_request_to_resolve_discussions_of`.

**Therefore the question cannot be answered by driving the editor, because there is nothing to
drive.** The PR page tells the human to resolve on the command line, and command-line git on
`base-union` is already measured clean at 5 records.

### Q3 — and the arm reported a cell that had never reached the state under test

Worth recording because it is the same shape this whole series hunts. `stageCell` opened PR a and
merged it immediately. Forgejo evaluates mergeability **lazily**, so the merge came back
`"Please try again later"` with the PR simply not merged — and the run continued anyway:

```
{ "aNumber": 7, "aMerged": false, "aMessage": "Please try again later",
  "bNumber": 8, "bMergeable": true,           <-- no conflict: PR a never landed
  "afterA": { "records": 3, "ra0": false, "rb0": false }, ... }
```

`main` still held the base, so PR b had nothing to conflict with, `mergeable` came back **true**, and
the conflict editor 404'd. Had the arm only asked *"did the editor page load?"* it would have
reported a clean cell for a PR that was never in the conflicted state. What exposed it was reading
`records.jsonl` **from the server** and finding `ra0` absent where the fixture says it must be.

Fixed in the harness two ways, both measured on the re-run above: PR a is settled before merging,
and a refused merge now **throws** instead of being recorded as a field. A cell that did not reach
the state under test must stop the run.

One smaller instrument note: `puppeteer`'s `button[type="submit"]` matched nothing on Forgejo's
sign-in form. The button carries **no `type` attribute** — the DOM *property* reads `submit` because
that is a `<button>`'s default, but the attribute selector matches nothing. The arm now clicks by
text. A selector that silently matches zero elements is the same class of false-negative.

## Decision

**The Forgejo / Gitea-family web conflict editor: NOT REACHABLE — the surface does not exist in
10.0.3. Recorded as absent, explicitly not `0`.**

What follows for the guard `asc-98e1` built, which is what this bead exists to decide:

- **This surface cannot silently lose records, because it cannot resolve at all.** A forge that
  refuses and pushes the human to the command line is refusing in the safe direction — the same
  shape `EV-31` found for the merge button. On `base-union` the command-line path keeps both appends.
- **So this arm does not demonstrate a need for `asc store verify` in CI.** The guard's value against
  a forge-mediated loss is not shown here, because the reachable forge paths either refuse loudly or
  delegate to `git`, which honours the attribute. That is a statement about Forgejo 10.0.3's web
  surfaces, not about the guard's general worth — `EV-31`'s `mergeable` false-green is a separate,
  already-recorded reason to distrust a single reading.

**Still UNMEASURED, never `0`:** GitHub's own web conflict editor (a different implementation — the
owner's browser session would be the only route to it), GitHub Desktop and JetBrains (not installed),
and **VS Code** (installed and reachable, but not drivable by `puppeteer` — it is an Electron GUI and
needs a different mechanism, so it was not driven).

## Confidence

**High** that Forgejo 10.0.3 has no web conflict editor. Five independent checks agree, one of them
the binary's own symbol table with its control symbols verified present — and the negative claim is
the kind that needs more than a 404, which is why the last three were run.

**High** on Q1's reproduction: it is the same fixture, the same image digest, and the same
server-side read as `EV-31`, and it reproduces on both bases.

**Medium on scope, and worth stating plainly:** this is a statement about **one version of one
product**. Forgejo 10 is Gitea-1.22-derived; a later Forgejo, a different Gitea, Gitea Forge or
GitHub may add an editor, and this record would not cover it. The Gitea family was chosen for this
arm because it shells out to `git` for merge work; GitHub's editor is a different implementation and
remains unmeasured.

**Not measured at all:** whether any client can lose records on `base-union`. The only arm that could
have answered it — the editor — does not exist, so the honest result is absence, not a clean pass.
