# EV-50: can the hard-coded deriver rules move to typed handlers?

**Question.** `asc-tuur.10`, filed 2026-09-27 with the premise stated as fact:

> `asc-tuur` made `handlers/*.yaml` with `type:` a capture mechanism (find at ingest, say at a
> lifecycle hook). The derived types in `packages/adapter-claude-code/src/derive.ts` are still
> hard-coded TS rules. Moving them to typed handlers would put every capture route in one reviewed,
> replayable form.

The question the bead needs answered before anyone writes code is not *how* to port them but **whether
they can be**: what does each rule read, and does the handler DSL have that.

**Method.** Read every rule body in `packages/adapter-claude-code/src/derive.ts` (1,696 lines) — the
eleven `accept*` / `flush*` / `emit*` / `shape*` declarations reaching seven `emit` call sites for six
types: `acceptToolUseBlocks` and `acceptSkillAttribution` (`skill_activation`, two routes),
`acceptToolDenial`, `acceptCompaction`, `acceptVerification`, `acceptCorrection`, and
`acceptReviewCall` + `shapeFinding` + `emitReport` (`review_finding`'s reported route). For each, list
the facts it reads and where those facts come from. Then compare against `packages/core/src/event.ts`
(`EVENT_KINDS`, fifteen kinds) and the handler DSL's own vocabulary.

The question was named by the bead a month before this reading, and the alternative outcomes were
fixed in advance by the plan approved for it — record the blockers, or attempt the port. This is the
first.

**A framing correction, because it changes the answer.** The deriver does not read the event stream.
It reads normalized *records* — the transcript's own JSON, with its record-level fields intact — and
builds events as a side effect. A typed handler reads *events only*. So the gap between them is
`records → events`, and the question "can this rule port?" is exactly "does the event stream carry
what this rule reads?"

## Finding 1 — every remaining rule needs one of two things, and only two

| rule function | type | what it reads | on the event stream? |
|---|---|---|---|
| `acceptToolUseBlocks` | `skill_activation` (by invocation) | `claims` counter, `run` (held) | **no** — DSL state |
| `acceptSkillAttribution` + `flushRun` | `skill_activation` (attributed) | `attributionSkill`, `attributionAgent`, `file.kind === 'subagent'`, `claims`, `run` | **no** — record + file facts, and state |
| `acceptToolDenial` | `tool_denial` | `toolDenialKind` | **no** — record fact |
| `acceptCompaction` | `context_compaction` | `compactMetadata.preTokens/postTokens/cumulativeDroppedTokens/durationMs/trigger/preCompactDiscoveredTools`, record `uuid` | **no** — record fact + identity |
| `acceptVerification` | `verification_run` | `lastVerdict` (the per-file chain) | **no** — DSL state |
| `acceptCorrection` | `user_correction` | `userFeedback` (the user's own words), record `uuid` | **no** — record fact + identity |
| `acceptReviewCall` etc. | `review_finding` (reported) | `pendingReports` — the call is HELD until its own `tool_result` arrives | **no** — DSL state |

Two capabilities, and nothing else:

1. **Cross-record mutable state.** Three separate rules need it and none of them is a variation on
   another: `lastVerdict` is a *chain* (a value carried forward and compared), `pendingReports` is a
   *hold-and-resolve* (a record parked until a later one arrives), `claims` + `run` is a *count plus a
   carried aggregate*. The DSL has none of the three, and a design that ships only the chain would
   port one rule.
2. **Record-level facts on events.** `toolDenialKind`, `compactMetadata`, `userFeedback`,
   `attributionSkill` / `attributionAgent`, `file.kind`, and the source record's `uuid` — which is also
   what supplies `context_compaction`'s and `user_correction`'s entry identity, since neither has a
   tool call to be named by. This changes the event stream, so it owns the `EVENT_DERIVE_VERSION` bump
   (`packages/adapter-claude-code/src/normalize.ts`, currently 12).

## Finding 2 — three candidate capabilities the reading refuted

Recorded because a refutation is the part that stops the same idea being re-proposed. Each was
plausible from the outside and died on a rule body.

- **A trigger-vs-`before` comparison operator.** Refuted. Every comparison a rule makes is against
  either carried state (`previous !== verdict`, `run?.skill !== invoked`) or a field on the record it
  is already reading (`claimed === 0`, `file.kind === 'subagent'`). No rule needs to compare the event
  it triggered on to a different event's value.
- **A lookup: "which tool does this result belong to?"** Refuted, and it looked like the strongest
  candidate of the three. The deriver keeps an `invocations` Map precisely because a refusal and the
  invocation it refused are on different records — but the events already carry it: `tool.use.start`
  and `tool.use.end` both carry `tool` and `id`, and `check.run` carries `runner`, `verdict` and
  `verdict_source`. So `verification_run`'s per-event facts are **already normalized**, and the Map is
  redundant with the stream rather than evidence of a missing capability. What remains missing for
  `verification_run` is only `lastVerdict`.
- **A custom entry-identity capability** for the two types keyed on a record `uuid`. Subsumed, not
  refuted: an event carrying its source record's uuid supplies the identity, so it is a field on the
  event and belongs to capability 2 rather than to a bead of its own. Filing it separately would have
  been filing the same work twice.

## Finding 3 — the one port that already happened explains why the others did not

`handlers/review-finding-table.yaml` carries `type: review_finding` and writes entries as
`captured_by: parsed`. It is a derived type reaching the store through a typed handler — the bead's
goal, achieved. It works because **reading a Write's table is stateless**: the Write's content is the
answer, and no earlier record is consulted. Its docblock states the rest of the design in the shape
this analysis confirms — keyed on the Write's tool_use id and the row's position, validated against the
type like any derived entry.

That is the whole explanation of the split. The one route that ported is the one route with no state
in it, and it did not port because someone got to it first; it ported because it *could*. The reported
route of the same type — the one that reads a `ReportFindings` call and waits for its result — did not,
and cannot under the current DSL. **The same type has one portable route and one blocked one**, which
is a cleaner statement of the boundary than any count.

## Decision

**`asc-tuur.10` is not a port; it is two capabilities plus a re-scope.** The bead's premise — that
moving the rules "would put every capture route in one reviewed, replayable form" — is true only if all
six move, and two of the six cannot without work that does not exist. Porting three of six would not
achieve the stated goal and would leave the deriver and the handlers both holding capture routes: the
opposite of "one reviewed form".

Taking the owner's decision (2026-10-12): write the analysis, file the two capability beads, and
re-scope `asc-tuur.10` as their parent rather than as an implementation task. **No port code was
written, and none is claimed.**

`asc-tuur.10`'s own dependency notes are worth recording as still sound: it depends on `asc-73cb`
(a `segment` event, so a handler can key on the holdout unit — the `segment` field is now on the
envelope) and `asc-tuur.9` (`asc types capture`). Both are closed, and neither is the blocker. The
blocker is the DSL.

## What this does not show

- **It does not measure whether these rules *should* move.** The case recorded for porting is
  reviewability and replay in one form. A rule that is subtle for a reason unrelated to its
  expressibility — `acceptVerification`'s per-file-versus-per-session chain scope is the clearest, where
  chaining across a session id gives 171 verdict moments against the per-file 486, because subagent
  transcripts share the parent's id — may read *better* as code. This analysis says the port is
  currently impossible; it does not say it is desirable.
- **It does not size capability 1 or 2.** The bead must, and the sizing is not here. What is here is
  that capability 1 needs three shapes of state, not one, and that capability 2 changes the event
  stream and therefore the derive version.
- **It does not count the records that would move.** The figures quoted are the deriver's own, measured
  when its rules were written — 6,826 commands that run a check against the 486 verdict-change moments
  worth storing; 438 measured compactions with all five required fields present on 438; 105 of 105
  `Skill` results not errors. These are the rules' justification for existing as code, not a port
  estimate.
- **It does not touch either defect the pilot found.** `dogfood/0082` and `dogfood/0083` are separate
  findings with separate fixes (`asc-xagi`, `asc-4031`), and nothing here changes their mechanism.

## Confidence

`Traced` — every claim is read off a rule body, an `EVENT_KINDS` entry, or a docblock in the file being
discussed, and the two refutations in Finding 2 are refutations by enumeration: the fifteen event kinds
were listed and each rule's read was checked against them. Nothing here was executed, because there is
nothing to execute — which is the finding.
