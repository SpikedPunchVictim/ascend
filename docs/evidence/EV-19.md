# EV-19: run against ascend's own build corpus, does the SHIPPED analysis layer surface a real pattern — or noise?

> **PRE-REGISTRATION.** Everything above the `## Measurement` rule was written and committed
> BEFORE any measurement was run, as `asc-c9h` requires ("Name the question BEFORE running").
> The predictions are numbered so that each can be marked hit or missed rather than reinterpreted.
> Commit history is the receipt.

> **Project identifiers are redacted.** This repository is public and the corpus spans twelve
> working directories, only one of which (`ascend`) is this repo. Private project names are
> replaced with stable pseudonyms `<project-A>` .. `<project-F>`; the same pseudonym always means
> the same project, so every count and comparison below stays checkable. No unredacted version
> was ever pushed.

**Question**    This is the project's own acceptance test. EV-3 already established that an
                actionable pattern EXISTS in this corpus — but it found it with ad-hoc scripts
                (`spike/lib/stats.mjs`, `spike/spike-patterns.mjs`) carrying chi-square, Cramér's V
                and a 5,000-iteration permutation control. **None of that machinery shipped.** The
                CLI a user actually gets has `asc explore` (profile, sample), `asc annotate`
                (rules, census, remainder, back-test) and `asc kappa`.

                So the question EV-3 does not answer, and this one asks: **can the SHIPPED
                instrument recover a real pattern, and does it separate that pattern from noise?**
                If the analysis layer only works as a pile of spike scripts, ascend has not shipped
                its own premise.

## Method

Target `tool_denial`, N=564 — the largest hand-interpretable type, and the one EV-3 used, so the
two measurements can be compared directly.

**The prediction task, and why it is not a tautology.** The rule predicts `denial_kind` using ONLY
`tool_name`, `project` and `occurred_at`. `denial_kind` itself is held out from every rule. This is
deliberate: EV-3's own Decision section flags that `project × repo` scored V=0.761, survived the
shuffled control, and was still not a finding — the two are a deterministic mapping, and shuffling
cannot detect a definitional relationship. A hand label that is a function of a property the rule is
allowed to read would reproduce exactly that defect at precision 1.00. Holding the target out is
what makes the back-test able to fail.

1. **Profile** — `asc explore tool_denial`.
2. **Sample** — `asc explore tool_denial --sample stratified --by denial_kind`, fixed seed.
3. **Hand-label** — write the sampled entries' TRUE `denial_kind` as labels under a hand scheme via
   `asc annotate --scheme hand-denial --ids`. Stated plainly: these are read from a held-out
   property, not produced by human judgement. The data carries no command text (six structural
   properties, no `evidence_text`), so labelling by intent is not available on this type at all.
4. **Propose a rule** — SQL predicates over `tool_name` / `project` / `occurred_at` only.
5. **Back-test** — `asc annotate --backtest hand-denial`, giving per-label precision and recall as
   Wilson proportions.
6. **SHUFFLED CONTROL** — the same sampled entry ids, their labels permuted under a fixed seed,
   registered as `shuffled-denial`; the SAME rules back-tested against it. This is the false-pattern
   measurement: a rule that scores as well against permuted labels as against true ones has found
   nothing.
7. **Apply and report** the census and its unclassified remainder.

**Step omitted: `cluster`.** The METHOD names six steps; this runs five. Lexical clustering
(`asc-h7d`) is unbuilt, and would be the wrong instrument regardless: it reads `evidence_text`, and
1,702 of 1,785 entries (95.5%) have none by design (`derive.ts:92-95` — prose reaches
`evidence_text` on the one derived type whose value IS prose, which is what keeps raw transcript
text away from anything that prints). Clustering would see 81 of 1,785 entries. Decided with the
user 2026-09-17; recorded here rather than quietly dropped.

## Predictions, fixed before running

- **P1** The rule beats the shuffled control: at least one label's precision against `hand-denial`
  exceeds its precision against `shuffled-denial` by a margin whose 95% Wilson intervals do not
  overlap.
- **P2** The rule will NOT be highly accurate overall. `Bash` is 513/564 (91.0%) of entries and
  carries all four denial kinds, so `tool_name` cannot separate them within Bash. I predict overall
  accuracy well below 90%, and that the failure is concentrated inside Bash.
- **P3** Reproducing EV-3: the non-Bash interactive tools (`AskUserQuestion`, `ExitPlanMode`) are
  ~100% `user-rejected`. EV-3 measured 12/12 and 11/11.
- **P4** `automode-unavailable` was 1.2% (n=5) in EV-3 and is 23.0% (n=130) here — a ~20x shift. I
  predict this is real and concentrated in recent sessions, not spread evenly across the range.
- **P5** The shipped `asc explore` reports tallies as bare counts, without the Wilson intervals or
  the `MIN_N` anecdote flag EV-3 treated as mandatory — so a reader of the shipped profile cannot
  tell an estimate from an anecdote. I predict this is a real gap in the shipped layer.

**Disclosure of prior exposure.** Before writing this I had already seen, while verifying `asc-2pg`
earlier the same day, the `denial_kind` and `tool_name` marginal distributions, and I had read EV-3
in full. P2, P3 and P4 are informed by that exposure and are therefore weaker evidence than P1 and
P5, which concern machinery I had not run. Saying so is cheaper than pretending to a blindness I did
not have.

## Measurement

All figures below were produced by the shipped CLI on the real store. Sample `n=80` (14.2% of 564),
drawn with `asc explore tool_denial --sample stratified --by denial_kind --limit 80`, fixed seed
`ascend`. Allocation came back PROPORTIONAL, not equal — `automode-blocked` drew 5 of its 36 — so the
sample preserves the population marginals and a precision measured on it is not distorted by the
stratification.

**The rule.** Built from the sample's own cross-tabs, using `project` only. `tool_name` turned out
to be nearly useless: `Bash` is 513/564 (91.0%) of the population and carries all four denial kinds.

```
user-rejected        <- project = <project-A>
permission-rule      <- project IN (<project-B>, <project-C>)
automode-unavailable <- project = ascend (this repo)
```

`automode-blocked` was deliberately given NO rule: no project predicts it. The small projects were
deliberately left out, so the remainder stays a real signal rather than being papered over.

### The shuffled control — the decisive measurement

Same 80 entries, labels permuted under a seeded Fisher-Yates (mulberry32, seed 20260917), which
moved 71.3% of labels and preserved every marginal exactly. The SAME rule was back-tested against
both, with `asc annotate --backtest`.

| label | precision vs HAND | precision vs SHUFFLED | intervals overlap? |
|---|---|---|---|
| user-rejected | **90.9%** (95% CI 72.2–97.5, n=22) | 13.6% (4.7–33.3, n=22) | **no** |
| permission-rule | **90.3%** (95% CI 75.1–96.7, n=31) | 41.9% (26.4–59.2, n=31) | **no** |
| automode-unavailable | **85.7%** (95% CI 65.4–95.0, n=21) | 33.3% (17.2–54.6, n=21) | **no** |
| automode-blocked | `n=0 (no estimate)` | `n=0 (no estimate)` | not testable |

Sample accuracy **66/80 (82.5%) real** against **23/80 (28.75%) shuffled**.

**False-pattern rate: 0 of 3 testable labels.** No label's shuffled precision interval reached its
real one. The control rejected the noise hypothesis three times out of three.

`automode-blocked` returned `n=0 (no estimate)` for precision rather than `0.00`, because the rule
never predicted it — the omission-not-zero rule holding on real data — and its recall row carried the
`MIN_N` anecdote flag at n=5.

### Generalization — the rule applied to all 564

`asc annotate --scheme rule-denial ... --scope "type_name = 'tool_denial'"`: **504 labelled, 60
unclassified (10.6% remainder)**. Of the 504, **431 correct — 85.5%**. The rule was built from 80
entries and held up on 564, slightly ABOVE its in-sample accuracy.

### Predictions, scored

- **P1 — HIT.** All three testable labels beat the shuffled control with non-overlapping 95% Wilson
  intervals. This was the prediction the acceptance test rests on.
- **P2 — numeric claim hit, stated mechanism REFUTED.** Accuracy did land below 90% (85.5%). But the
  reason was the opposite of the one predicted: errors concentrated in the NON-Bash tail
  (21/39 correct, 53.8%) while Bash was the best-performing tool (410/465, 88.2%). P2 reasoned about
  a `tool_name`-based rule; the rule actually built used `project`, so P2's mechanism was never
  tested as written. Recorded as a miss rather than reinterpreted into a hit.
- **P3 — HIT, exactly.** `AskUserQuestion` 12/12 and `ExitPlanMode` 11/11 `user-rejected`. These are
  the identical counts EV-3 measured on a 409-entry corpus, meaning no new denial of either tool has
  occurred since — a stability result neither measurement was designed to produce.
- **P4 — HIT.** `automode-unavailable` ran 3/140 (2.1%) in 2026-08 and 127/424 (30.0%) in 2026-09.
- **P5 — CONFIRMED.** `asc explore --json` contains no `lower`, `upper`, `confidence`, `wilson`,
  `interval`, `proportion` or small-group key anywhere; its rows carry `field` and `value` only.

### Findings

1. **Denial kind is a property of the PROJECT, not the tool.** This is the actionable finding, and it
   is not the one EV-3 reported. EV-3's actionable split was `denial_kind` within `Bash`; at 564 the
   dominant structure is per-project, and `tool_name` barely predicts anything because Bash has grown
   to 91.0% of all denials. The action differs accordingly: permission configuration is per-project,
   so the fix is per-project allowlists rather than one global set.
2. **`automode-unavailable` is a new and now-dominant denial mode.** 1.2% (n=5) at EV-3; 23.0%
   (n=130) now, and 30.0% within 2026-09 alone. It is *unavailability*, not *blocking* — a capability
   gap rather than a policy refusal — and it is the single largest behavioural change in the corpus
   since EV-3.
3. **`automode-blocked` has no project signature — reported as a negative.** It is spread across six
   projects (ascend 16, <project-B> 9, <project-C> 7, <project-A> 2, <project-D> 1, <project-E> 1) and every rule
   misassigns it: 16 to `automode-unavailable`, 16 to `permission-rule`, 2 to `user-rejected`, 2 left
   unclassified. It is a mode-level artifact orthogonal to project, and no rule over the available
   properties can separate it. The method found this by failing to classify it, which is the
   remainder doing its job.
4. **ascend's own benchmark harness polluted its corpus.** Two of the 60 unclassified entries have a
   `project` of `/private/var/folders/<redacted>/T-<ev18-benchmark-tmpdir>` — ephemeral temp directories created by
   EV-18's own measurement runs, recorded as real denials against projects that will never recur.
   Surfaced by the remainder, not by looking for it.
5. **The shipped layer is internally inconsistent about the interval discipline (P5).** `asc annotate
   --backtest` reports every proportion as a Wilson interval with a `MIN_N` anecdote flag; `asc
   explore` — the command whose entire purpose is profiling — reports bare counts. EV-3's Decision
   section made intervals mandatory. A reader of the shipped profile cannot tell an estimate from an
   anecdote.
6. **A 14.2% stratified sample missed an entire project.** `<project-F>` holds 16 population entries and
   drew zero into the sample, so the rule could not have covered it and did not. Ordinary sampling
   variance, but worth stating next to any claim built on an 80-entry sample.

## Decision

**GO, with one qualification.**

The shipped instrument recovers a real pattern and separates it from noise. A rule proposed from 80
entries generalized to 564 at 85.5% precision, and the shuffled control rejected the noise hypothesis
on 3 of 3 testable labels with non-overlapping intervals. Five actionable findings emerged, of which
two (#4 data hygiene, #5 the interval gap) are defects in ascend itself that no one was looking for —
they arrived through the unclassified remainder, which is the mechanism `asc-2pg` exists to provide.

The qualification is finding #5. The analysis layer ships the interval discipline in `--backtest` and
omits it in `explore`. EV-3 established that discipline as the thing standing between a real finding
and a seductive one — its own decisive result was that `tool_name x project`, at p=8.61e-8, was an
artifact of the marginals. `explore` is the first command a user runs, and it is the one that cannot
currently say whether a number is an estimate or an anecdote. **This is filed rather than waved at.**

The acceptance test's own criterion — "if ascend cannot find a real pattern in the record of its own
construction, it will not find one in the user's work" — is met.

## Confidence

**Strong on P1, the question this test exists to answer.** The shuffled control is a permutation of
the same 80 labels, so it holds every marginal fixed and destroys only the pairing — it cannot be
beaten by a rule that has merely learned the marginals, which is exactly the failure EV-3 caught.
Three labels cleared it with non-overlapping intervals, and the rule then held up out of sample on
564 entries at slightly better accuracy than in-sample.

**What this does NOT establish, stated plainly:**

- **The rule was built from the sample it was back-tested on.** In-sample fit is optimistic by
  construction. The shuffled control is what makes that fit interpretable, and the 564-entry
  application is what makes it a generalization claim — but no held-out hand sample was labelled.
- **`project` and time are confounded, and this measurement does not separate them.** Each project
  was worked on in a period, so "denial kind follows project" is partly "denial kind follows when the
  work happened" — `automode-unavailable` concentrating in `ascend` is the same fact as it
  concentrating in 2026-09. EV-3's Decision section named a temporal-block control as a required
  addition to E7 for precisely this, and it is still unbuilt, so finding #1 carries that confound
  unresolved. Finding #2 is the same observation viewed along the time axis rather than the project
  axis, and the two should not be counted as independent corroboration.
- **The labels were read from a held-out property, not produced by human judgement.** `tool_denial`
  carries six structural properties and no `evidence_text`, so labelling by intent is not available
  on this type. Holding `denial_kind` out of every rule is what keeps the back-test able to fail, but
  this is a supervised-prediction exercise, not the hand-judgement task `asc-3o9` was written for.
- **`automode-blocked` is n=36 in population and n=5 in sample.** Every statement about it is an
  anecdote, and the tooling flagged it as one. Finding #3 is a real negative but a weakly measured one.
- **One of six METHOD steps was not run.** `cluster` was omitted, for the measured reason recorded in
  the pre-registration. This is five-sixths of the stated method.
- **Prior exposure, as disclosed before running:** the `denial_kind` and `tool_name` marginals had
  been seen and EV-3 had been read, which is why P2/P3/P4 are weaker evidence than P1/P5. P2 then
  missed on its mechanism anyway, which is some evidence the exposure did not simply pre-write the
  answers.

**Follow-up filed:** `asc-5x7` (P1) for finding #5 — `asc explore` reports bare counts while
`--backtest` reports Wilson intervals, and `renderProportion` already exists. `asc-80m` (P2) for
finding #4 — EV-18's temp directories ingested as real projects; entries are immutable, so the
options are prevention at ingest or an invalidation annotation, not deletion.

The two blind spots EV-3 named as required additions to E7 remain unbuilt and both bear on this
measurement: the **tautology check** (avoided here by holding `denial_kind` out of every rule
rather than by tooling) and the **temporal-block control** (not avoided — it is the confound in
finding #1, stated above).
