# EV-45: can a transcript file that appears between two ingest runs move an entry's id?

**Question.** `asc-hbxl` opened with two claims about the `#2` suffix the deriver mints for a
repeated per-event key: that it produces *a spurious collision warning on a clean incremental run*,
and that it produces *entry ids that are not stable across runs*. The first spike
(`spike/asc-hbxl-cursor-suffix.mjs`) confirmed the first and refuted the second — but only for an
**unedited** directory, and it left the reason explicit: the suffix is assigned in sweep order, so an
id can move only if that order *changes*. It also measured what decides the order.

Three questions remained, named before anything was run:

1. **Does a newly appeared file change which id an event gets?** A new subagent transcript is the
   realistic caller action; a rename is the other. Neither had been run.
2. **Does a second, suffixed id get written for an event that already has one?** The first spike's
   refutation rests on the colliding write being *refused*. If a sweep can instead mint a suffixed key
   that is still *free*, the event is written twice and the store holds one event under two ids — a
   genuinely different defect from a refused write.
3. **Does the shape of the duplicate matter?** The corpus's documented duplicate (two subagent files,
   one `(sessionId, uuid)`) carries *different* text in the two files. A byte-identical copy is a
   different case and might behave differently.

**Method.** `spike/asc-hbxl-suffix-newfile.mjs`, against the real built binary
(`packages/cli/dist/bin.js`), on throwaway fixtures under `$TMPDIR`. `HOME` **and** `CWD` are both set
to the fixture, so `defaultTranscriptRoot()` resolves inside it and the operator's transcripts are
never read. Each probe ingests fully, changes the directory in exactly one way, ingests again, and
reads the store back **from `entries`** rather than from the command's own report. Seven probes:
four with a duplicate partner file present in run 1, three without.

**Measurement.** 2026-10-09. The count is of store entries whose `evidence_text` equals the holder's
event — a second entry for one event is the damage, and "an id moved" is only one of the ways it
shows up.

| probe | fixture in run 1 | what run 2 changes | event stored | ids added | collision warned |
|---|---|---|---|---|---|
| N1 | A + duplicate partner B | new file copies the event; holder grows | 1× | 1 | yes |
| N2 | A + B | new file copies the event; holder **unchanged** | 1× | 0 | no |
| N3 | A + B | new file, fresh uuid; holder grows | 1× | 2 | no |
| N4 | A + B | ordering flips by **rename**; renamed file grows | 1× | 1 | yes |
| N5 | A alone | new file copies the event (**identical** text); holder grows | **2×** | 2 | no |
| N7 | A alone | new file shares the key with **different** text; holder grows | **2×** | 2 | yes |
| N6 | A alone | new file copies the event; holder **unchanged** | 1× | 0 | no |

Where the defect fires, run 2 exits **0** and the store ends like this (N5, verbatim):

```
  RUN 2 (incremental) exit=0  collision warned: false
      derived:claude-code:user_correction:sess-collide:fresh-uuid-a
        "a later event"
      derived:claude-code:user_correction:sess-collide:shared-uuid-1
        "use approach A"
      derived:claude-code:user_correction:sess-collide:shared-uuid-1#2
        "use approach A"

  entries after run 2 holding "use approach A": 2
  ids added by run 2:   2
```

and its only warning is this one, which is where the corpus's real duplicate was modelled (N7):

```
    | Warning: 1 event key(s) repeated within a transcript and were disambiguated with
    | a "#2" suffix. If a transcript is still growing, one of these may be written
    | again as a new entry on a later run.
```

**The mechanism, stated so it can be falsified.** An id is
`claude-code:<type>:<key>`, and `key` is the type's raw `${sessionId}:${uuid}` with `#n` appended when
the sweep has already issued that raw key for that type (`key` in
`packages/adapter-claude-code/src/derive.ts`; `idFor` in `packages/cli/src/commands/ingest/claude-code.ts`).
A later sweep therefore writes an event a second time exactly when all three hold:

1. **Only one file carried that raw key in run 1**, so `#2` is unoccupied. This is the condition N1
   vs N5 isolates, and it is why N1 stays inert: with B present, run 1 fills `R` *and* `R#2`, so run 2
   can mint only keys that are both already occupied — and both are refused on content.
2. **A file appears between the runs carrying the same `(sessionId, uuid)`, sorting before the
   holder.** The sweep order follows the file name, measured in part one.
3. **The holder also changes**, so the cursor cannot skip it (`unchangedSkips`).

Drop condition 3 and nothing happens (N6); drop condition 2 and nothing happens (N3); keep all three
but break condition 1 and the write is refused (N1, N4).

**Decision.**

- **The bead's id claim is reinstated, in a narrow, fully specified form.** Entry ids are not stable
  across runs when a transcript file appears between them that duplicates an existing event's
  `(sessionId, uuid)` and sorts before the file that holds it. The event is then written a second
  time under `<key>#2` — silently, exit 0 — and the corpus double-counts it. `asc-hbxl` is therefore
  **not** reducible to a warning bug, and any fix owes a compatibility rule for ids already written.
- **The refused-write half stands as part one measured it.** N1 and N4 reproduce the false alarm and
  move nothing; the store's content check refuses the write and the stored entry stands.
- **A second, independent defect is recorded here: the warning misdescribes the mechanism it
  reports.** It says the key was *"repeated within a transcript"*, and in N5/N7 the repetition is
  **across two files** — the sweep is per-project, and `issued` is swept across every file in it. In
  N5 that misleading sentence is the *only* signal the run emits, and it reads as benign.
- **A methodology correction, recorded because it decided the result.** The first four probes were
  written with the duplicate partner present throughout, and N1 — designed to answer question 2
  directly — came back "no duplicate" while the mechanism sat in the arrangement the fixture
  excluded. It was the probe's third variant that exposed it, not the probe designed for it. A
  fixture that supplies a plausible-looking second file can occupy the very slot the defect needs,
  and the first spike states this hazard one file over (*"a test that grew only the convenient file
  would have passed while the mechanism sat there"*). The probes that did not fire are kept in the
  record for that reason, not discarded.

**Follow-up measurement — how far condition 2 actually reaches.** 2026-10-09, same day,
`spike/asc-hbxl-suffix-crossfile.mjs`. The Confidence note below originally said this was unmeasured
and that nothing partitioned the ingest's `keyCollisions`; that was true when it was written and is
not any more, so the number goes here rather than being carried as an open question. The spike
re-derives the whole corpus through one shared deriver — `issued` is not reset per file, so one
deriver across every record is what a `--full` run does — and records which file each derived entry
came from. It reads the corpus where it is and prints only counts; every path and key is redacted to
a short digest.

The question is order-independent even though the suffix is not. `key()` gives the raw key to
whichever entry reaches it first and suffixes the rest, so *which* member of a group is suffixed
depends on sweep order — but *whether* the group is cross-file does not, because at most one member
of a multi-file group can hold the unsuffixed key, whichever it is.

```
re-derived the corpus: 1545 file(s), 939371 record(s)
3056 derived entry/entries, 176 file(s) skipped

raw keys carried by more than one derived entry: 4
  of those, spanning MORE THAN ONE FILE:        4
  of those, repeating WITHIN ONE FILE:          0

the store's own suffixed ids: 24
  re-derived by this sweep, so classifiable:  12
    minted ACROSS files:                       12
    minted WITHIN one file:                   0
  NOT classifiable (the corpus moved since):  12
```

Every repeat, without exception, is across files: 4 of 4 groups in a fresh full sweep, and 12 of 12
of the store's suffixed ids that the sweep can still reproduce. **By the repo's own rule this is an
anecdote, not a rate** — 4 groups is far under `MIN_N`, and 12 stored ids resolve to only a couple of
distinct groups — so it is stated as a count and not as a proportion. What it does establish is the
direction, and it is unanimous: the warning's *"repeated within a transcript"* is not a rare
misattribution, it is wrong for every case this corpus offers. A raw key is `(sessionId, uuid)`, and
one transcript does not repeat its own record uuid; the repeat appears exactly when Claude Code
writes one record into two files, which is the cross-file case by construction.

Two things this does not settle, and they are the natural next questions rather than part of this
record. The store holds **24** suffixed ids while a full sweep today mints **4**, so most were minted
over a corpus that no longer exists — 12 cannot be classified at all — and nothing distinguishes
"corpus has changed" from "an earlier incremental run minted it", which is the distinction that would
say whether the count is drift or damage. And the corpus has grown from the 1,491 entries of
`EV-baseline.md` to 3,056, so every rate quoted from the older record is against a smaller corpus.

**Confidence.** `Confirmed (empirical)` for every row of both tables and for the three-condition
mechanism — each was run against the shipped binary and read back from `entries`. The reach of
condition 2 is measured above, at `n = 4` groups and `12` stored ids, and is reported as an anecdote
under `MIN_N` rather than as a rate.
