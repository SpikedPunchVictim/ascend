# EV-37: does stating a version on every type line close the renumbering hole, and what does the one-time rewrite cost?

**Status**        Measured 2026-09-30 for `asc-i5tj.6` (E12). **The question was named in advance and so
                  were the predictions** — the approved plan's Stage 4 names the regression case, and
                  the two decisions below were taken by the owner before the work started. n = 1
                  corpus (this repository's own `.ascend/` tree); **no real `git merge` was
                  performed**, which is the limitation this record is least able to talk its way out
                  of. **The headline is that the hole is closed by construction rather than by a
                  guard: a reordered tree now reads identically, and the numbering is checked rather
                  than derived — and that the one-time rewrite touched 1 of 22 tree files.**

**Question**      `dogfood/0031` / `asc-i5tj.6`: a `TypeLine` carried no version, so a type's version
                  came from the line's POSITION in `types/NNNN.jsonl`. `.ascend/.gitattributes` is
                  `*.jsonl merge=union`, and a union merge concatenates both sides without asking —
                  so *"no writer may interleave them"* was an invariant no code could enforce. The
                  hole was measured at n=1 before the work: reordering a multi-version type that has
                  **zero** entries across all versions was silently renumbered with exit 0, because
                  an entry's `type_hash` is what catches a renumber everywhere an entry references
                  the moved version. Two questions follow, and only the first is about correctness:

                  1. Does stating `version` on the line, and sorting by it, make a reordered tree read
                     identically — including for a type with no entries at all?
                  2. What does the one-time upgrade of an existing tree cost, and how wide is its
                     blast radius?

**Pre-registered predictions** (from the approved plan, before the work):

- `version` sits **outside** `documentSpec` (`{name, properties}`), so adding it changes **no
  `type_hash`** and invalidates no entry.
- The rewrite rewrites **only** `types/` files; schemes, entries and annotations come back
  byte-identical.
- This tree's numbering will come out `note` v1/v2, `review_finding` v1/v2, `verification_run`
  v1/v2, and v1 for the other eleven names (17 lines, 14 names).
- A version-less type line becomes a hard parse error naming the rewrite; an identical
  `(name, type_hash)` repeat is still ABSORBED rather than renumbered.

## Method

**Every number below is the built binary on the real tree, or `node:sqlite`/the `@ascend/store` build
reading the real files back — not a fixture.** The tree is this repository's own `.ascend/`, already
cut over to itself in `37f7ee3`. `asc` is not on `PATH`, so every invocation is
`node packages/cli/dist/bin.js`, with `dist` rebuilt (`pnpm build`) after the source change.

- The **rewrite was driven first on a copy** at `/tmp/rw-probe/.ascend`, and only then on the real
  tree — the plan's *"verify that, do not assume it"* about the blast radius.
- The blast radius is asserted by **`shasum -a 256` over every `*.jsonl` in the tree before and
  after**, not by reading the diff and judging it.
- The two refusal paths are driven end to end through `asc import` on scratch projects.
- The two mutation checks replace one exact string in a source file, run the **one owning test file**,
  and restore the file from a copy; the restore is checked by `shasum`, not by trusting it.

## Measurement 1 — the hole, before the change (recorded in the plan, 2026-09-30)

Corpus: 17 type lines / 14 names; three names carry two versions each. `grep -c '"version"'` on
`.ascend/types/0001.jsonl` returned `0`.

| Perturbation | Result |
|---|---|
| Reorder a type whose versions **have** entries | **Refused** — both `asc import` and `asc index build` |
| Duplicate an identical line (union of two branches) | **Absorbed** — idempotent by `(name, type_hash)` |
| Replay a non-latest line again, last | **Held** at v1, v2 |
| Reorder a type whose versions have **no entries** | **Silent renumbering, exit 0** |

The hole end-to-end — two `note` lines swapped, no `note` entries:

```
baseline   note v1 = 96880b60e9c7   v2 = 2a540393995c
after swap note v1 = 2a540393995c   v2 = 96880b60e9c7     index build exit 0
```

## Measurement 2 — the rewrite on the real tree

Before: `wc -l < .ascend/types/0001.jsonl` → `17`; `grep -c '"version"'` → `0`; record files → `22`.

```
$ node packages/cli/dist/bin.js store rewrite
file              lines
----------------  -----
types/0001.jsonl  17
Warning: 17 type line(s) now state a version, so index.db no longer describes
the tree. Run `asc index build` before reading anything.
```

**Blast radius, by hash rather than by judgement:** `shasum -a 256` over all 22 `*.jsonl` files
before and after differ on **exactly one path**, `.ascend/types/0001.jsonl`. The other 21 files are
byte-identical. This is the plan's *"the rewrite also re-serializes 6,532 entries, which should be
byte-identical … verify that, do not assume it"* — and it never had to be verified, because the
rewrite never re-serialized them.

Assigned versions, read back from the rewritten file (17 lines):

```
context_compaction v1   decision v1   evidence_record v1   hand_empty v1
note v1   note v2   review_completed v1   review_finding v1   review_finding v2
search_miss v1   skill_activation v1   stage_transition v1   stuck_event v1
tool_denial v1   user_correction v1   verification_run v1   verification_run v2
```

Prediction confirmed exactly, including the three multi-version names.

**Idempotence, through the CLI:**

```
$ node packages/cli/dist/bin.js store rewrite
file  lines
----  -----
$ echo $?
0
```

An empty table and exit 0 — a second run rewrites no bytes, which is the property whoever runs it
depends on.

**The index, rebuilt:** `10455 records`, fingerprint
`7e6b236b0f182a3fc3c249957d721c…22528ac79c08dba7063d14d0d790f`. No `type_hash` changed, so no entry
was invalidated — predicted, and implied by the build replaying every line without a single hash
refusal.

## Measurement 3 — reads, on the real tree

```
$ node packages/cli/dist/bin.js types brief          # 14 lines
$ node packages/cli/dist/bin.js export                # exit 0, 10455 lines
$ node packages/cli/dist/bin.js search decision "version" --limit 2   # exit 0
```

Every exported type line states a version: 17 of 17, none without. The only versions above 1 are
`note v2`, `review_finding v2`, `verification_run v2`.

**Round trip, which is the check that the claim survives the wire:** a scratch project
(`asc init`) imported the real export — `asc import` exit 0, `asc index build` 10459 records — and
every stated version came back: `note v1/v2`, `review_finding v1/v2`, `verification_run v1/v2`, the
rest v1. `asc init` had already seeded four starter types, so the round trip is 21 type lines where
the source had 17; the duplicates are absorbed at replay by `(name, type_hash)`, which is the
pre-existing union-merge tolerance and not a new behaviour.

## Measurement 4 — the two refusal paths, end to end

A type line whose stated number disagrees with the stream:

```
Error: type 'context_compaction' (/tmp/asc-bad-version.jsonl line 1) claims
version 9 with type_hash
34606e3a051a63c4c11738081220950a603d481197e82ac102a6fdeb6cf67059, but the
definitions in this stream register that hash as version 1 -- and this project
held no context_compaction before the restore, so those numbers came from the
stream and this line disagrees with it. Re-export the corpus rather than
editing, filtering or concatenating the file: nothing was written.
```

A type line with no version at all — the owner's second decision, *"refuse it, naming the rewrite"*:

```
Error: /tmp/asc-no-version.jsonl line 1 is a type definition with no version,
and a corpus line always states one. Run `asc store rewrite` once to upgrade
this tree; it assigns each line the version line order gives it today, which is
the rule this field replaces.
```

One rule, no order-dependent fallback. The message names the rewrite, and the rewrite exists.

## Prediction log — one confirmed, one overturned

**Confirmed:** the blast radius, the assigned numbering, the absence of `type_hash` movement, and the
duplicate-absorption behaviour.

**Overturned by measurement:** the approved plan's Stage 2 put the "a stated version must continue the
sequence" check inside `registerType` in `registry.ts`. That placement produced a message that
blamed the caller's well-formed file (*"drop `version` along with `type_hash`"*) when the real
disagreement was with the *target store's* history — and
`packages/cli/test/corpus.test.ts > tells a divergent target apart from a tampered file, because the
repairs differ` went red on it. The check moved to the two call sites that can see both sides:
`import.ts`'s type loop (two-case, splitting on whether the target already held the name) and
`jsonl-index.ts`'s `replayType` (a tree-shaped gap message). `registry.ts` and `replay.ts` are
**net unchanged**. The scheme path already worked this way, so this is the pre-existing precedent
rather than a new design.

## Limitations, plainly

- **n = 1 corpus, and it is the corpus the change was designed against.** This repository's own tree.
  No foreign repository's tree was rewritten or reordered.
- **Nothing here measures the merge itself: no real `git merge` was performed.** Every probe simulated
  the union result by reordering the file, which is what union produces — but the simulation is not
  the merge. `EV-31` and `dogfood/0032` carry the real-git measurements, and they predate this change.
- **The forward/reversed equivalence is now asserted by a test rather than by a probe on the real
  tree.** The owning tests are `jsonl-files.test.ts`'s *"orders type and scheme lines by (name,
  version), so a reordered file reads as an ordered one"* and *"reads a tree whose files hold the
  wrong order as though they held the right one"*, both of which M1 reddens. The plan's Stage 4 asked
  for the zero-entry case specifically; that case is covered by the second of those, which appends v2
  into `0001.jsonl` and v1 into `0002.jsonl` and requires `[first, second]` back.
- **The rewrite reads a tree the reader refuses, and that leniency is exactly one rule**
  (`CorpusParseOptions.allowVersionlessTypeLines`). A second lenient reader would be the defect
  returning; the containment is a design property, not a measured one.
- **A hard refusal breaks reading any pre-change tree until it is rewritten** — including this
  repository's own before this run, and `.ascend-archived/partial-tree-2026-09-30T02-21-23-000Z/`,
  which is under a gitignored directory no command reads and is expected to stay version-less.
- **`asc store rewrite` takes no lock** and must be run on a quiescent checkout; nothing coordinates
  it with a concurrent `asc record`/`asc import`. Stated in the command's own doc; `asc-tyl7` tracks
  the class.

## A defect met on the way, filed rather than folded in

Verification was blocked for a while by a pre-existing false-green in `asc index build`, unrelated to
this change: the build checkpoints the *staging* handle's `-wal` and renames over `index.db`, but
never removes the *replaced* file's `-wal`/`-shm`, so frames a killed-but-committed writer left behind
are recovered onto the new file and restore the old `meta.index_fingerprint`. The build printed the
new fingerprint with exit 0 while the file held the old one, and the read error named `asc index
build` as the remedy — which was a no-op, three further runs in a row. Full measurement, including the
deterministic reproduction, is in `dogfood/0044-2026-09-30-a-build-that-replaces-its-file-and-not-its-wal.md`
and is tracked as `asc-pwv7`. It is **not** caused by this change: the diff to
`packages/store/src/jsonl-index.ts` here is a single 20-line hunk in `replayType`, and `buildIndex`
is byte-identical to `HEAD`. **Since fixed in the working tree** — `buildIndex` now removes the
replaced database's `-wal`/`-shm` before the rename, with the test that failed first and the
end-to-end re-run recorded in that finding.
