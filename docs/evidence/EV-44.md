# EV-44: does every declared analysis question have a field behind it? (`asc-xqf1`)

**Status**        Measured 2026-10-04 across **every type the store holds** — 17 type versions across
                  14 types — read through the real CLI (`asc types show`), never from the source.

                  **The pattern generalizes, and it is not uniform.** Of the **9 declared analysis
                  questions**, **4** are backed directly by a field whose own vocabulary names the
                  answer, **2** are reachable only through a mechanism **outside the type's schema**,
                  and **3** have **no field and no annotation that expresses the answer** —
                  `evidence_record`'s question among them, so the finding this bead was filed from is
                  not an isolated one.

                  A second, distinct defect surfaced: **a question can be dropped between versions and
                  is then invisible**, because `asc types show NAME` reads the latest only — `note` v1
                  declares *"What share of notes should have been another type?"* and `note` v2
                  declares none, while **v1 holds 19 of that type's 22 entries**. The survey by name
                  counts **8** questions; by version, **9**.

                  Pre-registered in `asc-xqf1` before any type was enumerated — three predictions with
                  falsifiers. **One held, one was incomplete, one was refuted.**

**Question**      Named in advance, and recorded in the bead before the measurement was taken:

                  > **SCOPE.** Every type the store holds, not just `evidence_record`. The question:
                  > for each declared `analysis_questions[i]`, does the type carry the data to answer
                  > it?

                  with, as predictions: **P1** the pattern is not unique to `evidence_record`; **P2**
                  the *mechanism* does not exist anywhere and every answerable question is answerable
                  by vocabulary coincidence; **P3** the types where a question is backed are
                  handler-backed ones, because `handlers/check.ts:112` aligns `judged[i]` with
                  `analysis_questions[i]`.

                  The pre-registration also recorded what had already been seen — `evidence_record`'s
                  schema, `guidance.ts:55-64`, `check.ts:112` — and committed to reporting every
                  proportion as an **anecdote** under `MIN_N`.

## Method

Arm **`spike/aq-survey.mjs`**, checked in because the claim is about the **schema** and changes
whenever a type is edited. It reads the types through the real CLI rather than from
`starters.ts`/`derived-types.ts` **because the question is what the store holds** — and that choice is
what surfaced the `note` v1 defect below. It enumerates **every version**, not the latest, and carries
a guard that **refuses to be trusted** if the renderer elides a row (`coverage.has_more`).

**The arm deliberately does not classify.** A script scoring each question by token overlap against
field names would produce a number that looks mechanical and is not. It prints the raw material —
every question, every field with its type — and the classification below is a **reading**, reported as
one, with the field lists printed beside it.

## The classification, as a reading

Three modes, and the middle one was not predicted:

| # | type | question | mode |
|---|---|---|---|
| 1 | `review_completed` v1 | what share end in changes requested? | **DIRECT** — `verdict`'s own enum contains `changes_requested` |
| 2 | `search_miss` v1 | which `failure_mode` dominates? | **DIRECT** — the field is named in the question |
| 3 | `search_miss` v1 | what share were caught `before_acting` vs `after_wrong_claim`? | **DIRECT** — both values are in `caught`'s enum |
| 4 | `stage_transition` v1 | how often does a stage go complete without its tests passing? | **DIRECT** — `to_status` + `tests_passing` |
| 5 | `decision` v1 | which decisions were later reversed? | **OUTSIDE SCHEMA** — no field; expressible only as an invalidation (`--label superseded --superseded-by`) |
| 6 | `decision` v1 | was reversibility marked correctly on the ones that were? | **OUTSIDE SCHEMA** — same path, compared against `reversibility` |
| 7 | `evidence_record` v1 | how often did a result contradict its pre-registered prediction? | **ABSENT** |
| 8 | `note` v1 | what share of notes should have been another type? | **ABSENT** — one free-text field; the answer is a classification of it |
| 9 | `stuck_event` v1 | do stuck events cluster by area of the code, or by kind of error? | **ABSENT** — neither axis is a field |

**DIRECT 4 · OUTSIDE SCHEMA 2 · ABSENT 3.**

**`n = 9`, and `MIN_N` is 20, so every proportion here is an ANECDOTE and is not offered as an
estimate** — by the pre-registration's own commitment. What is *not* anecdotal is the census itself:
this is **all 9 questions the store declares**, not a sample of them, so the counts are exact for this
store as of today. The generalization they do not support is "analysis questions are generally
unanswerable" — a claim about types at large, which n=9 cannot carry.

**The middle mode is the surprise, and it is the one worth carrying.** For `decision`, the answer
exists and is reachable — `asc invalidate --label superseded --superseded-by` records a reversal, and
`asc explore decision --struck` narrows to the struck rows — but it is **not a property of the type**.
It lives in the store's reserved invalidation scheme, which is the mechanism `dogfood/0041` and
`asc-9xi0` were about. So "does the type carry the data?" has a third answer: **the store does, the
type does not**, and a reader asking the question of the schema would conclude it is unanswerable when
it is not.

### The second defect: a question dropped between versions disappears

`note` v1 asks *"What share of notes should have been another type?"*. `note` v2 renames the field
`text` → `body` and **declares no question**. `asc types show note` reads the latest, so the question
is invisible through the surface a reader would use, while **19 of the type's 22 entries sit at v1**
(`select (select count(*) from v_note_v1) as note_v1, (select count(*) from v_note_v2) as note_v2` →
`19 | 3`). Measured: the survey by name counts **8** questions; by version, **9**.

## Predictions against results

- **P1 — "the pattern is not unique to `evidence_record`" — HELD.** Two other versions declare a
  question with no field behind it (`note` v1, `stuck_event` v1), and `decision` v1's two questions
  are reachable only outside the schema.
- **P2 — "the mechanism does not exist anywhere" — HELD on its first half, INCOMPLETE on its second.**
  No type declares a property whose stated purpose is to record its own analysis outcomes: the
  mechanism is genuinely absent. But the second half — *"every question that IS answerable is
  answerable by vocabulary coincidence"* — **named one mode where there are two**. I predicted that a
  backed question must be backed by a field; `decision` is backed by the reserved invalidation scheme
  and by no field at all.
- **P3 — "the types where a question IS backed are handler-backed ones" — REFUTED.** Every
  question-bearing version is a starter or a project-defined type. **All 8 derived versions declare
  zero questions**, so `handlers/check.ts:112`'s `judged[i]` ↔ `analysis_questions[i]` alignment —
  the mechanism I reasoned from — **is used by no type in this store.**

## Instrument notes

Three defects, all found before the numbers above were believed.

- **A field-type column that was a constant.** The first run printed `?` for all 40 field types:
  the script read `name`/`type` off the row's `value` (the rendered sentence) instead of off the row
  itself. A column that looks like data and is one repeated character — the same class as EV-40's
  `[type="submit"]` and EV-42's `cherry-pick -q`.
- **The latest-version blind spot.** `asc types show NAME` reads the latest version, so the survey by
  name silently loses `note` v1's question. Caught by counting the type lines in
  `.ascend/types/0001.jsonl` (17) against the CLI's types (14) and asking why they differed.
- **Elision.** `types show` elides rows past a row budget, so a type with many fields could lose a
  question or a field in silence. The arm now reads `coverage.has_more` and **exits 1** rather than
  reporting. Measured on this run: **0 elided**, so the guard passed rather than being untested.

## Decision

**The finding stands, at full width: 3 of 9 declared analysis questions have no field and no
annotation that expresses their answer, and a 4th pair is reachable only outside the type.**

What follows, stated as the options rather than a chosen remedy, because the choice belongs to the
owner and the count is an anecdote:

- **Bind a question to its answer at registration.** The reason the gap exists is that
  `analysis_questions` is free text validated only for non-emptiness (`guidance.ts:55-64`): nothing
  requires a field to exist. A registration refusing a question with no field behind it would make the
  class impossible rather than merely visible — the same move `jsonl.ts` makes for a reasonless
  invalidation (E12.6), and it is the option the `arms` property already argues for in its own words.
- **Or declare the questions decorative and remove them**, which is honest and costs nothing.
- **The `note` case is separable and needs its own answer**: a version that drops a question should
  say so, because `asc types show` cannot. At minimum the latest-version view should disclose that an
  older version declared one.

`asc-xqf1` stays **open** for that choice. `dogfood/0060` carries the original single-type finding and
scoped itself to one type; **this record is the census that extends it**, and 0060 is not wrong — it
said plainly that only one type had been checked.

## Confidence

**High that the counts are a census** of this store on 2026-10-04: every version was read through the
real CLI, the elision guard passed with 0 rows elided, and the population was reconciled two ways (14
types by name, 17 versions on disk, 9 questions against 8).

**Medium on the classification, and the judgement calls are the ABSENT row.** `stuck_event` is the
weakest: *"kind of error"* is arguably readable from `error_text`, and I judged it not backed because
there is no **categorical axis** to cluster on — a reader could reasonably disagree, and the fields are
printed above so they can. The DIRECT row is not a judgement: each question names its field's own
vocabulary, verbatim.

**Low on any generalization beyond this store.** `n = 9` is an anecdote, and this is one project's
types — which is exactly the `MIN_N` discipline the pre-registration committed to, and the same
discipline that stopped a claim about this series' predictions from being filed earlier the same day.
