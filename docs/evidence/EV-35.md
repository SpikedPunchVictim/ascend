# EV-35: does a producer run against a stale index mint a wrong line?

**Status**        Measured 2026-09-29 for `asc-i5tj.4.1` (E12.4b3). **The question was named in
                  advance and the answer was predicted numerically before the first run** — the
                  throwaway spike asserted `staleVersion === 2` and `currentVersion === 3`, and both
                  held. n=1: one scheme, one store, one kind of the five. **The headline is that the
                  claim the store package documents — "a producer is usable against a STALE index, and
                  that is the point" — is false: the stale probe minted a second version 2 with a
                  different spec, in a `merge=union` file, where it is permanent.**

**Question**      `line-producers.ts:27-32` states it as a design property: *"A producer is usable
                  against a STALE index, and that is the point. A checkout, a merge or a hand edit
                  leaves the index describing a tree that has moved, and the product cannot respond by
                  refusing every `asc record` until someone rebuilds … So the probe writes to whatever
                  index is there and rolls it back, and `writeLines` decides separately whether that
                  index is current enough to maintain."* That argument is about whether the **index**
                  can be maintained. It says nothing about whether the **line** is correct. If the
                  line is computed from an index that does not describe the tree, the write path may
                  not produce against a stale index at all — and `asc-i5tj.4.1` (b3) is the change that
                  would have shipped that, because before it no production path had a caller.

## Method

A throwaway vitest spike in the store package (`packages/store/test/zz-throwaway-stale-probe.test.ts`,
run once and deleted — it is quarantined on purpose, not a foundation). One scheme, `screening`, and
three specs that differ only in their label list, so the version a registration mints is the whole
measurement:

1. An empty tree, and an index built for it with `buildIndex`. **The index is opened writable**
   (`openStore` on `index.db`), because `produceLines` runs the real writer and rolls back — this is
   the same handle b3 needs, and `openIndex` cannot supply it (it is read-only).
2. `produceLines` registers `screening` v1 and `writeLines` writes it, so tree and index agree.
3. `produceLines` registers `screening` v2 **against the current index**, and then the line is
   appended to the **TREE ONLY**, through `openRecordWriter`. This is exactly the state a checkout, a
   merge or a hand edit leaves: the tree holds v1 and v2, the index holds v1, and the next honest
   registration is **v3**.
4. The measurement: `produceLines` registers a third spec against the now-stale index, and reports the
   version it computed.
5. The control: `buildIndex` again so the index is current, and the same registration is asked once
   more.

## Results

The spike's own output, verbatim:

```
=== SPIKE: producing against a stale index ===
tree holds            : scheme 'screening' v1, v2
index (stale) holds   : scheme 'screening' v1
produced (stale)      : version 2   spec labels ["maybe","no","unclear","yes"]
produced (current)    : version 3
honest next version   : 3
```

Both pre-registered expectations held: `produced (current) = 3`, and `produced (stale) = 2`.

The stale probe is wrong in the way that does not announce itself. It does not fail, and it does not
return a line the store would reject — it returns a **well-formed scheme line claiming version 2**,
which the tree already holds, carrying a spec the tree's version 2 does not. The label arrays differ
because the two lines are two different specs under one version number; the ordering
(`["maybe","no","unclear","yes"]`) is the store's own canonicalization, not a defect.

## What the numbers decide

**Producing requires a current index.** This is the change to the design: *"build, then write"* is not
a convenience or an invariant-preserving nicety, it is a requirement for the **content** of the lines.
A probe against a stale index does not produce "lines the index cannot maintain" — it produces lines
the **tree** cannot accept.

Concretely, for `asc-i5tj.4.1`:

- **`writeLines`' `stale: true` outcome is unsound for a fused produce-and-write path**, and this is
  the measured reason, not a preference. Appending the tree and leaving the index alone is defensible
  when a caller hands over lines it already had; it is not defensible when the caller *computed those
  lines from the index that was stale*. So the fused function refuses rather than appends.
- **The currency check must be inside the write lock**, because it is a check-then-act: the answer read
  before `BEGIN IMMEDIATE` describes a moment that a concurrent writer can invalidate. That is the same
  placement `annotate.ts` already argues for `nextSpec` (asc-q4p), for the same reason.
- **`line-producers.ts:27-32` is wrong as written** and must be corrected in the same change. It is a
  paragraph that reasons carefully about the wrong object: it asks whether the index can be maintained
  and never asks whether the line is true. Leaving it would re-justify the defect to the next reader —
  which is worse than the defect, because the defect is caught by a refusal and the paragraph is not.
- **The five producers are not all alike here, and only one of them was measured.** `schemeLines` was
  chosen because a version number is visible in its output. `entryLines` against a stale index is
  expected to *refuse* (`UnknownTypeError`, or the wrong version for a name whose versions the tree
  grew) rather than to mint a silent duplicate — a different failure mode, and **unmeasured**.

## What this does NOT measure — and where it is still weakest

- **n=1, and one kind of five.** One scheme name, three specs, one store, `schemeLines` only. The
  generalization to `entryLines`, `typeLines`, `annotationLines` and `invalidationLines` is an
  inference from the mechanism (each reads the index to decide what to write) and not a measurement.
  `entryLines` is the one worth measuring next, because its stale failure is expected to be a refusal
  and a refusal is a *different* argument from a wrong line.
- **No rate.** How often a stale index is actually met — after a checkout, a merge, a hand edit — is
  not measured here and is not claimed. One occurrence in a spike is an anecdote.
- **It says nothing about the build/write race it exposes.** `buildIndex` publishes by `renameSync` and
  takes no lock, while a writer holds a transaction on the file being replaced. A build concurrent
  with a write can therefore publish an index whose fingerprint describes a tree that already contains
  the writer's lines, while its replay does not — a false-green, and the severity-zero class. That is
  a separate defect with its own bead; this record establishes only that "build, then write" is now on
  the hot path, which is what makes it reachable.
- **The spike is deleted.** The numbers above are the artifact; the file is not, and is not a
  regression test. What replaces it is a test in the landing change that the fused path refuses a
  stale index — a refusal, which is the decision, rather than the version number, which is the
  evidence.
