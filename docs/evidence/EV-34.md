# EV-34: does this repo's own corpus survive the JSONL tree, and what does the corpus format have no way to carry?

**Status**        Measured 2026-09-29 for `asc-i5tj.4` (E12.4, the cutover). **The question was named
                  in advance** — both halves were written into `spike/e12-migrate.mjs`'s own doc
                  comment before the first run — but **no numeric prediction was registered**, so this
                  is a measurement and not a test of a hypothesis. n=1: this repository's own store,
                  which is the corpus the migration exists for. **The headline is that the corpus
                  migrates faithfully on every row the format defines — and that two pieces of store
                  state have no representation in the format at all: 1,070 `ingest_cursor` rows, and
                  the `ingest.applied_handlers` ledger.**

**Question**      E12.4 archives the SQLite store it migrates away from, so a record the tree cannot
                  carry is not a defect that can be fixed later — it is gone. The equivalence check
                  that exists (`packages/cli/test/import-vs-index.test.ts`) drives both replay drivers
                  over a **9-line hand-written fixture**, and a fixture cannot answer this question for
                  a corpus with 17 types, 7 schemes including the reserved `invalidation` one, 3,141
                  invalidations, and scheme names (`hand-denial`, `rule-denial`) that `asc-i5tj.5` is
                  still open about. So: (a) does the real corpus survive `export → tree → index` with
                  every observable row equal, and (b) what does the source store hold that the four
                  line kinds have no way to express?

## Method

**The live store is only ever opened read-only.** The tree is written to a scratch directory, so
nothing here can damage the thing being measured — which matters, because the answer decides whether
the migration is safe to run for real.

- **Export through the real command** (`asc export` as a subprocess), then parsed with `parseCorpus`
  — the codec the tree layout itself uses. `JSON.parse` over the lines is the mistake EV-33 records
  making: a `TypeLine` is NESTED in memory and FLAT on the wire.
- **The tree is laid out by `openRecordWriter` + `writeGitattributes`**, the same layer a real write
  will use, and then read back with `readRecordTree` and compared line-for-line by serialized text.
  That is a check on the codec being the identity, separate from the check on the rows.
- **`buildIndex` replays the tree**, and the result is compared to the source with the same
  canonical dump `import-vs-index.test.ts` uses: `SELECT *`, keys sorted, `entry_types.created_at`
  dropped **by name** (it comes from the caller, not from any `TypeLine`, so a build stamps its own
  moment).
- **Invalidations are checked twice, and the second check is the one that matters.** The corpus format
  has no invalidation kind — an invalidation rides as a scheme line plus an annotation — so a
  comparison over kinds is green by construction for it. It is therefore checked as annotation rows
  *and* per entry through `listInvalidations()`, which is what "still striking the same entries" means.
- **Search parity is by `entry_id`**, for the reason recorded under the false readings below.

## What the numbers decide

**1. The format carries this corpus faithfully, and that is checkable rather than arguable.** 10,316
lines out, 10,316 read back, **0 lost and 0 gained**. Every observable row of all four kinds equal.
**3,141 invalidations** equal as rows *and* equal one-by-one through `listInvalidations()`, which is
the stronger check the format's own shape forces. Five search probes returning **identical `entry_id`
sets**. So E12.4's migration is buildable on the existing `asc export` path with **no format change**,
and the hand-written 9-line fixture was not hiding a real-corpus divergence.

**2. The whole migration costs ~4.65 s** at this store's 6,404 entries: export 0.78 s + tree write
0.48 s + index build 3.39 s. The tree write is **negligible** (0.48 s for 7.85 MB into 22 files), and
the cost is the same `buildIndex` EV-33 timed — 3.39 s here against EV-33's 2.97 s median at 6,387
entries, consistent within EV-33's own stated ±15% for single wall-clock readings. A migration is
therefore a one-off cost of seconds at this size and scales with the index build, not with the layout.

**3. Two things have NO representation in the format, and both are absent rather than wrong.**
`ingest_cursor` is **1,070 rows in the store and 0 in the index** — the table exists because
`migrate()` creates it, and nothing ever populates it, which is exactly why a check that asked "does
the index have this table" would have reported `carried` for the one table that is not. And of the
store's three `meta` keys, two are dropped: `created_by_ascend_version` and
**`ingest.applied_handlers`** — the latter being the ledger of which handler YAMLs `asc ingest` has
already applied. Filed as `asc-i5tj.14`.

**4. `entries_fts_data` and `entries_fts_idx` differ by one row each (70→69, 68→67) and are excluded
by name with the reason.** They are FTS5's b-tree segment tables, holding allocator state rather than
documents, so a row count there compares the insertion sequence and not the corpus. The check that can
fail for a real reason is document parity, which is by `entry_id` and passes on all five probes.
Excluding them silently would be the mistake; excluding them with the measurement that says why is not.

**5. The two false readings this instrument produced before it was correct — recorded because a false
DIFFERS is the mirror of the false green.** Both were mine, both cost a re-run each, and both would
have sent a migration plan chasing a defect that does not exist:
- **Comparing `entries_fts.rowid`** reported **five probes as DIFFERS with identical hit counts**.
  `entries_fts` is a standalone `fts5(evidence_text, entry_id UNINDEXED, tokenize='trigram')` — not
  `content='entries'` — so its rowid is its own, assigned in insertion order. The link to an entry is
  the `entry_id` **column**.
- **Joining through `entries.rowid`** was wrong for the same reason one level down: `entries` assigns
  rowids in insertion order too, and the two stores insert in different orders (the store in recorded
  order, the index in the tree's `(timestamp, id, serialized)` order), so two identical corpora
  produce different rowids by construction.

  A check that invents a difference between two identical things is as corrosive as one that hides a
  real one, and this one is silent in the direction people do not look: it fails loudly, so it gets
  "fixed" by weakening the check rather than by fixing the comparison.

## What this does NOT measure — and where it is still weakest

- **n=1, and it is the corpus the migration is FOR.** A foreign project's store would be the honest
  n=2, and it is the case that matters: the export format is what a foreign store has to be
  expressible in. Not measured. (This is the home-field validation the project's own method warns
  about, and it is stated rather than papered over.)
- **Only the export/read direction. Nothing here writes to the tree from a command.** `openRecordWriter`
  has **no production caller**, so this exercises the writer as a library — not `asc record` as a user
  runs it, with its validation, its `--na` rules and its refusals. The write path is unproven.
- **The `ingest_cursor` gap is identified, not resolved.** Whether the cursor state can be
  reconstructed from the tree (a derived entry carries its transcript's session id) is a separate
  question and is not answered here. What is measured is that it is 1,070 rows and that the format
  cannot express them.
- **Nothing was checked about a tree that has been through a git merge.** `merge=union` reordering and
  the duplicate-line question are E12.1's subject (`dogfood/0032`, `asc-i5tj.7`) and were not
  re-measured.
- **Timings are one run each on a warm page cache**, with EV-33's same-machine caveat: the 1.6× drift
  EV-33 measured between two days on identical code means a cross-day comparison of these numbers is
  not usable.
