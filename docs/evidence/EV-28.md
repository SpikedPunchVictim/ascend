# EV-28: how much of a seeded defect set does a reviewer find, per lens class?

**Status**      Measured 2026-09-27 for `asc-gtnu.8`. **24 of 24 planned reviewer runs completed, 0
                failed, 0 discarded**, $11.7667 of a $40 ceiling. The predictions were frozen in the
                bead before any measurement and are copied verbatim below; the apparatus was sealed by
                sha256 before the first review (`spike/recall/PREREG.md`). **Two of five predictions
                are falsified, one is unresolvable, one lands between its thresholds, and the one that
                holds is the one registered as a caveat against the design.** Four of the nine lens
                classes were measured, and one of the four is a small group (n=11).

**Question**    For `asc-gtnu`, need (4): per lens class, what fraction of known defects does a
                reviewer report through `ReportFindings`? Plus `asc-gtnu.7`'s direction question: does
                the implementer edit a finding concerns precede the finding, and in which stream?

## Method

Everything named here is in `spike/recall/`, and the seal lines are in the `asc-gtnu.8` notes.

- **Subject.** `packages/core/src/handler.ts`, and nothing else is seeded. **81 seeds**
  (`seeds.json`): `boundary_conditions` 25, `error_paths` 25, `cross_implementation_divergence` 20,
  `time_concurrency` 11. Each seed is a line edit, and the edits in one class are at least 7 lines
  apart. For each seed alone, `seeds.mjs --check` measured whether it compiles (81 of 81 do) and
  whether it fails the committed `handler.test.ts` (35 of 81 do: bc 9, ep 9, ci 7, tc 10). The
  control edit changed a comment and broke nothing.
- **Trees.** Each run gets a fresh allowlist slice of the repo under the OS temp root, with a
  neutral name (`rv-XXXXXX`), one git commit, and one class's seeds applied. The npm cache is empty
  and npm runs offline.
- **Arms.**
  - A: the test runner is installed.
  - B: the runner is removed, and the tests stay readable.
  - C: no seeds applied, the same tree as A.
- **Runs.** 4 classes × 2 models (`claude-sonnet-5`, `claude-opus-5-5`) × 3 arms = 24 headless
  `claude -p` sessions. Every session gets the same brief (`brief.md`), which names the nine lenses
  and `ReportFindings`. The pilot was an arm-C Sonnet run on the sealed apparatus. It filled the
  `boundary_conditions` C-Sonnet slot, as PREREG section 4 fixed in advance.
- **Scoring.** `score.mjs` ingests the transcripts into a fresh scratch store with
  `asc ingest claude-code` and reads the `review_finding` entries back. A seed counts as found when
  some finding in its run names `handler.ts` within R=3 lines of the seed. If the finding has no
  line, the seed's distinguishing token must appear in its text instead. The lens `category` is not
  used in scoring.

## Predictions (verbatim from the bead, frozen before any measurement)

1. **Recall is under 50% in at least 4 of the 9 lens classes.** At n=25 seeds per class, a class
   whose observed recall is below 0.50 has an upper 95% Wilson bound below 0.70. Falsified if 6 or
   more classes land at or above 0.50.
2. **`boundary_conditions` has the highest recall of the nine; `time_concurrency` and
   `cross_implementation_divergence` are the lowest two.** Falsified if `boundary_conditions` is not
   the maximum, or if neither of the other two is in the bottom two.
3. **A seeded defect that fails a committed test is found far more often than one that does not.**
   Predicted gap: at least 0.30 in absolute recall. Rationale, and it is the mechanism this bead
   suspects: a reviewer can run the suite, so a test-breaking defect is handed to it, while a defect
   the suite does not cover must be found by reading. Falsified if the gap is under 0.15.
4. **Two reviewers on the same seeds overlap far less than they agree with the truth.** Predicted
   Jaccard on the FOUND sets: under 0.40, consistent with the 2-of-12 anecdote (Jaccard 0.09).
   Falsified if the two models' found-sets overlap at Jaccard 0.40 or more.
5. **Seeding changes the reviewer's reporting rate, not only its recall.** Predicted: reviews over a
   seeded repo report MORE findings per run than reviews of the same repo unseeded, because seeded
   defects are findable and a findable defect invites more searching. Falsified if the seeded arm's
   findings-per-run is not higher.

PREREG section 2 restricted P1 and P2 to the four measured classes **before any run**. P1 is read
as "k of 4 under 0.50", which cannot confirm the prediction. P2 is read among those four.

## Result

All blocks below are `score.mjs` output, pasted exactly (`spike/tmp/recall/score.txt`, not
committed). No home paths appear in them, so nothing is redacted.

### Integrity

```
runs completed=24 failed=0 total spent=$11.7667
```

Checks made on every run:

- **Stored findings match the stream.** The store's count equals the count of `ReportFindings`
  elements in the raw stream in all 24 runs.
- **No git use.** No run used git (`git=0`).
- **The runner was almost never used.** `runnerRan=true` in exactly one run,
  `A-boundary_conditions-claude-opus-5-5`, and in no arm-B run.
- **Nothing outside the tree was read.** Two runs have `outside=2`. In both, the reviewer re-read
  its own persisted tool-result files under the harness's `~/.claude/projects/` directory for its
  `rv-` tree. That is not the repository.
- **Denials.** 19 runs had exactly one permission denial, and 5 had none. The denials are compound
  `cd … && grep` reads, plus one attempted write.

### Prediction 3 — test-breaking versus not

```
arm A: breaking 84.3% (95% CI 74.0-91.0%, n=70) | not 56.5% (95% CI 46.3-66.2%, n=92) | gap 0.278 | chi2 14.206 perm p=0.0001
arm B: breaking 87.1% (95% CI 77.3-93.1%, n=70) | not 59.8% (95% CI 49.6-69.2%, n=92) | gap 0.274 | chi2 14.636 perm p=0.0003
```

**P3: the gap is 0.278, between the 0.15 falsifier and the 0.30 prediction, so the prediction is
neither confirmed nor falsified. The mechanism it names is contradicted.** P3 said the gap exists
because a reviewer runs the suite. The suite was run in 1 of 8 arm-A runs, and arm B, which cannot
run it, shows the same gap (0.274). Whatever makes a test-breaking seed easier to find, running
the test is not it. See post-hoc 3 for what it might be.

**P4: falsified.** The pooled Jaccard of 0.762 is nearly twice the 0.40 threshold, and every class

### Prediction 5 — findings per run

```
claude-sonnet-5  seeded n=8 mean=14.75 [15,19,15,19,14,12,14,10] | unseeded n=4 mean=9.00 [12,10,6,8]
claude-opus-5-5  seeded n=8 mean=19.13 [22,22,18,18,15,14,14,30] | unseeded n=4 mean=8.75 [9,7,9,10]
```

**P5: holds for both models.** Seeded runs report 1.6× (Sonnet) and 2.2× (Opus) as many findings as
unseeded ones. PREREG registered this outcome as a caveat against the design: seeding changes how
much a reviewer reports as well as whether it finds a defect. The recall above is recall under
that changed behaviour.

### Scorer against hand labels

```
## Scorer vs hand, n=40: agreement 0.975, Cohen's kappa 0.844
```

I labelled the 40 sampled findings by hand from their summaries and the seed rationales, before
seeing any per-finding scorer label. There was one disagreement, sample 11. It is a
`cross_implementation_divergence` finding at line 383 that describes seed ci02 (line 379) by
naming the sibling line: `eq` and `ne` disagree when both operands are absent. The scorer missed
it because 383 is 4 lines from 379 and R is 3. **The one disagreement is a scorer false negative.
The scorer does not credit findings by proximity alone in this sample. If anything it
undercounts.**

### Post-hoc — NOT pre-registered

These three checks were written after scoring, in `spike/recall/posthoc.mjs`, to test the scorer
and P3. None of them changes a reading above.

**1. The chance-hit rate.** Each unseeded arm-C run was scored against every class's seed lines,
using the same R=3 rule. The code at those lines is correct in an unseeded tree, so any "hit" is a
finding that happens to sit near a planted spot. Across the 8 runs, 32 cells, the rates range from
**4.0% to 20.0%** (per-cell n = 11–25). Example lines:

```
pilot-claude-sonnet-5                    findings=12  boun 16.0% (95% CI 6.4-34.7%, n=25)  erro 12.0% (95% CI 4.2-30.0%, n=25)  cros 20.0% (95% CI 8.1-41.6%, n=20)  time 9.1% (95% CI 1.6-37.7%, n=11)
C-time_concurrency-claude-opus-5-5       findings=10  boun 20.0% (95% CI 8.9-39.1%, n=25)  erro 8.0% (95% CI 2.2-25.0%, n=25)  cros 15.0% (95% CI 5.2-36.0%, n=20)  time 18.2% (95% CI 5.1-47.7%, n=11)
```

Arm-C runs report about 9 findings each. A seeded run reports 15–19, so its chance floor is
plausibly higher than this. Every recall cell (50–100%) is well above a 4–20% floor, but the floor
is not zero. Read each recall as an upper bound, loose by up to roughly that much.

**2. Seeded-run findings that hit no seed of their class.**

```
all seeded runs: 11.4% (95% CI 8.2-15.8%, n=271)
```

That is 31 of 271. The rate is highest in `time_concurrency`, at 26.7–42.9% in three of its four
runs. Given a seeded tree, reviewers reported almost nothing but the seeds. A seeded tree is
therefore a poor instrument for finding real latent defects, and the recall here is not recall on
unseeded code.

**3. The P3 gap within each class.** 10 of the 11 `time_concurrency` seeds break a test, and that
class has the highest recall. So the pooled gap could come from class membership alone.

```
A boundary_conditions              breaking 66.7% (95% CI 43.7-83.7%, n=18) | not 75.0% (95% CI 57.9-86.7%, n=32)
A error_paths                      breaking 100.0% (95% CI 82.4-100.0%, n=18) | not 46.9% (95% CI 30.9-63.6%, n=32)
A cross_implementation_divergence  breaking 85.7% (95% CI 60.1-96.0%, n=14) | not 50.0% (95% CI 32.1-67.9%, n=26)
A time_concurrency                 breaking 85.0% (95% CI 64.0-94.8%, n=20) | not 0.0% (95% CI 0.0-65.8%, n=2)
B boundary_conditions              breaking 77.8% (95% CI 54.8-91.0%, n=18) | not 78.1% (95% CI 61.2-89.0%, n=32)
B error_paths                      breaking 100.0% (95% CI 82.4-100.0%, n=18) | not 53.1% (95% CI 36.4-69.1%, n=32)
B cross_implementation_divergence  breaking 78.6% (95% CI 52.4-92.4%, n=14) | not 42.3% (95% CI 25.5-61.1%, n=26)
B time_concurrency                 breaking 90.0% (95% CI 69.9-97.2%, n=20) | not 100.0% (95% CI 34.2-100.0%, n=2)
```

The gap is not a `time_concurrency` artifact:

- **`error_paths` and `cross_implementation_divergence` carry it**, at +36 to +53 points, in both
  arms.
- **`boundary_conditions` shows none.**
- **Most of the not-breaking error_paths seeds are silent acceptances.** ep03, ep04 and ep06–ep10
  each make a malformed condition "accepted", and it then silently never (or always) matches. So in that class, "breaks a committed test" and "changes behaviour
  a reader can see" plausibly pick out the same seeds.

This is a hypothesis for the gap, not a measurement of it.

## Limits

- **Four of nine classes were measured, and `time_concurrency` has 11 seeds.** Every statement
  about that class is an anecdote under `MIN_N` = 20, and P2's falsification rests on it.
- **The effective n is smaller than the CIs imply.** A cell's seeds share one reviewer session, and
  P3 pools seed-runs across sessions. Wilson intervals and the permutation null both treat
  seed-runs as independent, so they are too narrow. The P3 permutation p-values in particular
  overstate the evidence.
- **This is recall given a brief that names the lenses and the tool.** It is not recall of the
  route `CLAUDE.md` describes. That route never names `ReportFindings`, and reviewers following it
  write prose (`dogfood/0019`). It is also recall on one file of 1,312 lines, with one class's
  seeds per tree.
- **Some seeds may be equivalent mutants.** 46 of 81 seeds break no committed test, and I did not
  prove each of those changes observable behaviour. A seed that changes nothing cannot be found, so
  any equivalent mutant lowers recall. Seeds written with "silently never true" rationales were
  meant to avoid this, but that is not checked.
- **One pilot, one operator, one machine, one day.** The two models are single runs per cell, with
  no replicates in arms A and B.
- **The P3 mechanism test is weak.** The runner was used once, so arm A barely differs from arm B in
  practice. The arms compare the availability of a runner, not its use.

## Decision

**Per-class recall for a briefed reviewer is 50–100% on seeded defects, above the 4–20% chance
floor, and the scorer agrees with hand labels at κ = 0.844.** That settles need (4) for these four
classes. Recall is not the weak point the bead suspected (P1). The two models largely agree on
which seeds they find (P4). The larger effects are elsewhere:

- `cross_implementation_divergence` is the weakest class in every cell.
- Whether a seed breaks a committed test predicts finding it, and running the test is not why.
- Seeding roughly doubles how much a reviewer reports (P5).

**The `asc-gtnu.7` direction question is not answered, because this design cannot answer it.**

- Every reviewed tree is one commit with no implementer, so there is no implementer edit whose
  distance from a finding could be measured.
- `asc-gtnu.8` was the wrong bead to own that test. The bead said so in its deliverables, and the
  design never had a place for it.
- `asc-gtnu.7` stays open. Its reopen condition becomes "a session in which a reviewer reports on
  an implementer's live edits". It stays unbuilt for the reason it already gives.

**`asc-gtnu.13`** (a checklist drawn from the other model's finding classes) is unblocked by this
record. It is also weakened: with found-set Jaccard 0.762, the other model's classes are mostly
your own.
