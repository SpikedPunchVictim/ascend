# EV-47: can `install-hook` put `asc` on a session's PATH?

**Question.** Nothing links an `asc` binary onto `PATH` — README §Install says so in as many words —
so every artifact that shows a bare `asc` command depends on a shell alias the reader has to define.
`dogfood/0050` is that cost made concrete, and `dogfood/0028` is why the recording route is shaped
the way it is: *the hook script cannot spell the bare form either*.

`asc-zser` names one candidate mechanism: **`CLAUDE_ENV_FILE`**, a file Claude Code runs as a shell
script before each Bash command, so `export PATH="/x:$PATH"` really expands — unlike `settings.json`'s
`env` block, whose values are literal and where a `PATH` value *replaces* the inherited one. The bead
was filed separately from `asc-uftd`/`asc-l38f` because this changes what `install-hook` writes **and
touches a file outside the project**, so it needs its own measurement. Three questions were
pre-registered, and none of them is answerable by reading `install-hook.ts`:

1. Does `CLAUDE_ENV_FILE` **exist on a stock install** — a variable Claude Code sets, or one the user
   must configure first?
2. Is a write to it **honoured in the same session that writes it**? If the file is read *before*
   hooks run, a hook's write lands only on the next session and the feature is worth much less.
3. What happens **when it is absent**? A hook that writes to an unset path unguarded must not turn
   every session start into an error.

Predictions P1–P5 and the decision rule were written to `spike/env-file/PREREG.md` **before any
treatment run**, deliberately in parallel with the documentation research so that a doc claim
contradicting a prediction would be a finding rather than a reason to adjust one.

**Method.** 2026-10-09, this checkout, macOS, 12 cores. Throwaway probe at `spike/env-file/probe.mjs`
(`spike/tmp/` is gitignored). One ephemeral project per rep, **two sessions each**, a fresh
`--session-id` apiece: 4 reps × 2 arms = 8 projects, **16 sessions**, Haiku 4.5, ≈$1.92 total.

Each project holds a `bin/asc` that prints `MARKER-OK` — a command named `asc` that exists *only* on
the project's own `bin/`. A `SessionStart` hook consumes its JSON stdin, logs whether
`$CLAUDE_ENV_FILE` is set and whether it lives inside or outside the project (**never the value
itself**), and in the **write** arm appends `export PATH="<project>/bin:$PATH"` to it. The **control**
arm differs by exactly that write and nothing else.

Each session then runs one Bash command and reports what it prints:

```
echo "$PATH"
```

The verdict is read off the shell's **result** text — `yes` iff it contains the rep's own absolute
`bin/` directory — never off the command text, which contains the literal the model typed. A denial
is its own verdict, so a refused command can never be read as a marker that is genuinely absent.

## Measurement 1 — the three questions, and all five predictions hold

| arm | session 1 sees `asc` | session 2 sees `asc` | hook logged | cost |
|---|---|---|---|---|
| **write** | **4/4** | **4/4** | `set where=outside-project base=sessionstart-hook-2.sh` | $0.904 |
| **control** | **0/4** | **0/4** | `set where=outside-project base=sessionstart-hook-2.sh` | $1.017 |

- **P1 — confirmed.** `CLAUDE_ENV_FILE` is **set** for a `SessionStart` hook on this stock install, in
  **8/8** rep-pairs. The user does not configure it.
- **P2 — confirmed.** The path it names is **outside the project**, in **8/8**, basename
  `sessionstart-hook-2.sh` — the per-session `~/.claude/session-env/<session id>/` layout the
  documentation research independently reported and the official docs do not describe.
- **P3 — confirmed, and this is the load-bearing one.** The `write` arm resolves `asc` in the **same
  session** that the hook wrote it, **4/4**; the control arm resolves it **0/4**, differing only by
  the write. The attribution is therefore clean.
- **P4 — confirmed.** The control arm resolves `asc` in neither session, so a positive in the write
  arm is attributable to the write and not to something already on `PATH`.
- **P5 — confirmed.** Session 2 resolves it **4/4** as well, so the mechanism is not one-shot.

**Every session ran exactly one command.** All 16 emitted `echo "$PATH"` and nothing else, so no
positive can be a session that went off-script.

**Corroboration.** The documentation research (parallel, not consulted before the predictions) reads
the same way: the hooks reference says to write `export` statements to `CLAUDE_ENV_FILE` and its own
worked example appends a `PATH` entry; the hooks guide says Claude Code *"runs as a script preamble
before each Bash command"*, which is precisely the same-session ordering P3 predicts. The official
example guards with `if [ -n "$CLAUDE_ENV_FILE" ]`, which is evidence the variable can be unset —
question 3, below.

## Measurement 2 — the absent case

Not a live arm: whether an unguarded write to an unset path errors is a fact about `sh`, tested
directly rather than inferred from a session.

| write | stderr | exit |
|---|---|---|
| unguarded, `CLAUDE_ENV_FILE` unset | `sh: : No such file or directory` | **1** |
| guarded by `[ -n "$CLAUDE_ENV_FILE" ]` | — | **0** |

**An unguarded append turns session start into a failing hook with a shell error on stderr.** The
guard is not defensive style here; it is the difference between a hook that works and one that
reports a failure on every start.

## Decision

**P3 holds, so the mechanism is real and `asc-zser` is buildable as designed** — that branch of the
fixed decision rule, and no branch was moved after the numbers arrived. `install-hook` can write a
`PATH` export into `CLAUDE_ENV_FILE` at `SessionStart`, and **the first session after the install
sees a bare `asc` in its own shell**, which is the property the feature needs. The question this
record closes is whether the mechanism exists; it is not a measurement question any more.

What remains is **what to install**, and this record does not decide it:

- the checkout's own built entry point, resolved relative to the running binary the way
  `.claude/ascend-hook.sh` already is, so the script stays free of this checkout's absolute paths; or
- a shim, which would survive the binary moving but is a second thing to keep current; and
- what the write must **not** do to a `CLAUDE_ENV_FILE` the user set themselves — the documented
  input/output role contradiction (GitHub #19357, closed unresolved) means a user may have pointed
  this variable at their own script, and a hook that appends to whatever path it finds is not
  distinguishable from one that appends to a file it owns.

**What this does not do.** It does not change any code. It does not measure the installed `asc` — the
probe's marker is a `#!/bin/sh` stub, not this checkout's binary. And it does not establish that
`install-hook` *should* write this: that is the implementation call, made on the mechanism this
record establishes.

## What was built, and the one bullet that stayed open

*(Added 2026-10-10, when `asc-zser` landed. The Decision above deliberately stopped at the mechanism;
this records which of its three bullets the implementation took, and which it did not.)*

**Taken: the shim**, at `.ascend/bin/asc`. `asc install-hook` writes it beside the hook script —
generated whole on every run, under the same staleness check as the script — and the hook appends a
`PATH` export to `CLAUDE_ENV_FILE`, guarded by `[ -n "$CLAUDE_ENV_FILE" ]`.

The first bullet is not merely unchosen, it is **not buildable as stated**, which this record did not
know when it wrote it: the entry point a checkout has is `packages/cli/dist/bin.js`, mode 644 with a
`#!/usr/bin/env node` shebang, so there is no directory that can be put on `PATH` which yields a
command called `asc`. A file that spells `node <path>` is the only form that works, which is the
shim — that a `.js` target needs `node` in front of it is the shim's reason for existing, not a
detail of it.

The third bullet — **appending to a `CLAUDE_ENV_FILE` the user set themselves — is still open, and
was not measured.** What limits the damage is the text that gets appended rather than the guard
around it: the block is a `case ":$PATH:" in` … `esac` that adds one directory only when it is
absent, so appending it to a foreign file is idempotent and inert unless that directory is genuinely
missing from `PATH`. Nothing here establishes that Claude Code cannot be pointed at a file the user
owns, and nothing here establishes what a user's own file would make of a shell fragment appended to
it.

**Harness deviation, stated rather than buried.** The probe command registered in `PREREG.md` was
`echo "FOUND=$(command -v asc || echo NONE)"`, under the allowlist `Bash(echo:*)`. **It could not
run.** Claude Code splits a compound command at `||` and `$( )` before matching it against the
allowlist, so it decomposes into three commands and the middle one matches no allowed rule; every
session was denied. The replacement is a bare `echo "$PATH"`, and the measurement is the same
question read off the shell's PATH directly instead of off a lookup it runs. Measured, not assumed:
`Bash(echo:*)` **allows** `echo hi` and **denies** `echo "$PATH"` in the same headless configuration,
so the allowlist was widened to bare `Bash`, and the probe now records **every** Bash command a
session emits so an off-script session is visible in the row. The predictions and the decision rule
were not touched.

**Confidence.** `Confirmed (empirical)` for both tables: 16 real headless sessions plus two
validating reps per arm, and a directly-executed `sh` test. `Traced` for the document corroboration —
the pages were read, not re-driven. **Not established, and stated as unestablished:** every session
here is a **fresh launch**. The documentation research found community reports that the sourced-env
cache is stale after `/clear`, `/resume`, `--continue` and compaction (issues #24775, #14433, #56400),
and none of those paths was tested, so the same-session result must not be read as covering them.
Also not established: whether an empty-string `CLAUDE_ENV_FILE` (reported in older builds, #15840)
occurs on this build — it was set in every one of the 16 sessions observed.
