# EV-25: do delegated subagent tasks return usable results, and what does delegation cost?

**Status**      Measured 2026-09-26 for `asc-6ola.9`. Predictions were written to the bead's notes
                (PREREG, 2026-09-26) before the first replay of the handler. **Both numeric
                predictions missed**, in exactly the direction the PREREG's own contrary evidence
                named in advance. The handler and the `judged` candidate mechanism it carried are
                sound and green; the bead's QUESTION is not yet answerable, because the upstream
                event `agent.return` undercounts returns by 45%.

**Question**    For `asc-6ola.9`: *"do delegated tasks return usable results, and what does
                delegation cost?"* Also the acceptance case for one DSL promotion: `judged` — the
                declaration that a field is deliberately not measured, which is the parent
                `asc-6ola`'s open design question 5.

## Method

One handler, `handlers/subagent-outcome.yaml`: `on: agent.spawn`, a `first` window with
`until: session.end` matching `agent.return` on `child_agent_id: {eq: $child_agent_id}`, emitting
the return's own `status` and counts, and declaring `judged: [outcome]`. Replayed by the
production normalizer and evaluator (`derive_version` 2) through `asc handlers check`.

The window's `until` is `session.end` and NOT `agent.return`. An `until` is evaluated before the
window's own match and closes the window there, so `until: agent.return` with a `first` watching
`agent.return` emits no rows AND reports `unclosed: 0` — a handler green over its whole signal.
That was this plan's first draft; it is now refused at compile time, and the refusal is
mutation-tested. Measured both ways, not reasoned — see Limits.

Three follow-up probes then asked *why* the handler's numbers came out as they did, on the
event log and on the transcripts directly: the spawn/return join shapes, whether each unreturned
spawn has a notification anywhere, and — decisively — which record shape carries it.

Horizon: 87 files, 111,730 events, 2026-09-12T01:07:55.847Z → 2026-09-26T10:02:14.716Z,
`derive_version` 2, ingest counters: records 86,556, `unpairedResults` 0, `unfinishedCalls` 1,
`unmatchedNotifications` 55. The project directory is written below as
`-Users-<user>-projects-ascend`; the real name is redacted, the measurement is not.

## Predictions (bead PREREG, before measuring)

- **rows = 85** (one per Agent/Task spawn across this project's 87 transcripts)
- **unclosed = 0** (every spawn has a return)
- `status` values drawn from the notification's `<status>` tag: `completed` in the majority,
  plus `killed` and `failed`
- the cost fields present on a **minority** of rows, because they come from the notification tag

Registered in the same note, so a miss could not be explained after the fact: *corpus-wide only
694 of 1,244 notifications join a spawn at all, so `rows` may be materially below 85 and
`unclosed` may be non-zero; the 85/85 pairing was measured with a looser method than the
`child_agent_id` join this handler performs.*

**Every one of the 36 has a notification.** None is a genuinely un-notified delegation. So
`unclosed: 41` is not a delegation failure and not a handler bug — it is 36 returns the adapter
never emitted, plus 5 spawns that carry no `child_agent_id` at all (no tool result).

Which record shape carries them:

```
record shapes carrying a MISSING id: {
 "queue-operation": 72,
 "attachment": 35,
 "user+isMeta": 1
}
```

`taskNotification` (`packages/adapter-claude-code/src/normalize.ts:145`) returns `undefined`
unless `record['type'] === 'user'` AND `record['message']['content']` is a string that
`startsWith('<task-notification>')`. The notifications for all 36 arrive as `queue-operation`
records (the tag in a **top-level** `content`, no `message` field) and as `attachment` records,
which the adapter never reads. They are invisible to the parser — and to the counters, because
`unmatchedNotifications` (55) counts only notifications that **parsed** and failed to join. 108
notification records, and nothing counts them.

All 36 were also in the **same file** as their spawn, which is what rules out the per-file
`spawned` set (`normalize.ts:425`) as the cause: the gate would have fired had the record been
read at all.

## Limits

- **One project, one operator** — n = 1 at the project level; no claim about other projects.
- **The headline numbers measure the adapter, not delegation.** 44/80 is a count of returns
  *emitted*, not returns *made*. Nothing in this record supports a rate about subagent behaviour,
  and the bead's question stays open until the parser sees the records.
- **`failed` is an anecdote.** 3 `is_error` among this project's 85 spawns is under `MIN_N` (20,
  `packages/analysis/src/proportion.ts:50`), so it is named as an incident, never a rate.
- **The 5 spawns with no `child_agent_id`** carry no tool result at all; their `agent.spawn`
  events are emitted with `agent_type` and `description` only.
- **Corpus-wide join figures** (694/1,244, `<tool-use-id>` 984 vs `<task-id>` 1,243) were
  measured over 1,231 files of the whole corpus, not this project, and are quoted as context.
- **The `until` refusal was verified by mutation, not by a real handler.** Disabling it fails 4
  named tests; no committed handler exercises it.
- **The corpus is live.** `events` moved from 111,616 to 111,730 between two runs twelve minutes
  apart; `rows`, `triggers` and `unclosed` were unchanged across both.

## Decision

**The `judged` promotion is accepted.** It was forced by a real handler (the spike rule), it
changes one row builder and adds one top-level key, a handler without the key produces
byte-identical rows, and the four refusals and the row-carriage are each killed by a named test
under mutation. It answers the parent's question 5 in the only way the store allows: `not_measured`
is the default state and needs no encoding, so a candidate is an entry whose judgment field is
simply absent, and the handler's single new obligation is to declare that the absence was
intended. Confirmation is an ordinary later record against the same row, not a new mechanism.

**The `until`-equals-watched-kind refusal is accepted** on the strength of a measured silent
zero: `rows []` with `unclosed 0`. Making the class unwritable at compile time is worth more than
the comment and the test that would merely document it.

**`subagent.outcome` is NOT yet trustworthy as a source, and the bead's question is not
answered.** The event is correct, its rubric is properly deferred under `judged`, and the handler
reports honestly — but it reports over a log where `agent.return` fires for 55% of identified
spawns. A rate computed from it today would be a rate about the parser. The parser defect is
filed as its own bead and recorded as `dogfood/0017`; `asc-6ola.9`'s question closes when that is
fixed and this replay is re-run unmodified.

**What the miss actually taught.** The PREREG's contrary evidence was one sentence, written from
one measurement, and it was the whole story. A prediction registered alongside the evidence
against it is worth more than a confident one — the miss was legible immediately rather than
excusable afterwards.
