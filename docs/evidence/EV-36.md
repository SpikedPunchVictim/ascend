# EV-36: what does a cursor-less ingest cost on this machine, against the 7.965 s / 977-file / 1.63 GiB baseline?

**Status**        Measured 2026-09-30 for `asc-i5tj.14` (E12.4). **The question was named in advance
                  and so was the comparison** — acceptance criterion 3 of that bead reads *"measures
                  its own first-run-after-cutover cost on this machine, against the 7.965 s /
                  977-file / 1.63 GiB baseline above… The number is the acceptance test."* n=1
                  machine (this one), n=2 runs of the full read. **The headline is that losing the
                  cursor costs 17.6 s and 16.5 s, once, over 1,083 files — and that the same corpus
                  with the cursor present costs 0.369 s, a 46× ratio measured the same day.**

**Question**      `asc-i5tj.14` moved the ingest cursor out of SQLite and into
                  `.ascend/ingest-cursor.json`. The migration cannot carry it, so after the cutover
                  the cursor is absent and the first `asc ingest claude-code` reads every transcript
                  in full. Criterion 1 of the bead decided the cursor's home; criterion 2 (deleting
                  it reproduces a full read and nothing else) is already asserted —
                  `ingest.test.ts`'s *"deleting the cursor file reproduces a full read, with no
                  duplicate entries"*, green. What was left is the size of the degradation: the
                  module doc's own figure was 7.965 s for a full read, and that figure was four days
                  old and about a smaller corpus. So: what does it cost **now**, and how much of the
                  difference is the corpus growing rather than anything else changing?

## Method

**The measurement is the real command on the real corpus, not a fixture.** The live store is this
repository's own `.ascend/`, already cut over in `37f7ee3`, and the corpus is this machine's
`~/.claude/projects`.

- The cursor was **copied to `/tmp` before anything was deleted**, so the measurement is repeatable
  and the machine's accumulated skip state is not destroyed by measuring it.
- `.ascend/ingest-cursor.json` deleted, then `ingest claude-code` run as a subprocess through the
  **built binary** (`node packages/cli/dist/bin.js`; `dist` confirmed current — its
  `packages/store/dist/schema.js` has no `version: 4`). Wall clock is `date +%s.%N` brackets around
  the process, so it includes node's own startup, which is the honest cost of the run as a user has
  it.
- **Twice with the cursor absent** (n=2), then once with the cursor present, which is the contrast
  that makes the first number mean something.
- **The corpus size is measured, not quoted.** `find … -name '*.jsonl' -type f | stat -f %z`,
  summed. The command skips transcripts under known OS temp project roots by default (`asc-80m`,
  landed 2026-09-18), so the like-for-like figure is the non-ephemeral set: paths not under a
  `-private-*` project directory, which is `files=1083 bytes=2146378468`.
- **The baseline is like-for-like and that was checked rather than assumed.** The 977-file figure is
  from `claude-code.ts`'s module doc, written by `f427769` on **2026-09-22**; the ephemeral
  exclusion is `9766ef4`, **2026-09-18**, four days earlier. So the baseline already excluded the
  temp roots and its 977 counts files read, as 1,083 does here.

## What the numbers decide

**1. The degradation is ~17 s, once, and then it is over.** A cursor-less run costs
**17.56 s / 16.51 s**; the next run, with the cursor it rebuilt, costs **0.369 s**. The bead's
question — *what does losing the cursor cost* — has the answer the contract predicted ("absence
costs time, never correctness") and now has a size: **one run of ~17 s**, after which the state is
rebuilt and every subsequent run is at the floor.

**2. The 46× ratio is the measurement that is not subject to the repo's own drift caveat, and it is
the one to quote.** `EV-33` measured **1.6× drift between two days on identical code**, so any
comparison of today's 17.0 s against a figure taken eight days ago is weak by the project's own
standard. Run A and Run C read the *same 1,083 files on the same machine on the same day*, and the
only difference between them is the cursor: **17.0 s vs 0.369 s**. That is the number that says what
the cursor is worth.

**3. Against the baseline, the corpus grew 23% in bytes and the time roughly doubled — and that
difference must NOT be read as a regression.** Files **977 → 1,083** (+10.8%), bytes **1.63 GiB →
2.00 GiB** (+22.6%), time **7.965 s → 17.03 s** (the mean of two, +114%). Per byte that is
**4.55 ns/B → 7.93 ns/B**. A 1.8× per-byte slowdown sounds like one, but `EV-33`'s 1.6× two-day
drift on identical code covers most of that gap, and nothing here holds the corpus constant across
days. **Stated plainly: this measurement cannot separate "the corpus grew" from "the machine is
slower today" from "ingest regressed", and it does not claim to.** What it does establish is the
absolute cost on this machine today, which is what criterion 3 asked for.

**4. Criterion 2 is confirmed on the real corpus at 1,083× the fixture's scale.** A full re-read of
every transcript produced **2 new entries and 0 duplicates** — those 2 being this session's own new
transcript content, which the earlier run could not have derived. Runs B and C each left the count at
6,530. The fixture's one-file corpus asserts the same property; this is that assertion at scale, and
it is the evidence that the idempotency the contract leans on is real rather than argued.

**5. The rebuilt cursor is the same size as the one that was deleted** — 1,083 rows, 1 handler —
which is the check that a full read re-derives the whole skip state rather than a subset of it. Had
it come back smaller, every subsequent run would have been a partial full read, which is exactly the
`asc-n4eg` shape.

## What this does NOT measure — and where it is still weakest

- **n=1 machine, n=2 runs, one corpus, warm page cache.** No foreign machine and no foreign
  repository. The project's method asks for the second case and this is not it; `asc-i5tj.4.4` is
  where a real corpus other than this one would come from, and it is still this repo.
- **The cross-day comparison is unusable by the repo's own evidence**, as stated in point 3. The
  46× same-day ratio is the finding; the 977-vs-1,083 and 1.63-vs-2.00 GiB growth is context for it.
- **The cursor's own write cost is not isolated.** Run C's 0.369 s includes reading, parsing and
  rewriting a 327 KB JSON file. How much of the 46× is the *read* being skipped and how much is the
  file being small is not separated here.
- **The 176 ephemeral files are excluded by default and were not read**, so the byte figure counts
  the 1,083 only. Reading them (`--include-ephemeral`) is a different measurement and was not taken.
- **Nothing was measured about a crash between the entries commit and the cursor write.** That is the
  cost the sidecar's design accepted (a file cannot join a SQLite transaction) and this record does
  not measure it — it measures what a *deliberately* absent cursor costs, which is the same read.
