# EV-14: what is a dump file, and is the index a measurement of what is on disk?

**Question**    `asc explore <type> --dump <dir>` writes a type's entries as files and an index of
                them, so a corpus that does not fit in a context window can be *selected* cheaply and
                read one file at a time. Three questions, and the first is a published contract:

                1. **What is a file?** One entry, or a group of them? The spec says each file has a
                   count, and a file holding one entry has a count that is always 1 -- so the two
                   readings are both defensible and one of them makes the index the size of the thing
                   it exists to avoid reading.
                2. **Is `manifest.json` a measurement of the files beside it?** The index is read days
                   after the command that wrote it, by someone holding the files and nothing else. A
                   figure that overstates or understates a file is a caller budgeting wrong in a way
                   nothing corrects.
                3. **What does `--max-tokens` touch?** A dump is the one mode whose output outlives the
                   command, so a budget that reaches the disk is a permanent lie about a directory.

**Method**      The `docs/evidence/EV-11` frozen corpus (`/tmp/sx7/corpus/.ascend/ascend.db`, 1,491
                entries of which 486 are `verification_run`), driven through the real `asc` binary --
                not the pure functions, so the flag parser, the store round trip, the file writes and
                the render are all in the path. Read-only: the corpus was opened, dumped into a
                scratch directory, and never written to.

                **Q1** ran the shipped binary at three chunk sizes over the same 486 entries and
                measured each arm's files and its index from the bytes on disk -- the index pretty-
                printed as it is written, not as a compact string. The corpus's entries are ordinary
                rows of real evidence text, so the sizes are real.

                **Q2** re-derived every figure in `manifest.json` from the files it names, by a
                different expression than the one that produced it: counts from counting LINES, token
                figures from measuring the file TEXT by code points, totals from summing the rows.
                Also at `--limit 1` (486 files) and `--limit 7` (70 files), where the per-file blocks
                dominate and the smallest error would be largest.

                **Q3** ran the same dump twice, with and without a budget, and compared the two
                directories byte for byte; and separately walked the whole type through `--page`, to
                confirm the dump's order and membership are the paging path's rather than a second
                opinion about what is in the type.

                The failure cases the corpus cannot produce -- an empty type, a directory that is
                already occupied, a budget below the floor -- were driven against a five-entry scratch
                project, because a corpus with 486 entries cannot be made to fail on a technicality.

**Measurement**

**Q1 -- a file holds a group, and the measurement is what decides it.** The same 486 entries,
dumped three ways:

| arm | files | `file_tokens` | index | index as a share of the data |
|---|---|---|---|---|
| one file (`--limit 1000`) | 1 | 93,604 | **186** | 0.2% |
| 40 per file (the default) | 13 | 93,607 | **1,295** | 1.4% |
| one entry per file (`--limit 1`) | 486 | 93,772 | **44,805** | **47.8%** |

The data is 93,604 tokens (187,207 bytes). An index that lists every entry separately is **44,805
tokens -- 47.8% of the corpus it exists to avoid reading**, and a caller who reads the index to decide
what to read has already spent nearly half the corpus's cost to decide. The grouped index is **34.6x
cheaper** than the per-entry one, and it is the only reading under which the spec's "count" per file
carries information: a file holding one entry has a count that is always 1.

*An earlier probe on this same corpus recorded 34,840 and 460 tokens for these two arms (203x). That
figure is superseded and is not reconciled here, because the index has changed since: it now carries a
per-file `recorded_at` range, a `filter` block and a `chars_per_token` field. The ratio that stands is
the one measured on the bytes this code writes -- **34.6x** -- and the direction of the conclusion is
unchanged.*

**Chunking costs the data nothing; it costs the measurement one token per file.** The 13 files and the
single file are byte-for-byte the same text (187,207 bytes each, verified by comparing the
concatenation), because a chunk file is its lines joined by `\n` plus a trailing `\n` -- so splitting
changes no byte. What moves is the estimate: **93,607 against 93,604**, three tokens for thirteen
files, which is the estimator's per-file rounding and nothing else. The trailing newline is included in
the measurement deliberately, so the figure describes the file an editor would write rather than one
nobody has.

**Q2 -- the index agrees with the bytes, at every chunk size, and the check was shown to fail.** For
each of the three arms: every line count matched the manifest's `count`; every token figure matched an
independent code-point measurement of the file; the totals matched the sums; every line parsed as JSON;
and the concatenated ids equalled the ids the store returned, in order, with no duplicates. Zero
mismatches across 486 entries at `--limit 1`, `--limit 7` and the default.

That the check is load-bearing was established by breaking it, per this project's rule that a check
must be shown to fail before it is trusted to pass. Eight mutations were applied to the shipped source,
rebuilt, and run against the CLI-level suite; every one produced a failure, and the source was restored
byte-identical afterwards:

| mutation | what it broke | result |
|---|---|---|
| the coverage guard removed from the dump render | the index claims a completeness the trim block contradicts | fail: `expected 1 to be 5` |
| the fit moved back after the file writes | a refused budget writes a complete dump | fail: directory exists |
| the index written before the chunk files | a failed write leaves an index naming files that never landed | fail: `manifest.json` exists |
| the stale-file warning removed | `--force` leaves files silently | fail: no warning emitted |
| the empty dump's floor raised to 1 | the refusal claims a file that does not exist | fail: wanted `-- 0 files --` |
| a per-file token figure inflated by one | the index no longer measures the file | fail at both unit and CLI level |
| `chunkText` writing two lines per entry | the count no longer matches the lines | fail: `expected [ …(4) ] to have a length of 2` |
| the chunk list reversed | the dump order is no longer the paging order | fail: `to strictly equal` |

**Q3 -- the budget fits the index and cannot touch the disk.** `--max-tokens 500` over the corpus
trimmed stdout to 4 of the 13 file rows while every file and the on-disk `manifest.json` were
**byte-identical** to the untrimmed run, confirmed with `diff -rq`. And the dump's 486 ids, in order,
are the ids `--page --limit 1000` returns: same set, same order, 0 duplicates.

**Two defects were found, both by driving the binary, and neither was visible in the code or in the
planner's unit suite.**

The first is the severity-zero class. `--dump --max-tokens 500` printed

```
"coverage": { "shown": 4, "total": 4, "has_more": false }
```

beside a `trim` block reporting `dropped: 9`. The coverage block defaulted to "complete" because the
dump render never passed one, so the one field a consumer reads to decide how much of the dump it is
holding said the dump was four files. This is the same defect the map mode had already been fixed for,
in the one output whose entire job is to say what exists on disk. Fixed with the same guard; the
corrected output reads `{"shown":4,"total":13,"has_more":true,"percent":30.8}`.

The second is the same class one step further out: **a budget the command refused still wrote the whole
dump.** The first version fitted the index *after* writing the files, so `--dump <dir> --max-tokens 1`
exited 2 with a message about the budget and left a complete six-file dump behind it. A command that
declines to answer the caller's question and modifies their filesystem anyway is a failure the caller
cannot see from the exit code or the message. The fit now runs before the first write, so every refusal
this mode has -- the type, the mode conflict, the occupied directory, the budget -- precedes the disk.

A third finding is a limitation that was made visible rather than removed. `--force` overwrites the
names it writes and touches nothing else, so re-dumping a *smaller* dump into a directory that holds a
larger one leaves the extra files behind: measured, a one-file dump written over a five-file dump left
`2.jsonl`–`5.jsonl` in place, and someone globbing the directory would read them as part of this dump.
The command now names them on stderr and points at the index, which is the authority on what belongs to
the dump. It does not delete them: deleting files this command did not write is a larger power than a
dump flag should hold.

**Decision**    Ship the dump, with the file holding a **chunk**, decided by the measurement above: a
                per-entry index is 47.8% of the corpus it indexes, and grouping is the only reading
                under which the spec's per-file count means anything. The chunk size is `--limit`, which
                is also the page size -- one flag, two questions, and the mode that is running decides
                which one it is. The extension is `.jsonl`, matching the `asc export`/`asc import`
                format the CLI specifies; note that no such command exists yet, so the format has no
                consumer and that intent is unverified.

                **Every refusal precedes the first write, and the index is the last thing written.** A
                directory with data and no index is self-announcing -- there is nothing to read. An
                index naming files that were never written is the opposite, and it is the one failure of
                this feature a reader cannot detect for themselves.

                **`--max-tokens` fits the index on stdout and never the bytes on disk.** A trimmed
                stdout is honest: it carries `trim` and names the files it withheld. A truncated
                manifest on disk would be a permanent claim about a directory, read later by someone
                with no way to tell.

                **The floor is zero for an empty dump.** A floor above what an output holds changes
                nothing about what is emitted -- measured by mutating it -- but it does change the
                refusal, which names the floor: "the smallest possible one in this output format -- 1
                file -- is about 195 tokens" for a type that has no files at all, when the truth is 0
                files and 86 tokens. A refusal that overstates what exists is the same class of claim as
                a report that does.

**Confidence**  High for Q1, Q2 and Q3: the measurements are of the real binary's real bytes, the
                index was re-derived from the files by independent expressions, and every assertion that
                carries the feature was mutated and shown to fail.

                **Medium for the corpus, and the limitations are stated rather than implied.** n = 1,
                and this corpus is derived rather than earned: it was backfilled, so 4 of its 9 types
                have 0 entries and every one of its 1,491 entries shares a single `recorded_at`
                (`2026-09-15T17:57:38.651Z`). **That makes the per-file `recorded_at` range
                uninformative here** -- every file reports `min == max` -- and it means the chunk
                boundaries were exercised only on an order effectively determined by the id, not by
                time. The feature is exercised; it is not validated on a corpus with real spread.

                The envelope columns are empty in this corpus as well (`run_id`, `workflow`, `actor`,
                `repo`, `branch`, `git_sha`, `cwd` each have 0 distinct values), so no chunking axis
                other than the paging order was available to test. That is also why chunking is not
                parameterised by property: there is no natural axis in the data this was measured on,
                and `--group-by` belongs to `asc-56k` rather than being invented here.

                Unverified: the dump format's interop, since no `asc export`/`asc import` exists to
                read it back; the behaviour of a dump large enough for memory rather than correctness to
                be the constraint (the largest measured is 486 entries, 187 KB); and `--force`'s
                behaviour on a directory holding a partially-written dump from an interrupted run,
                which was not constructed.
