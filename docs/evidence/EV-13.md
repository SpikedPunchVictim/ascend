# EV-13: does `--max-tokens` actually keep an output inside its budget?

**Question**    `asc explore --max-tokens N` fits an output to a context budget, drops rows to get
                there, and prints a report saying what it cost. Three questions, and the third is the
                one that decides whether the feature is honest:

                1. What is the code-points-per-token ratio for ascend's output, and is the folklore
                   figure (four characters per token) usable?
                2. Is the emitted output actually within the budget, and is the number on the report
                   the size of the bytes on stdout -- or does the fit *say* it fits?
                3. A trimmed page is a subset with a cursor. Does walking it still reach every entry,
                   or does it leave a hole?

**Method**      The frozen EV-11 store (`/tmp/sx7/corpus/.ascend/ascend.db`, 1,491 entries of which
                486 are `verification_run`), driven through the real `asc` binary -- not the pure
                functions, so the flag parser, the projection, the store round trip and the render are
                all in the path. Three real tokenizers, none of them a dependency of ascend:
                `tiktoken` `cl100k_base` and `o200k_base`, and `@anthropic-ai/tokenizer`.

                **Q1** tokenised six real outputs of the frozen corpus -- the map, a 40-entry page and
                a sample, each as JSON, table and CSV where the format allowed -- and compared each
                tokenizer's count against the code-point count. Then, because the ratio is applied to
                content ascend *stores* and not only to what it *prints*, the same three tokenizers
                were run over bare content in eleven scripts and encodings, with no JSON envelope: the
                envelope's punctuation tokenises well and would flatter the result.

                **Q2** swept four mode/format combinations (map, page, sample, page-as-CSV) across
                budgets from 200 to 6,000 in steps of 137 -- 84 runs -- and for each one measured the
                bytes that actually arrived on stdout with an independent implementation
                (`[...text].length`, where the shipped estimator walks UTF-16 units by hand), then
                compared that measurement against both the budget and the number the report claimed.

                **Q3** walked the whole of `verification_run` through pages budgeted at 900 tokens
                against a limit of 40, following each `next_cursor` to the end, and compared the
                distinct ids collected against the store's own count for the type (read with `sqlite3`
                directly, not through this code path).

**Measurement**

Q1, ascend's own output -- worst (smallest) ratio across the three tokenizers:

| output | code points | worst code points/token |
|---|---|---|
| `--page --limit 40 --csv` | 14,607 | **2.18** |
| `--page --limit 40 --table` | 7,123 | 2.30 |
| `--page --limit 40 --json` | 15,998 | 2.35 |
| `--sample --limit 40 --json` | 15,711 | 2.32 |
| `--json` (the map) | 5,877 | 2.78 |
| `--table` (the map) | 1,759 | 4.11 |

The folklore 4.0 is right for exactly one of these -- the smallest and most label-heavy, a 1,759-code-point
table -- and 1.8x optimistic on the output a caller is most likely to budget. **This is what the
shipped constant is calibrated on: `CHARS_PER_TOKEN = 2`.**

Q1 again, bare content -- the same three tokenizers, no envelope:

| content | worst code points/token | at `CHARS_PER_TOKEN = 2` |
|---|---|---|
| English prose | 5.77 | over-estimated |
| symbol-dense (ascend-like) | 3.30 | over-estimated |
| Cyrillic | 1.63 | **under-estimated 1.2x** |
| base64 | 1.49 | **under-estimated 1.3x** |
| hex | 1.23 | **under-estimated 1.6x** |
| Arabic | 1.10 | **under-estimated 1.8x** |
| Japanese | 0.96 | **under-estimated 2.1x** |
| Korean | 0.90 | **under-estimated 2.2x** |
| CJK | 0.79 | **under-estimated 2.5x** |
| emoji (ZWJ families) | 0.39 | **under-estimated 5.1x** |
| emoji (single) | 0.33 | **under-estimated 6.1x** |

**Q2 succeeded, and two defects were found on the way -- both by running the binary, neither by
reading the code.** The first was the severity-zero class: the search measured a rendering WITHOUT
the report, then appended the report to what it emitted, so `--max-tokens 400` printed an output
whose own report read `estimated_tokens: 401`. A fit that reports success wrongly destroys trust in
every other number the tool prints. Fixed by making every candidate be measured as the output it
would actually produce, report included, and by asserting the fixed point in the shipped code rather
than in a test. After the fix, across the 84-run sweep: **0 over budget, 0 disagreements between the
reported number and the measured bytes**, tightest fit 1 token of slack (`--page --limit 40`, budget
3,351, measured 3,350).

The second was in the refusal path, and it is the same class one level up: a budget below the floor
is refused with a message naming the smallest budget that would work -- but the report contains the
budget, so a larger number is a wider report, and the figure named at the caller's budget was
*refused again by the message that named it*. Measured: the map's four header rows measure 183 tokens
at a budget of 1, and fitting at 183 does not fit. The figure is now the fixed point of "the smallest
budget at which the floor output fits", and the message says which output format it is the size of --
because that, too, is measured rather than assumed: the same four rows are 183 tokens as a table and
212 as a JSON envelope.

**Q3 succeeded.** 164 pages, **486 distinct ids, 0 duplicates**, against the store's own count of 486;
the largest page measured 873 tokens against its 900 budget. This is the check that would have caught
the silent-hole failure mode -- slicing a page and printing the *original* cursor tells the caller to
resume past the rows that were cut, so those rows are shown to nobody. The store computes the cursor
for the boundary actually on screen instead, and the walk is what proves it.

The sample report survives the same re-draw: `sum(strata[].selected) === rows on stdout` at a generous
budget (40 of 40) and at a tight one, where the sample is re-drawn smaller and the report follows it
(11 requested, 4 emitted, 4 reported).

**Decision**    Ship the fit; `CHARS_PER_TOKEN = 2`, calibrated on real ascend output. Correct the
                claim that accompanied it. The first version of `budget.ts` said the constant was
                "chosen to sit BELOW every ratio measured, so the estimate is an over-estimate by
                construction and the budget is a ceiling rather than a hope". **The second half of
                that sentence is false and the measurement above is what overturns it:** it was true
                of six outputs and false of the corpus they are made from, because ascend stores
                LLM-written `evidence_text` and that text need not be Latin. A store full of CJK
                evidence overflows the budget by about 2.5x and emoji by about 6x -- the exact failure
                the flag exists to prevent.

                No cheap derivation replaces it, and this was measured rather than reasoned about: a
                model charging ASCII at the measured prose rate fails on base64 (1.49), and one
                charging non-ASCII a token per code point fails on emoji (0.33, about three tokens per
                emoji). So the honest position is a calibrated default, a stated boundary, and a
                caller who can override the assumption -- and the override does not exist yet, which
                is why it is filed as `asc-squ` rather than guessed at here. In the meantime
                `chars_per_token` rides on every report, so the assumption that produced any given
                number is visible to whoever received it.

                Both defects were found by driving the binary against real data. Neither was visible in
                the unit suite, which did not exist yet at the time, and the second one -- the
                self-refuting refusal -- was found by a CLI-level test that passed the named figure
                back, which is now the assertion that covers it.

**Confidence**  High for Q2 and Q3: the measurement is the emitted byte count of the real binary on a
                real corpus, checked against an independent implementation of the same quantity, and
                the failure modes were reproduced before they were fixed. High for the ascend-output
                half of Q1: three real tokenizers, six real outputs.

                **Medium for the bare-content half, and the limitation is stated rather than implied.**
                The samples are constructed, not harvested -- there is no CJK evidence in this corpus
                to harvest. A constructed sample can be unrepresentative in either direction: repeated
                text tokenises better than varied text (which is why English prose measures 5.77 here
                and 4.16 inside a real JSON row), so the non-Latin ratios above are a floor on the
                under-estimate, not a ceiling on it. n = 1 corpus; the ratios are not re-measured on a
                second, foreign store, so whether the CJK figure holds for real CJK evidence is
                unverified.

                Also unverified: the fit's behaviour on an output large enough for the binary search to
                be the cost rather than the query. The corpus's largest single output is a 486-entry
                type walked 164 pages at a time, and no output here exceeded ~16 KB.
