# EV-51: can `asc hook` exit non-zero for a benign reason?

**Question.** `asc-nopa`, split out of `asc-xagi` on 2026-10-12. The generated
`.claude/ascend-hook.sh` ends its stage path with an unconditional `exit 0`:

```sh
if [ -n "$1" ]; then
  run hook "$@"
  exit 0
fi
```

which turns any failure of the resolved binary into success. The bead records the measured case: in a
temp project with the hook installed and no `node` on `PATH`, `sh .claude/ascend-hook.sh post-tool-use`
exits 0 while the shim prints `asc: <bin> needs node, and node is not on PATH` on stderr.

The bead names the question and says it is not settled:

> Not settled: whether it should stop masking. A non-zero lifecycle hook is visible to the reader but
> risks interrupting a session, and for PostToolUse the meaning of each exit code differs (2 is blocking
> feedback to the model; other non-zero is shown to the user). Options worth measuring before choosing:
> propagate `exit $?`; keep `exit 0` but have `asc hook` itself emit the refusal in a form the session
> shows; or leave it and rely on stderr.

So the deciding measurement is narrow and was named before anything ran: **can `asc hook` exit non-zero
for a benign reason?** If it can, propagating its status converts ordinary sessions into hook errors.
If it cannot, propagating can only ever fire on "the binary could not be launched".

**Method.** Two throwaway probes against the real binary, `packages/cli/dist/bin.js`, driven from a
temp project with a store and a `say:` handler. Probe 1 walks the failure paths an ordinary session can
reach; probe 2 attacks the invariant directly with filesystem and shape conditions. Then the exit-code
semantics were read off the Claude Code hooks reference, because the bead's own statement of them is a
paraphrase and the answer turns on them. Finally, one measurement to test whether the obvious fix is
safe: what an ascend that cannot resolve the subcommand exits with.

## Finding 1 — `asc hook` cannot exit non-zero. 23 of 23 paths exit 0

Probe 1, an ordinary session:

| condition | exit | stderr |
|---|---|---|
| no project root above cwd | 0 | *(nothing)* |
| stdin is not JSON | 0 | warning |
| empty stdin | 0 | warning |
| valid JSON, wrong `hook_event_name` | 0 | warning |
| input missing `session_id` | 0 | warning |
| stage name that is not a stage | 0 | warning |
| no stage argument at all | 0 | warning |
| `--holdout` that does not parse | 0 | warning |
| matching handler, delivered | 0 | — |
| malformed handler YAML | 0 | warning |
| `--holdout` set, transcript path unreadable | 0 | warning |
| `--help` | 0 | — |

Probe 2, attacking the invariant:

| condition | exit | stderr |
|---|---|---|
| `.ascend` is a FILE, not a dir | 0 | *(nothing)* |
| `.ascend` absent entirely | 0 | *(nothing)* |
| handler file unreadable (mode 000) | 0 | warning |
| `handlers/` is a FILE, not a dir | 0 | warning |
| handler file is empty | 0 | warning |
| `say:` is a number, not a string | 0 | warning |
| `on:` an event kind that does not exist | 0 | warning |
| `--holdout` set, `.ascend` unwritable | 0 | *(nothing)* |
| `where.skill.in` a string, not a list | 0 | warning |
| `say` template names an absent field | 0 | warning |
| holdout 0.3, delivered | 0 | — (JSON on stdout) |

The control, in the same empty directory probe 1 used: `asc types brief` exits **1**
(`Error: No .ascend/ store found in …`). So the zero is a property of `asc hook` and not of the binary
or of the harness.

The enforcement is `Hook`'s `catch` override, which reports to stderr and returns instead of calling
`BaseCommand.catch`, whose own body is `this.emitStderr('Error', …)` followed by
`this.exit(failure.exitCode)`. The module doc states the contract — *"NEVER FAILS THE SESSION. Exit 0
whatever happens"* — and this is the measurement that the code holds it, including for a malformed
handler and an unreadable file, which are the shapes the doc does not enumerate.

## Finding 2 — the only non-zero sources are failures to launch the binary

None of them is reachable from session data, and all are fixable by the reader:

| source | exit | where |
|---|---|---|
| shim resolved, `node` not on `PATH` | 127 | the shim's own guard (measured in `dogfood/0082`) |
| `node` too old for `node:sqlite` | 1 | `nodeVersionRefusal`, called from the entry point before any command loads |
| the subcommand or a flag cannot be resolved | 2 | oclif — measured: `asc hook-not-real` → 2; `asc hook post-tool-use --no-such-flag` → 2 |

## Finding 3 — stderr from an exit-0 hook reaches nobody

This is the fact that decides the question, and it is external. The Claude Code hooks reference:

> Claude never sees stderr from a hook that exits 0.

It is not shown in the transcript either; reading it yourself requires debug logging. So the bead's
third option — *"leave it and rely on stderr"* — is not a weaker signal than an exit code. It is **no
signal**, and it is the mechanism by which `dogfood/0082` cost three sessions: the shim's refusal was
printed, and there was nothing downstream of the print.

## Finding 4 — bare `exit $?` is not safe, because 2 blocks

The reference gives the per-event semantics:

- **`UserPromptSubmit`, exit 2** — blocks the prompt, so it never reaches the model.
- **`PreToolUse`, exit 2** — blocks the tool call.
- **`PostToolUse`** — cannot block; exit 2 shows stderr to Claude, since the tool already ran.
- **any other non-zero** — a non-blocking `<hook name> hook error` notice carrying
  `Failed with non-blocking status code:` plus **the first line of stderr**.

And the generated stage entry can carry a flag the resolved binary does not know:
`asc install-hook --holdout` bakes `--holdout 0.3` into it. An ascend predating that flag resolves
`hook post-tool-use --holdout 0.3` as an unresolvable command — measured, exit **2**. So the bead's
first option turns a stale install into a **blocked prompt** on `UserPromptSubmit`, which is the
"risks interrupting a session" concern arrived at with a specific mechanism rather than as a worry.

The bead's second option is not worse, it is unavailable. In the failure `dogfood/0082` measured, the
shim exits before `asc hook` is a process; there is no `asc hook` to emit anything in-band. Only the
shell that ran the binary can report that the binary did not run.

## Finding 5 — the `.js` guard is a second silent exit that `exit $?` does not reach

The generated script's interpreter selection runs before `run` is defined or called:

```sh
case "$bin" in
  *.js)
    command -v node >/dev/null 2>&1 || exit 0
    run() { node "$bin" "$@"; }
    ;;
```

A missing `node` there is silent, and it never becomes a status for the stage path to propagate. This
is not hypothetical for ascend's own checkout: installing here resolves the relative branch, which
names `packages/cli/dist/bin.js` — a `.js` — so this repository's own hook takes that branch. The shim
branch (a foreign project) reaches `run` and returns 127; the `.js` branch does not.

## Finding 6 — the trailing `exit 0` is load-bearing for CONTROL FLOW, found by deleting it

This was not predicted and was caught by an existing test, which is the point of recording it. The
obvious form of the fix — replace the discarded status with a tested one — reads as though the `exit 0`
at the end of the stage path is the mask, so the first implementation deleted it:

```sh
if [ -n "$1" ]; then
  run hook "$@"
  status=$?
  [ "$status" -eq 0 ] || exit 1
fi
```

Measured: `install-hook.test.ts`'s asc-tuur.4 case, which drives a stage call and parses stdout as one
JSON object, failed with

```
SyntaxError: Unexpected non-whitespace character after JSON at position 118 (line 2 column 1)
```

The script's last two statements are the SessionStart tail — `run ingest claude-code` and
`run types brief` — so a stage call that stops exiting early **falls through into them**. The hook
answered with its own JSON document and then `types brief`'s output on the same stream, and a hook
that answers with two documents is one Claude Code can parse neither of. The `exit 0` must stay; what
had to go was the *discard* of the status, not the exit. Two different things spelled the same way,
one line apart.

A second self-inflicted false green, found by asking why a mutant had no killer: the first version of
this fix's own `.js` test passed `$ASCEND_BIN` a path that did not exist. `$ASCEND_BIN` is gated on
`-f`, so nothing resolved, the chain fell through to the shim, and the shim reached the same condition
by a different route — the test passed while the `.js` branch was never exercised, and it passed
against the guard replaced by `exit 0`. The fixture now writes the file.

## Decision

**Any failure on the stage path exits 1, and the `.js` node guard reports the same condition the same
way.** Exit 1 is never blocking on any of the three stages and always produces a non-blocking notice
carrying the first line of stderr, so the change surfaces every launch failure — 127, 1, and a stale
ascend's 2 — without ever being able to block a prompt or a tool call. The stage path still ends with
an `exit 0`, which is Finding 6's line and is not the mask: it is the early exit that keeps a stage
call out of the SessionStart tail, and it is reached only after the status was tested.

The principle the exit codes now draw: **nothing to run stays silent; something found that would not
run reports.** The resolution's own `exit 0` when no candidate resolves, and the store guard above it,
are unchanged and deliberate — a teammate who clones this repository has the hook and no store, and
that must stay inert. Past the store guard the project has a store, and `install-hook` guarantees a
shim inside it, so a binary that resolves and cannot run is a breakage and not a configuration.

The sentence both scripts print is one exported constant rather than two copies. The shim and the hook
are regenerated independently and make the same claim about the same condition — the shim at 127
because it is a command someone typed, the hook at 1 because it must not block — so two copies of the
sentence is how the next edit teaches one of them something else. A test asserts both generated files
carry it exactly once.

Rejected, with the measurement that rejected each:

- **bare `exit $?`** — Finding 4: it passes 2 through, and 2 blocks a prompt.
- **`asc hook` surfaces the refusal in-band** — Finding 4: structurally unavailable, the shim fails
  upstream of the only component that could report it.
- **leave `exit 0`, rely on stderr** — Finding 3: measured to reach no reader at all.

The store guard's deliberate silence is a different thing and was not used to justify anything here:
it protects against filing one project's transcripts into another's, and its reader is a teammate with
no store, not an environment that is broken.
