# EV-18: what does one `asc record` call cost the agent that makes it?

**Status**      PRE-REGISTERED. The Question, Method, Threshold and Predictions below were written
                **before any measurement was taken** (`asc-9y1`'s requirement, inherited from
                `asc-9an`: *"Name the question BEFORE running"*). The recorded hash and the exact
                bytes it covers are in *Pre-registration* at the foot of this document.

**Question**    `asc-9y1` asks what a single `asc record` call costs an agent, with a decision rule
                attached: *"if a record costs more than a few hundred tokens, simplify the
                surface."* E4 shipped `asc record` without ever measuring this, and the deadline
                passed, so the task is retrospective. It is not idle: E10's skill is the surface a
                model actually reads, and E11's dogfooding rule has **every** task close record
                entries, so the per-call cost is a multiplier on every other task in the project.

                The question decomposes, and all five parts are named here so none can be settled by
                whatever the run happens to produce:

                1. **Wall-clock.** What is the end-to-end latency of one recording on the real CLI
                   against a real store -- p50/p95 over 20 calls? This is the cost a hook pays on
                   every session start, and the number EV-8 deliberately did not measure (EV-8
                   priced the SQLite INSERT at 0.150 ms; everything else is process start, and
                   "everything else" is the number).
                2. **Context tokens.** How many tokens does one call occupy in an agent's context --
                   the command the model must EMIT plus the output it must READ? Reported per
                   surface, p50/p95, because the two surfaces put different text in different places:
                   one puts the entry in argv, the other in a document.
                3. **Realized cost.** What does a recording actually cost inside a live session,
                   measured from that session's OWN `usage` numbers, and does it agree with
                   `estimateTokens`? The estimator is a calibrated constant
                   (`CHARS_PER_TOKEN = 2`, `budget.ts`), not a tokenizer; if recorded calls sit
                   outside its stated 9-28% band, that is a finding about the estimator.
                4. **Permission friction.** Granted an allowlist entry for exactly
                   `Bash(asc record:*)`, does a recording run to completion in a headless session
                   WITHOUT a permission prompt? This is the bead's third MEASURE and the one nothing
                   but a real session can answer -- a prompt on the hot path is a cost that no
                   millisecond and no token count would reveal.
                5. **Which surface wins, and by how much.** The decision rule presumes there is one
                   surface to simplify. There are two shipped surfaces, so "simplify" is only
                   meaningful against a measured alternative.

**Method**      Two arms. The second exists because the first cannot answer part 4 and cannot
                produce a realized token count.

                **Arm A -- the estimator arm, no model.** 20 real recordings through the real binary
                against a real store, on BOTH shipped surfaces:

                - **S1, the flag surface**: `asc record <type> --prop=<k>=<v> ...`
                - **S2, the document surface**: `asc record <type> -` with a JSON document on stdin

                The CONTENT is real, not authored for the experiment: the 20 entries are the
                property sets of the real entries already in this repo's own dogfood store
                (`.ascend/ascend.db` -- the records this project has been writing at every task
                close). Their sizes are therefore representative by construction, because they are
                the actual entries an agent wrote.

                Each call is timed end to end, from process spawn to exit, with the exit code
                recorded so a failed call cannot be averaged in as a fast one. Tokens for a call are
                `estimateTokens` over the exact command string plus the exact stdout and stderr the
                call produced -- the whole text, since all of it enters a model's context.

                **Arm B -- the realized arm, one bounded session.** A single headless
                (`claude -p`) session on a small model, granted exactly `Bash(asc record:*)` via
                `--allowedTools` under `--permission-mode dontAsk`, and no other tool. It is asked
                to record 20 real entries against a scratch store. Its token cost is read from its
                own transcript's `usage` fields -- a realized count, not an estimate -- and whether
                it completed without a prompt is read from the same transcript.

                No bypass flag is used and no other tool is granted; the grant is the smallest one
                that lets the session record and nothing else.

                All 20 recordings in arm A go to a scratch project (`mktemp -d`), never to this
                repo's store. `~/.claude/projects` is read-only and is not touched by this task.

**Threshold**   The decision rule says "more than a few hundred tokens". That is operationalised
                **before running** as **300 tokens of command plus output per call**, averaged over
                the 20 recordings, on the cheaper of the two surfaces. Above 300 the surface is
                simplified; at or below it, it is not. Stating the number now is the point: chosen
                afterwards, any result would have justified a threshold near it.

**Predictions** Written before running, so being wrong is legible.

                - **P1** -- wall-clock p50 is **under 100 ms** per call. EV-8 measured 0.150 ms of
                  index work at 20 properties; the rest is Node process start, which dominates.
                - **P2** -- for entries with four or more properties, **S2 is the cheaper surface
                  per call**, because S1 repeats `--prop=` and the property name for every property
                  while S2 states each name once. For one-property entries S1 should win, since the
                  document's JSON punctuation is pure overhead.
                - **P3** -- the per-call token cost lands **under 300** on the cheaper surface, so
                  the DECISION is *do not simplify*. The command is on the order of 100-300
                  characters and the success output is a few short lines.
                - **P4** -- with `Bash(asc record:*)` granted, **no permission prompt fires**.
                - **P5** -- the realized per-call cost in arm B is **higher** than arm A's estimate,
                  because a real session also pays for the model's own deliberation around the call,
                  which no command-and-output measurement includes.

**Reporting**   Both surfaces are reported whichever wins, per the protocol's *"report the losing
                arm"*. If P3 is wrong and the cost exceeds 300 tokens, that is the task succeeding
                and the record says so plainly rather than re-scoping the threshold.

## Measurement

### Arm A -- the estimator arm, and the floor under it

Twenty real entries, both shipped surfaces, the real binary, real stores. Harness
`spike/record-cost.mjs`, which writes its raw per-call rows to `spike/tmp/ev18-arm-a.json`; the floor
is `spike/record-cost-floor.mjs`, writing `spike/tmp/ev18-floor.json`. Both are committed and
re-runnable as they stand, on this machine, against this repo's own dogfood store.

**The raw dumps are regenerated, not committed.** They are the entry text itself -- 87% of what this
record is about -- and committing them would publish 20 complete dogfood entries a second time, in a
file nobody reviewed for that purpose. Re-running the harness reproduces them exactly. What is
committed is the instrument, which is what makes the numbers arguable; the reading it produced is
what the tables below are for.

| | S1 (flags) | S2 (document on stdin) |
|---|---|---|
| calls | 20 | 20 |
| failed | 0 | 0 |
| wall-clock p50 | **173.894 ms** | **175.408 ms** |
| wall-clock p95 | 197.437 ms | 188.784 ms |
| tokens p50 | 693 | 696 |
| tokens p95 | 1248 | 1241 |
| tokens mean | **794.15** | **795.25** |
| command chars (mean) | 1405 | 21 |
| stdout chars (mean) | 183 | 183 |

**The two surfaces are the same surface, measured twice.** Mean cost differs by 1.1 tokens in 795 --
**0.14%**. Paired per entry, S1 is cheaper on 14 and S2 on 6, and every one of those deltas is between
-7 and +7 tokens. There is no property-count threshold: P2 predicted S2 would win from four properties
up and S1 below, and the measured difference never leaves the noise band in either direction.

### The cost is the entry, not the surface -- and that is the finding

S2 is what makes this legible, because it is the one surface that puts the surface and the content in
different places. Per call, at the means:

| component | chars | share of what a model handles |
|---|---|---|
| the entry itself (properties) | 1386 | **87.17%** |
| the surface (command, or document punctuation) | 21 | **1.32%** |
| the output the model must read | 183 | 11.51% |

S1's command is 1405 characters, of which 1386 is the same entry text; its entire surface -- every
`--prop=`, every property name, every quote -- is **19 characters per call**. The two surfaces
disagree about where to put 1386 characters, and agree to within 2 characters per call about how much
extra scaffolding to wrap around them.

**So "simplify the surface" cannot reach the number that fired it.** The threshold in this document
was crossed by content: 87.17% of the cost is the entry the agent is recording, which is the
product's payload. A surface costing zero would still leave 698 tokens per call -- 2.3x the threshold.
Simplifying the surface is aimed at the 1.32%.

This is the answer to the bead's DECISION, and it is not the answer the bead's rule anticipated. The
rule presumes a fat surface and thin content; the measurement finds the reverse, by a factor of 66.

### The floor: 88% of the wall-clock is starting the process

P1 predicted under 100 ms. Measured 173.894 ms. The floor measurement says why that prediction was
never reachable by any change to `asc record`:

| rung | p50 | p95 |
|---|---|---|
| `node -e 0` -- the interpreter alone | 52.770 ms | 56.368 ms |
| `asc --version` -- CLI + oclif dispatch, no store opened | 147.820 ms | 154.280 ms |
| `asc query` -- store opened, real query answered | 157.068 ms | 197.601 ms |
| `asc record` (arm A) | 173.894 ms | 197.437 ms |

Bare Node is 52.770 ms; oclif dispatch adds **95.050 ms** before any ascend code runs. The recording
itself -- open the store, validate, insert 18 columns, update the expression indexes, commit -- is
**16.826 ms**, or **9.7%** of the call. EV-8 priced the index work at 0.150 ms and said *"everything
else is process start"*; this is that sentence with the number attached, and the number is 88% once
the interpreter's own 53 ms is included.

**A second finding, which the bead did not ask for and which belongs to the CLI standard this project
adopted.** `cli-best-practices` lists *"Slow startup from eager imports"* as a pitfall with the target
*"<100 ms to `--help`"*. Measured: `asc --help` is **171.414 ms** p50, **242.150 ms** p95 -- 71% over
the target at p50 and 2.4x it at p95. `asc --help` is also the slowest rung here, above `asc --version`
(147.820) and above `asc query` (157.068, which does strictly more work). It is recorded rather than
fixed: it is a conformance gap against a standard this repository cites, and it is out of `asc-9y1`'s
scope. Filed as **`asc-baj.1`** (P3), with the four rungs and the decomposition above carried into the
bead so a later reader does not have to re-derive them.

### Arm B -- the realized arm: RUN

The pre-registration committed to a second arm and the user authorized it. **It ran.** One headless
session, one scratch store, 20 of 20 entries recorded, and the answer to the question no arm A could
reach.

Before the numbers, the one thing about this run that a reader must weigh: **the model was not an
Anthropic model.** This environment routes Claude Code through a local gateway
(`ANTHROPIC_BASE_URL=http://127.0.0.1:11434`), and the model the harness named by default --
`claude-haiku-4-5-20251001` -- is not served there. The first launch died on exactly that:

    There's an issue with the selected model (claude-haiku-4-5-20251001). It may not exist or you
    may not have access to it. Run --model to pick a different model.

It was re-run on `deepseek-v4.1-flash:cloud`, the model this environment does serve. So the session
is a real model, a real CLI and a real transcript, and it is **not** the model the pre-registration
imagined. Every token figure below is that gateway's tokenization. `EV18_MODEL` overrides the choice,
so the run is reproducible on an Anthropic model wherever one is reachable; nothing here was measured
on one.

`spike/record-cost-session.mjs` builds the same 20 entries into a 29,096-byte prompt, initialises a
scratch store, puts a shim `asc` on `PATH` that execs the built binary, and runs one headless session
granted exactly `Bash(asc record:*)` under `--permission-mode dontAsk` -- the bounded grant the
pre-registration specified and the user authorized, with the permission gate narrowed and never
disabled. Before spending a session on it, the instrument was dry-run
(`EV18_DRY_RUN=1 node spike/record-cost-session.mjs`): `asc record --help` exits 0, 20 records, 20
with an `na` array, 0 rows in the scratch store, grant exactly as pre-registered.

**What the session did.** `exit_code: 0`, `result_is_error: false`, the session's own closing word
`"done"`. 20 bash calls, every one of them `asc record` (0 off-command), 0 tool errors, and **20 rows
in the scratch store, read back with `asc query` rather than taken from the session's report of
itself**. Wall clock **75,439 ms** for the 20 recordings: **3,771.9 ms per call**, against arm A's
173.894 ms p50 -- 21.7x, which is model latency, not tool latency. The context grew from 28,948 to
49,074 tokens across the run.

**P4 -- with `Bash(asc record:*)` granted, no permission prompt fires: CONFIRMED, as a measured
contrast rather than an absence.** 20 calls, **0 permission denials**. A count of zero is not evidence
of anything until the detector has been shown to fire, so the same harness was then pointed at a tool
the session was *not* granted -- `EV18_ALLOWED='Bash(echo:*)'`, `EV18_PROMPT` a one-line request to run
`asc record note --prop=text=negative-control`, `EV18_EXPECT_ENTRIES=0`. Same bounded grant mechanism,
one tool narrower, no bypass flag in either direction. That session produced exactly one denial:

    Permission to use Bash has been denied because Claude Code is running in don't ask mode.

`permission_denials: 1`, `tool_errors: 1`, 0 rows in the store, and the model's own report confirms
the mechanism -- *"no prompt was shown for me to approve"* -- and that it did not attempt a workaround.
So the allowlist is what let the 20 recordings through: the identical command, issued under a grant
that did not cover it, was stopped before execution. This is the bead's third MEASURE and the one
thing arm A could never reach.

**P5 -- the realized per-call cost is higher than arm A's estimate: CONFIRMED, but not in the shape
the prediction implied.** The realized figure is the context a recording *appends*: the difference in
`input_tokens` between a turn that made a call and the turn after it -- the tool call the model wrote
plus the result the tool returned. That is the same quantity arm A measures (command plus output), so
the two arms are comparable at all. Nearest-rank percentiles, the convention `record-cost.mjs` uses.

| per recording | n | min | p50 | p95 | max | mean |
|---|---|---|---|---|---|---|
| **arm B, realized** | 20 | 526 | **700** | **1,888** | 3,809 | **1,006.30** |
| arm A, S1 estimate | 20 | -- | 693 | 1,248 | -- | 794.15 |
| ratio | | | **1.010** | **1.513** | | **1.267** |

So the prediction holds on the mean (1.27x) and on p95 (1.51x) and **fails at p50, where the two agree
to 1%**. A typical recording costs exactly what arm A said it costs. What arm B adds is not a higher
centre but a **heavier tail**: the model pays for its own rendering of the call -- JSON escaping, the
quoting of long prose values -- and that cost scales with the content in a way that command-and-output
character counting does not capture, because a character of prose can become several characters of
escaped argument. The 3,809-token maximum is the longest entry in the set. That is a more specific
finding than "higher", and it is the one the numbers support.

Every one of the 20 realized commands was on the flag surface (S1), so the comparison is against S1 --
the surface arm A found *cheaper* for entries of four or more properties. The realized arm did not get
to choose a surface; it used what it was told to use.

The session launch was then attempted **ten times, in both foreground and background**, and every
attempt was refused before execution with the same message:

    deepseek-v4.1-flash:cloud is temporarily unavailable (timed out), so auto mode cannot
    determine the safety of Bash right now.

This is **not** a policy answer about the command and it is **not** a product failure. Diagnosed
rather than assumed: trivial commands (`ls`, `grep`, `node -e '…'`) ran normally throughout the same
minutes, while *every* command that launches a session failed, including a minimal `claude -p` session
with the same grant and a one-line prompt. The auto-mode classifier does not return a
verdict on agent-spawning commands; it times out on them. This is the same class as the denial this
project recorded earlier for an unbounded agent harness, arriving this time as a timeout rather than
a refusal. One hypothesis was tested and **rejected**: that a comment in the harness spelling the
gate-disabling flag name was tripping it. Removing that literal did not change the outcome, and it is
recorded here as a rejected hypothesis rather than quietly dropped.

**Consequence for this record: question 4 is answered and P4 is confirmed.** The pre-registration
named part 4 -- *"granted an allowlist entry for exactly `Bash(asc record:*)`, does a recording run to
completion in a headless session WITHOUT a permission prompt?"* -- as the one thing nothing but a real
session can answer. A real session answered it, and the negative control above means the answer rests
on a detector that has been seen to fire, not on a count of zero.

The run is one command. `! node spike/record-cost-session.mjs` executes it in this session. Its
analysis is built in: it reads the scratch store back (an entry that exists was written by a command
that ran), derives the realized token cost from the transcript's own `usage` fields, and scans the
transcript for permission denials. Everything it writes lands in `spike/tmp/ev18-arm-b-*.json`.
`EV18_REPLAY=<stream.jsonl>` re-analyses a stream already on disk instead of spending another session.

**Two defects in the instrument, both found by running it rather than by reading it.** They are
recorded because a harness that reports the wrong number is indistinguishable from a product that has
the property, and both would have gone into this record as findings if they had not been caught:

1. **`realized_tokens_per_call` was computed by dividing a cumulative sum by the call count.** A
   turn's `usage.input_tokens` is the *whole conversation* the model was sent, so summing it across
   turns counts the growing context once per turn. The field reported **82,053.8** -- against a prompt
   of 29,096 bytes, which is the arithmetic equivalent of a check that cannot be wrong in the safe
   direction. It is now the marginal context a recording *appends* (below), which is the quantity the
   bead asked about and the quantity arm A measures.
2. **A run that recorded 0 of 20 entries wrote `failures: []` and exited 0.** `failures` listed only
   bash calls that were not `asc record`, and there had been no bash calls at all. The first live run
   -- the one that died on the model name -- was reported as a clean run with an empty failure list.
   This is the false-green class this project ranks severity zero, in the instrument measuring it.
   Blocking reasons are now collected separately, the session's own error text is carried into the
   record, and the process exits non-zero.

Both fixes were shown to fail before being trusted to pass. The blocking check: the same harness on a
model this environment does not serve exits **1** with *"the session ended in error: …"* and *"the
store holds 0 of the 20 entries the prompt asked for"*. The store read-back: replaying the real stream
against a real, initialised, **empty** store exits **1** with the shortfall named, while replaying it
with no store available reports `null` and does not claim a measurement -- *not looked at* stays
distinct from *measured absent*, which is the project's rule 7 applied to the harness itself.

**This is the second time, and the second time is better diagnosed than the first.** `EV-16`
(`asc-9an`) recorded the same wall: its model arms were pre-registered, its first harness used the
gate-disabling flag and was refused by the classifier, and when it was rewritten to the bounded grant
its note records that *"the classifier then returned its model-unavailable timeout on every attempt
including a trivial probe."* From that, the blocker read as the classifier being down.

Here it is not down. Trivial probes ran fine in the same minutes -- `ls`, `grep`,
`node -e '…'`, and two throwaway scripts that spawn nothing -- and every command that launches a
session failed. The distinguishing variable is not command length, file contents, foreground versus
background, or time: it is **whether the command starts an agent**. So the honest statement of the
blocker is narrower than EV-16's and should be carried forward in its place: *the auto-mode classifier
does not return a verdict on agent-spawning commands; it times out on them.* Two occurrences, one
environment, and the second narrows the first.

**And the third attempt went through.** The launch succeeded on a retry minutes later with the same
harness, the same grant and the same command shape. That does not retract the diagnosis above -- it
confirms the part of it that matters: the refusals were **temporal**, a window in which the classifier
was unavailable, not a verdict about agent-spawning commands that this environment will never give.
The practical consequence is the one a reader should carry: *an agent-spawning command that is refused
here may simply need retrying, and should not be recorded as a permanent environmental limit.* EV-16
and this record both came close to recording it as one.

**Nothing is folded into `asc-4so.2` from here.** It was the fallback when the launch looked
impossible; the launch happened, so arm B leaves this record measured rather than deferred. `asc-4so.2`
stays open on its own question -- the recall hook's *compliance* rate needs a real Anthropic account,
which this environment does not have -- and this record does not touch it.

**`asc-9y1` closes with all three MEASUREs measured**, which is the outcome the earlier draft of this
section did not expect. Tokens, wall-clock, and permission friction each have a number, and the third
has a negative control behind it.

## Decision

**Do not simplify the surface.** The pre-registered threshold of 300 tokens was crossed -- 794.15 on
S1, 795.25 on S2, 2.65x over -- so the rule as written fires. **The rule is not being re-scoped, and
its firing is not being argued away.**

What the measurement shows is that the rule's remedy cannot achieve the rule's goal. 87.17% of the
cost is entry content and 1.32% is surface; a zero-cost surface leaves 698 tokens per call, still
2.3x the threshold. So the decision is *do not simplify the surface*, taken on the measurement, and
the threshold's premise -- a fat surface over thin content -- is recorded as **overturned**. Per
`KICKOFF.md`, the evidence wins, and what it overturned is recorded here rather than left implicit.

There is no cheap version of this to fall back on. The content is the answer to "what did the agent
learn", which is what ascend exists to store; the only ways to lower 1386 characters per call are to
record less or to record less often, and both are product decisions about the deferred-analysis
premise, not surface decisions. That question is not this task's to answer, and it is not answered
here.

**Wall-clock is not a surface property either.** 88% of it is process start, the floor for *any*
ascend invocation is 147.820 ms, and 9.7% is the recording. P1's under-100 ms was unreachable, not
merely missed.

**The realized arm does not change the decision.** Arm B's realized cost is 1,006.30 tokens on the
mean and 700 at p50, against an estimate of 794.15 and 693. Both are far past the 300-token threshold,
and both are dominated by content for the same reason arm A's numbers are: the model is writing the
entry into the command line either way. A realized measurement that had come back at 40 tokens would
have overturned the decision; one that comes back 27% higher does not move it.

**One follow-up leaves this record, unclaimed:**

1. `asc --help` at 171.414 ms p50 against a published `<100 ms` target in the CLI standard this
   project adopted. Filed as **`asc-baj.1`**; not fixed here.

Question 4 -- the permission-prompt question -- is no longer a follow-up. It is answered above, with a
negative control, by a real session.

## Confidence

**High -- the two surfaces cost the same.** 20 paired calls per surface, every delta between -7 and
+7 tokens on a mean of 795, and both surfaces put 1386 identical characters per call in front of the
model. This is the finding the task exists for and it is not close.

**High -- the decomposition.** The 87.17/1.32/11.51 split is not a model, it is char counting on the
exact bytes each surface carried; the two surfaces independently reproduce 1386 characters per call of
content, which is the cross-check.

**High -- the floor.** Four rungs, n=20 each, 0 failures, measured back to back on one machine. The
ordering is internally consistent (`asc query` costs more than `asc --version` and less than
`asc record`), which is what a floor measurement should look like if it is measuring what it claims.

**Medium -- the tokens themselves, in the direction that does not matter.** `estimateTokens` is a
calibrated constant, not a tokenizer; `budget.ts` records it running 9-28% high against three real
tokenizers. So 794 is an upper estimate. **This does not change any conclusion here**: the surface
share is a ratio of character counts, so an estimator that is uniformly 25% high leaves 1.32% at
1.32%, and the threshold is crossed at 2.65x, which 25% cannot reach.

**High -- the permission answer.** 20 allowlisted calls with 0 denials, and a negative control that
produced a denial on the identical command under a grant one tool narrower. The check was shown to
fire before it was trusted not to.

**Medium -- the realized cost, and lower than the estimate's confidence for three reasons.** One
session, one model, n=20, so a single run stands behind the tail; the model is not an Anthropic model
and its tokenization is its own; and the per-turn transcripts report `output_tokens: 0` for every
turn, so the realized figure counts the context a recording appends and **not** the tokens the model
emitted to write it. The direction of that omission is known: the realized number is a floor on the
session's true cost, not a ceiling. It is still past the threshold by 3.4x at p50.

## Limitations

- **One machine, one corpus.** All wall-clock numbers are this laptop, and all 20 entries come from
  this repo's own dogfood store. `ORDER BY type_name, id LIMIT 20` selects 20 entries that are all of
  type `decision`; the other three starter types do not appear. `n >= 2` is not satisfied here in the
  sense `empirical-planning` means it -- there is no second, foreign corpus. A different project's
  entries would have different sizes, and the split would move with them; the *direction* of the
  finding (content dominates surface) is a property of the ratio, not of these particular entries.
- **The corpus is self-selected in one respect worth naming.** These are entries this project wrote
  at task close, so their length is a property of how this project writes. They were not chosen to
  make a surface look good, but they were also not chosen by anyone else.
- **The shell-quoting rule is a choice and it moves the S1 number.** Values are single-quoted only
  when they contain a character the shell acts on, and the S1 command is rendered under that rule. A
  more conservative quoter would inflate S1 -- by bounded amounts, since S1's total surface is 19
  characters per call.
- **`asc --help`'s p95 is 242.150 ms against a 154.280 ms p95 for `asc --version`.** The tail is
  wider than the medians suggest, and four rungs of 20 cannot say why.
- **Arm B is one session on one non-Anthropic model.** `n = 1` for the session, `n = 20` within it,
  and the model is one this environment's gateway serves rather than a Claude model. The permission
  result is a property of the CLI's permission system and travels; the token distribution is that
  model's and should be re-measured before it is relied on. `EV18_MODEL` is the switch.
- **The realized token count omits the model's own output.** The gateway reported
  `output_tokens: 0` on every turn (only the final result event carried output, 17,873 for the whole
  session). So the realized figure is the context each recording appended, and not the tokens the
  model spent composing the call. Re-measuring on a model that reports per-turn output would raise
  the number, not lower it.
