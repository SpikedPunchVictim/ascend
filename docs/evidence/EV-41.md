# EV-41: does VS Code's conflict resolution honour `merge=union`? (`asc-kq2f`)

**Status**        Measured 2026-10-04 for `asc-kq2f`, against **VS Code 1.139.0** (Electron 43.6.0,
                  Chrome 150.0.7871.250) installed on this machine, driven over the Chrome DevTools
                  Protocol with `puppeteer-core` 25.12.0 — the real GUI, its real command palette,
                  its real merge-conflict extension.

                  **VS Code: clean / 0 lost on `base-union`.** The control cell reproduces the
                  silent-loss shape exactly, so the instrument is shown to detect the failure it is
                  being trusted to rule out. `EV-40.md` listed VS Code as UNMEASURED; this record
                  replaces that for this version, with the bound stated under **Confidence**.

                  This is the last surface of the bead that was reachable at all. GitHub's own web
                  conflict editor, GitHub Desktop and JetBrains remain **UNMEASURED, never `0`**.

**Question**      Same three as `EV-40.md`, the bead's own:

                  **Q1.** Does this client's conflict-resolution path honour `merge=union`? On
                  `base-union` the command line already merges clean to 5 records.

                  **Q2.** Drive it to a **naive one-sided resolution** (accept one side), then read
                  `records.jsonl` **from disk**. Success is 5 records with `ra0` and `rb0` both
                  present, no markers, no duplicates.

                  **Q3.** The failure being hunted is **not** markers. A one-sided resolution leaves
                  *well-formed* JSONL with the other side's appends silently gone — every line
                  parses, no markers, the file simply holds fewer records.

                  Each surface is recorded **clean / 0 lost** or **UNMEASURED** — never as `0`.

## Method

Fixture `spike/git-layout/union-fixture.sh`, the same one `EV-31.md` and `EV-40.md` used: two bases
differing **only** in `.gitattributes` (`base-union`: `records.jsonl merge=union`; `base-plain`: the
attribute absent), each with branches `a-*` and `b-*` appending one record from its own base. Re-run
for this record, its local arm printed the baseline unchanged — `base-union (merge=union): clean, 5
records` / `base-plain (merge=unspecified): CONFLICT` — so the fixture is still the shape the earlier
records were taken on.

Harness `spike/git-layout/union-vscode-arm.mjs`, two modes: `--setup` builds both cells from the
seed, `--drive` drives them. **Both cells are driven with the same instrument** — the merge-conflict
extension's *Merge Conflict: Accept All Current*, the naive one-sided resolution, chosen over
*Accept Current* because it resolves every conflict regardless of cursor position:

- **`plain` is the control.** git conflicts, VS Code resolves, and the appends must be **gone**. A
  clean `union` result means nothing unless the same instrument is first observed losing a record.
- **`union`** is the cell under test.

**Every reading is taken from `records.jsonl` on disk** after the drive, never from the editor's own
report — the failure under test is a file that parses cleanly while missing records.

**Two things were deliberately not done.** VS Code is launched in **single-file mode** (`--goto
<file>`, no workspace folder), which raises no Workspace Trust prompt at all — so the arm never needs
`--disable-workspace-trust`, and the trust guard stays fully in force. Nothing here disables a
security control. And no extension is installed: the merge-conflict extension is a built-in.

## Measurement

### Q1 — the control cell loses the record, exactly as predicted

Stated before running: `plain` should end at 4 records with `rb0` absent, no markers, every line
parsing. It does.

```
--- plain: merge=unspecified, status=UU records.jsonl
    before VS Code: 8 lines, ra0 present, rb0 present, markers PRESENT, unparseable lines 3
--- union: merge=union, status=(clean)
    before VS Code: 5 lines, ra0 present, rb0 present, markers none, unparseable lines 0

=== plain
  palette chose : Merge Conflict: Accept All Current
  before        : 8 lines, ra0 present, rb0 present, markers PRESENT, unparseable lines 3
  after         : 4 lines, ra0 present, rb0 ABSENT, markers none, unparseable lines 0
```

Read straight off disk afterwards, independently of the harness:

```
=== plain cell, from disk ===
{"id":"r0"}
{"id":"r1"}
{"id":"r2"}
{"id":"ra0"}
=== plain git status ===
UU records.jsonl
```

That is the shape Q3 names: **well-formed JSONL, no markers, `rb0` silently gone.** The instrument
can detect the loss, so its silence on the next cell is evidence.

### Q2 — on `base-union` the resolution is a no-op

```
=== union
  palette chose : Merge Conflict: Accept All Current
  before        : 5 lines, ra0 present, rb0 present, markers none, unparseable lines 0
  after         : 5 lines, ra0 present, rb0 present, markers none, unparseable lines 0

=== summary (the claim is per-append survival, not a line delta)
  plain ra0 survived, rb0 LOST
  union ra0 survived, rb0 survived
```

From disk, the union cell holds 5 records and `git status` is clean.

The identical command ran in both cells — the palette row was selected and dispatched in each, and in
`plain` it changed the file. So the union cell's no-change is the command finding nothing to resolve,
not the command failing to fire.

### Q3 — the one path that ignores the attribute is real, measured, and gated

VS Code's merge code was **read out of the installed bundle** rather than assumed
(`extensions/git/dist/main.js`). `merge`, `mergeBranch` and `mergeAbort` shell to the **`git`
binary**, so they inherit `.gitattributes` — the same path the command-line arm measures clean. The
exception is `mergeFile`, which shells to `git merge-file -p <in1> <base> <in2>`, a standalone 3-way
merge with no repository context.

**Measured: `git merge-file` ignores the attribute.** Run on `base-union` — where `git check-attr`
confirms the attribute is live — with the three inputs named so the attribute could match:

```
--- check-attr (on base-union): records.jsonl: merge: union
--- attr matching the first argument, cwd inside the repo:
{"id":"r0"}
{"id":"r1"}
{"id":"r2"}
<<<<<<< records.jsonl
{"id":"ra0"}
=======
{"id":"rb0"}
>>>>>>> theirs.jsonl
exit=1
```

A real bypass, then — but reachable only from an already-open Merge Editor. `runGitMerge`, the sole
caller of `mergeFile`, returns before ever reaching it unless the active tab is a
`TabInputTextMerge` (offset 628038 of the bundle):

```js
async runGitMerge(e){ let{ activeTab:t } = d.window.tabGroups.activeTabGroup;
  if(!t) return; let r = t.input;
  if(!(r instanceof d.TabInputTextMerge)) return;
  let n = await this.git.mergeFile({ basePath:r.base.fsPath, input1Path:r.input1.fsPath,
                                     input2Path:r.input2.fsPath, diff3:e }), o = d.workspace.t
```

A `TabInputTextMerge` exists only once a conflict has been opened in the Merge Editor. On
`base-union` git produces no conflict, so no Merge Editor opens, so the bypass is never entered — and
in single-file mode there is no repository for the Merge Editor to open from at all. **The
attribute-ignoring path is downstream of the conflict it would have to cause.**

### Instrument notes

Both are the same class as `EV-40`'s `[type="submit"]` note: a plausible spelling that means
something else, found by running rather than by reading.

- **`page.keyboard.press('Meta+s')` does not work.** `puppeteer-core` 25's CDP `press` does not split
  a `+`-joined chord — it hands the whole string to `down` and asserts:
  `Error: Unknown key: "Meta+s"`. `Meta` *is* a defined key; the chord must be driven as three calls
  (`down('Meta')`, `press('s')`, `up('Meta')`). The arm now does that.
- **The first `--setup` deleted its own seed.** `WORK` was the seed's parent directory and `setup`
  begins with `rmSync(WORK, {recursive:true})`, so the fixture was gone before the first `cpSync`
  could read it. It failed loudly rather than measuring an empty directory — which is the only reason
  it is a note and not a silently wrong number. Rebuilt from `union-fixture.sh` and the arm now
  refuses a seed that sits inside `WORK`.

## Decision

**VS Code 1.139.0: clean / 0 lost on `base-union`.** Combined with `EV-40`'s measured absence for the
Gitea family, every client surface for this bead that could be reached has now been reached, and none
of them loses a record on a tree that declares `merge=union`.

This does not demonstrate a need for `asc store verify` in CI. What it does is close the last
reachable hole in `EV-40`'s UNMEASURED list, so that "no measured client loses records on
`base-union`" is a statement about measurement rather than about attention.

**Still UNMEASURED, never `0`:** GitHub's own web conflict editor (a different implementation;
reaching it needs the owner's browser session), GitHub Desktop and JetBrains (not installed).

## Confidence

**High** that the instrument detects the loss shape. The control cell was predicted before running and
landed exactly: `rb0` gone, 4 records, no markers, 0 unparseable lines. A check observed failing is
the precondition for trusting it to pass.

**High** that VS Code's resolution path does not lose records on `base-union`, on the following
chain, each link measured rather than assumed: VS Code's merge delegates to the `git` binary; the
`git` binary on this fixture is measured clean at 5 records; the sole attribute-ignoring path
(`git merge-file`) was measured to ignore the attribute *and* is gated behind an already-open Merge
Editor; and driving the extension's real command in a cell where it *does* have work to do showed it
performing that work.

**Medium on scope, stated plainly.** This is **one version of one product, on macOS**. Two bounds
deserve naming:

- **In the union cell the merge itself was performed by command-line git**, deliberately, because
  that is the binary VS Code delegates to. What the cell measures is that VS Code adds no conflict of
  its own on top of git's clean merge. It does not exercise a VS Code merge path, because at this
  version there is no VS Code merge path that runs before git does.
- **The resolution was saved but never staged.** VS Code left the cell `UU` — the working-tree file
  was rewritten and nothing was added to the index. That is sufficient for this record, since the
  loss is already present in the file at that point and no later step can restore what the save
  dropped, but the full commit-a-resolution flow was not driven.

**Not measured:** the Merge Editor's own accept-incoming/accept-current commands. Reaching them needs
a workspace folder, which raises the Workspace Trust prompt, and the arm deliberately does not
disable that guard. On `base-union` there is nothing for them to open on, so they cannot bear on this
question — but that is reasoning from the gating above, not a drive.
