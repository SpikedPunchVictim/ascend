# EV-49: does the hook fire in a foreign repo, and how many units does one session of that shape produce?

**Question.** `asc-hllr`. `asc-xn4g` built the controlled arm — `asc hook` decides held-out
deterministically from `unitKey(session, agent, segment)`, stays silent for held-out units, and writes
one line per match to `.ascend/exposure/decided.jsonl` — but every test of it ran against a fixture.
No `decided.jsonl` had ever existed in a real project. So the arithmetic of the whole experiment rests
on two numbers nobody had taken, and both were named before anything was run:

1. **Does the hook fire at all in a repository that is not this one?**
2. **How many units per session does a foreign repo's shape actually produce?**

The second is the one that decides feasibility, because `asc handlers compare` needs `MIN_N` (20,
`packages/analysis/src/proportion.ts`) *clean units in each arm*, so ≥40 units at a 50 % holdout. If a
session of n8n's shape yields one unit, that is 40 sessions; if it yields one per compaction, it is
far fewer. Everything after the measurement is arithmetic, which is why the pilot was three sessions
rather than forty.

**Pre-registered before running** (from the pilot option the owner chose, 2026-10-12): *"does the hook
fire at all in this repo, and how many units per session does n8n's shape actually produce."* The
prediction on record was that units track compaction segments, so a long session yields more than one.

**Method.** Working copy `/Users/spikedpunchvictim/temp/ascend-backtest/n8n`, a `git clone --depth 1`
of `n8n-io/n8n` at `cea974e770027a0834e1e7be55fbfb6c23169b03` (2026-10-12), copied out of
`~/temp/enterprise-apps/` as the owner asked. Then:

- `asc init` — store created, starter types installed.
- `handlers/unverified-edit-nudge.yaml` — the **intervention**: a `say:` handler on
  `tool.use.start`, `where: tool in [Edit, Write, MultiEdit, NotebookEdit]`, asking for the package's
  own checks before the edit is reported as done.
- `handlers/edit-unverified.yaml` — the **outcome**, copied verbatim from this repo
  (`on: file.changed`, `window.until: prompt.submit`, `absent: {on: check.run}`).
- `asc install-hook --holdout 0.3 --yes` — the hook, with a 30 % holdout baked into the entry.
- Three headless sessions, `claude -p --model sonnet`, all one shape: *make exactly one small real
  improvement under `packages/workflow/src/`, run the narrowest check that covers it, then stop.*

The first session was run **before** the binary-resolution defect in `dogfood/0082` was found, so it
ran with an inert hook. It is included in the trigger counts and excluded from the decision counts,
and the tables below say which is which.

**A note on the environment, because it is load-bearing for one reading.** The clone has **no
`node_modules`** — a `--depth 1` clone of a pnpm + turbo monorepo was not installed, and the volume
had 13 GiB free. So `pnpm` was never going to run: the sessions attempted checks and were refused.
That is a property of *this* pilot, not of n8n, and it is why the outcome count in Measurement 3 has
to be read with care.

## Measurement 1 — the hook fires, and one session is one unit

| | session A | session B | session C |
|---|---|---|---|
| transcript size | 401.7 KB | 617.0 KB | 371.1 KB |
| `compact_boundary` records | **0** | **0** | **0** |
| Edit/Write tool calls | 3 | 1 | 1 |
| unit (`session`, `main`, segment) | 1 | 1 | 1 |

**`0` compaction boundaries in all three, including the 617 KB session.** The segment index is
therefore always 0, and **one session of this shape is exactly one unit** — the pre-registered
prediction that a long session yields several is *not* what happened, and the reason is structural
rather than statistical: `claude -p` is one turn, and automatic compaction is a property of a
long-running interactive session. A three-session pilot cannot measure the compaction rate of a shape
that never compacts.

`asc handlers check handlers/edit-unverified.yaml --project -Users-…-ascend-backtest-n8n`, over all
14 transcripts in that project directory:

```
(log)            files                              14
(log)            events                             724
edit-unverified  triggers                           6
edit-unverified  rows                               0
edit-unverified  unclosed                           1
edit-unverified  noMatch                            0
```

6 triggers is exactly the number of Edit/Write calls counted out of the transcripts by hand (3 + 1 +
1, plus the pre-fix session's 1), and 4 is the number of streams containing one. The offline replay
of a handler counts the same units the live hook decided.

## Measurement 2 — the controlled arm ran live for the first time

`.ascend/exposure/decided.jsonl`, after the three sessions and one by-hand invocation:

| arm | units | triggers |
|---|---|---|
| `delivered` | **3** | 5 |
| `held_out` | **1** | 1 |
| total | **4** | 6 |

Every line carries `intervention_id`, `intervention_version`, `rate: 0.3`, `session`, `agent`,
`segment` and `tool_use_id`, e.g.

```
{"exposure_id":"unverified-edit-nudge@f096c777…:64866eb1-…\u0000main\u00000:call_cmrj5m9k",
 "intervention_id":"unverified-edit-nudge","arm":"delivered","rate":0.3,
 "session":"64866eb1-…","agent":"main","segment":0,"hook_event":"PostToolUse","tool_use_id":"call_cmrj5m9k"}
```

Three things this settles that no fixture could. **One unit, one arm**: session A made 3 edits and
all 3 took the same arm, which is the design — the arm is per (unit, intervention), so a unit is
delivered or withheld whole, and a reader must not count 5 triggers as 5 independent decisions.
**The held-out unit was silent and still recorded**: its hook invocation emitted no
`additionalContext` and wrote a decision line anyway, which is E30.1/E30.4 end to end. And **the live
count and the replay count agree**: 4 units in `decided.jsonl`, `units 4` from
`asc handlers power` over the same transcripts, derived by two different code paths from two
different sources.

## Measurement 3 — the plan, and why its headline number is not usable from this corpus

`asc handlers power handlers/edited-without-check.yaml --effect 0.5 --holdout 0.3 --project …`:

```
edited-without-check  units                              4
edited-without-check  successes                          1
edited-without-check  active_days                        1
edited-without-check  proportion                         0.25 [0.046, 0.699] 95% Wilson (n=4 < 20: anecdote)
edited-without-check  units_needed                       345
edited-without-check  units_per_arm                      104
edited-without-check  units_per_day                      4
edited-without-check  verdict                            answerable here in 87 active days
```

**`units_per_day 4` is an artifact and the plan built on it is not usable.** The three sessions ran on
one calendar day, so 4 units / 1 active day = 4, and 345 units ÷ 4 = 87 days. That is not a forecast;
it is three sessions in an afternoon divided by one. The honest reading is the one the command itself
already gives beside it — `n=4 < 20: anecdote` — and the number the pilot was actually for:
**at 1 unit per session, 20 clean units per arm is 40 sessions of this shape at a 50 % holdout**, and
more at 30 %.

The `proportion` row is also the first live exercise of the shared renderer (`handler-scope.ts`): it
prints the Wilson interval with the small-group label, which is what `handler-compare.test.ts` pinned.

## Measurement 4 — the outcome the handler watches, and a counter that does not add up

`edit-unverified` (absent: `check.run`) emitted **0 rows over 6 triggers**, and 1 `unclosed`. The 5
windows that are neither were decided by *something matched* — a `check.run` followed the edit — and
are counted nowhere: `triggers 6 = rows 0 + unclosed 1 + noMatch 0` leaves 5 unaccounted.

This is not a fault in the measurement, and it is written up on its own as **`dogfood/0083`**. It
matters here because it is the reason Measurement 3's `successes` must not be read as "n8n's sessions
never check their edits". Over this repo's own corpus the same handler reports

```
edit-unverified  triggers                           5907
edit-unverified  rows                               910
edit-unverified  unclosed                           56
edit-unverified  noMatch                            0
```

— 4 941 of 5 907 triggers (83.6 %) invisible the same way. The counter tuple is the finding; the
number 0 is not a statement about n8n.

## Decision

**The hook works, and the pilot's arithmetic is the answer the pilot was for: at 1 unit per session,
a controlled comparison at `MIN_N` needs 40 sessions of this shape, not the 3 run here.** No further
backtest is justified on this evidence, and the next step is a decision about session count rather
than about tooling.

**What the pilot bought beyond the two answers.** Two defects that no fixture could have produced,
both filed and recorded: `dogfood/0082` — `asc install-hook` reported success in a project where the
hook could not resolve a binary, and **every hook invocation in a whole session was silently inert**;
and `dogfood/0083` — an `absent` window that matches is counted nowhere, so the reader cannot tell
"the watched thing happened" from "the window never opened".

**What this does not show.**

- It does not measure the compaction rate. Zero `compact_boundary` records in three `-p` sessions is a
  fact about the harness, not about n8n.
- It does not show `asc handlers compare` splitting an AFTER arm into delivered and held out. The
  decision log it needs now exists and is well-formed, but only 4 units are in it, which is two orders
  of magnitude short of a split worth comparing. That half of E30.4 remains exercised only against
  fixtures.
- It does not measure the intervention's effect. One delivered-vs-held-out pair is not an estimate,
  and `n=4` is labelled an anecdote by the tool itself.
- It does not show the outcome handler working on n8n, because 5 of its 6 windows landed in the
  uncounted branch (`dogfood/0083`).

**Confidence.** `Confirmed (empirical)` for Measurements 1 and 2: every row is a real command over
real transcripts from real sessions, and the two independent counts of units (4) agree. `Confirmed
(empirical)` for Measurement 3's rows as printed, with the caveat above as the reason `units_needed`
is quoted rather than believed. Measurement 4 is `Traced` — the mechanism is read off the `absent`
branch of `step`'s close loop in `packages/core/src/handler.ts` and confirmed by the same tuple
reproducing on two corpora of different sizes.
