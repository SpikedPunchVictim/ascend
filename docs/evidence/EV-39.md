# EV-39: what an ascend-owned event log costs, and whether the pressure behind it is real

**Status**        Measured 2026-10-03 for `asc-igg8` **(P1)**. Four questions were frozen in
                  `spike/event-log/PREREG.md` before any of them ran, with five pre-registered
                  predictions; **two failed and are reported as failures**. **The headline is that the
                  figure the bead calls *"a measurement rather than an estimate"* and *"the whole
                  argument for the cost"* is not reproducible from any scope constructible from the
                  retained corpus, and the expiry pressure it cites is not observable on this machine.**
                  n = 1 machine, 1 filesystem, 1 project's transcripts, plus a machine-wide read-only
                  sweep for the expiry question.

**Question**      `asc-igg8` asks for a retained event log because *"transcripts expire (~30 days), so
                  every handler count replayed from them is a count over a shrinking window"*, priced
                  at **16,380,630 B raw / 3,937,484 gz for all 16,251 tool inputs in this project's
                  ~35 days**. This spike exists to measure the premise before designing against it:
                  Q1 what the retained shape costs, Q2 whether expiry is observable, Q3 whether
                  concurrent appends interleave, Q4 whether the carried figure reproduces.

**Where it came from**  An audit of the bead's own premise, commissioned as a step of the work rather
                  than stumbled into. It found the cost figure had no recoverable source, which turned
                  the bead from a build into a measurement. **Someone was looking** — see
                  `dogfood/0057`, which records the carried figure and says plainly that it is not a
                  "nobody was looking" case.

## Method

Both scripts are read-only against `~/.claude/projects/-Users-spikedpunchvictim-projects-ascend`;
nothing was copied out of the transcript store. `asc-bolz` froze its corpus with `cp -cR`; that copy
was **declined here by the permission classifier**, so the freeze is a **manifest plus a cutoff
instant** instead: scope = every transcript line whose own `timestamp` is `<= 2026-10-03T09:08:02Z`.
Lines written after the freeze are excluded by construction. This is weaker than a clone in exactly
one way, stated in `PREREG.md`: a file deleted between the freeze and a later re-run changes the
answer and nothing detects it.

`cost.mjs` (Q1, Q4) and `append-race.mjs` (Q3); findings verbatim in `spike/event-log/FINDINGS.md`.

## Measurement 1 — Q1, three candidate shapes

```
scope     : ts <= 2026-10-03T09:08:02.000Z
corpus    : 132 files, 105216 lines, 459944234 bytes

shape                     inputs        raw       gz   gz/corpus
i   full tool inputs     27462   29276075  6221485   1.353%
ii  slim (argv<=4)       27462   22043834  4404292   0.958%
iii full, redacted       27462   29275995  6221477   1.353%
```

Shape (i) is what the bead asks for; (ii) is what `asc-bolz` actually built and measured; (iii) prices
a capture-time redaction mitigation. Redaction is **80 bytes** of 29,276,075 — it costs nothing in
bytes and everything in consequence (Measurement 4).

**The unit caveat, because it flatters the result.** `gz/corpus` divides a *gzipped* log by
*uncompressed* transcript bytes. A like-for-like comparison would gzip the transcripts too and the
share would rise by their compression ratio. **That ratio is not measured** — the sampling run was
denied by the permission classifier and not re-attempted — so the compressed-to-compressed share is
unknown and the 1.353% should not be quoted as though it were one.

## Measurement 3 — Q2, expiry is not observable

Read-only over 188 project directories:

```
projects total: 188 | machine-wide oldest transcript: 2026-08-27T06:45:13.557Z
age of machine-wide oldest: 37.1 days
```

**No retention setting is configured** — neither `~/.claude/settings.json` nor `settings.local.json`
contains `cleanupPeriodDays` or any expiry-related key. The oldest transcript on this machine is
**37.1 days old and still present**, past the ~30-day default the bead cites; this project's own
directory spans **2026-09-12 .. 2026-10-03 (21 days by mtime)**, so the "~35 days" is neither this
project's span nor, on this machine, any project's.

**This shows expiry has not fired, not that it cannot.** The sweep could be disabled by
configuration, or the documented default could differ from the code's. `P4` held on the available
evidence and **the available evidence is weak by construction**: a 21-day project cannot observe a
30-day boundary at all, so `ascend` has never held a transcript long enough to test the premise it is
asked to build against.

## Measurement 4 — Q3, the proposed append mechanism tears

8 concurrent appenders × 3 repeats per cell, lines at an exact known length with their own trailer.
Four writer styles, because the question is not whether `O_APPEND` tears but **how many `write()`
calls the writer makes**:

```
single        0 torn line(s) total; no tearing at any size tested      (one writeSync, up to 1 MiB)
chunk       115 torn line(s) total; first tears at 65536 B (64 KiB)   (64 KiB pieces)
cat         478 torn line(s) total; first tears at 8192 B (8 KiB)     (`cat >> file`, the proposal)
byte       1919 torn line(s) total; first tears at 1024 B (1 KiB)     (1 byte per write)
```

`P3` held, but for a different reason than predicted: **the threshold is not a size.** `cat >> file`
— the literal mechanism the bead proposes — tore in every repeat at 8 KiB and above. Three
properties matter more than the counts:

- **Intermittent, not deterministic.** `chunk` at 8192 B produced 4 torn lines in one run and 0 in the
  next, same code and machine. An intermittent corruption survives every test that does not hit it.
- **Silent.** Line counts frequently matched expectations exactly (`32/32`, `320/320`) while the
  content was torn — the file looks complete and parses as garbage. Severity-zero shape.
- **Avoidable, cheaply.** A single `write()` per line never tore at any size tested.

`cost.mjs` reports **3 of 27,462** blocks changed, against an all-projects rate of 862 of 149,634

```
-…-projects-grizzly-grizz...      49749    209      9        7

-…-projects-ascend                27472      6      9        4
-…-projects-spindle               17318      6      1        1
-…-projects-grizzly-grizz...       5013      5      1        1
-…-projects-grizzly-grizz...       3776      4      2        1
projects with any tool_use: 164
TOTAL blocks 150337  hits 862  (0.573%)
```

**97% of the matches are `grizzly` directories.** The framing given to the owner earlier — *"9.09% of
sessions (21 of 231)"* — pooled 164 projects, and a per-project log carries only its own. For
`ascend`: **6 blocks of 27,472 (0.022%), across 4 of 9 sessions.** This **weakens the framing and not
the conclusion**: `asc export` refuses the whole export on one match with no override (`asc-42i1`) and
entries are immutable, so a per-block rate is a rate at which a project is bricked rather than
dirtied. The 6-versus-3 gap between the two methods is **reported and not resolved** — both are
effectively zero and neither is understood.

## Measurement 6 — the bead's four open questions, taken as far as the evidence carries

The owner chose to design on measured numbers. (a), (b), (c) and (d) each got a measurement; two are
answered outright and two are answered **for today's handlers only**, which is stated where it applies.

**(a) 12 of 14 `EVENT_KINDS` are required.** Read from the seven handlers in `./handlers/`, every
`on:` (including nested window triggers) and every `until:`: 5 kinds are top-level triggers
(`file.changed` ×3, `file.read`, `review.finding`, `agent.spawn`, `tool.use.start`), 5 more are window
or second triggers (`check.run` ×2, `command.run`, `search.run`, `agent.return`, `model.context`), and
2 are window bounds (`session.end` ×2, `prompt.submit` ×2). **Referenced by nothing: `tool.use.end`
and `segment.start`**, and no handler references `is_error` or `segment`. An `until:` is a *retention*
requirement even though nothing keys on it, which is why "only the kinds a handler triggers on" would
be wrong by five.

**(b) The cap mechanism exists; the drop policy does not.** Measured growth ≈ **1.33 MB/day raw /
0.28 MB/day gz** (29,276,075 raw and 6,221,485 gz over a ~22-day content span). Against `asc-8uzh`'s
20 MiB file bound that is **~15.8 days per file** — and rollover appends a higher-index file and never
drops, with no drop-oldest code anywhere in `packages/store/src`. So the cap bounds a *file*, not the
log: it grows ~1.3 MB/day without limit unless a drop policy is chosen. That is what (b) poses.

**(c) Per project, on Measurement 5.** A per-user log pools every project's text, and the risk is
concentrated where this project cannot use it: `ascend` contributes 6 of 27,472 secret-shaped blocks
while four `grizzly` directories contribute 836 of 93,401.

**(d) The per-record cap is not a blocker.** `spike/event-log/record-size.mjs`, same scope:

```
events            : 27462
store per-record cap: 1048576 B (MAX_BYTES_PER_RECORD, refused not rolled)
max               : 60289 B
p99.9             : 21448 B
p99               : 9657 B
p50               : 431 B
over the cap      : 0 of 27462
max / cap         : 0.057x
```

The largest event is **5.7% of the cap and nothing exceeds it**, so a store type can hold these events
without meeting `asc-8uzh`'s refusal — (d) does not turn on the size limit, and the reason to prefer
one shape over the other must come from somewhere other than this measurement. Limitation: **n = 1
project**; a corpus of large file reads could produce a bigger event than `ascend` ever has.

**The bead's open item (2) resolves to "not required".** It said `tool_response`, if retained, is *"the
one number that decides whether (a) above is affordable"*. **No handler references `tool_response`**,
and it is not a field of any declared `EVENT_KIND` — `tool.use.end` carries `tool`, `id`, `role`,
`is_error` (`event.ts:64`) and `duration_ms` rides on `agent.return` (`:116`), which *is* needed. So
the cost basis of Measurement 1 stands without measuring it. This reopens if a future handler wants
output bodies, and that is the boundary of the claim.

## Predictions, including the two that failed

| # | predicted | measured | verdict |
|---|---|---|---|
| P1 | shape (i) gz **< 5 MB**, **< 1%** of corpus | **6,221,485 B**, **1.353%** | **FAILED, both halves** |
| P2 | redaction removes **< 5%** of bytes | 80 B of 29,276,075 = **0.00027%** | passed, **vacuously** |
| P3 | appends tear above a size threshold | tears from **8 KiB**; the threshold is a write-call count | passed, different reason |
| P4 | no deletion observable | none observable; oldest 37.1 days, present | passed, weak evidence |
| P5 | carried figure not reproducible | not reproduced | passed |

**P1's miss is the load-bearing one.** It was predicted from `asc-bolz`'s slim rate of 0.545% gz, on
the reasoning that full inputs are a superset and "the same order". They are not the same order of
*share*: that 0.545% was slim-log-gz over a different corpus. **A prediction built from a carried
ratio fails the same way the carried figure does** — which is the same error the bead made, made
again by this spike, caught only because the prediction was written down first.

## Limitations, plainly

- **n = 1 machine, 1 filesystem (APFS), macOS 25.3.** The append result is this filesystem's.
- **Single-`write()` atomicity is observed, not guaranteed.** POSIX promises atomicity of the *offset*
  under `O_APPEND`, not of the data. 3 repeats per cell is a small n for that negative result: no tear
  was **observed** on `single`, which is not the same as none being possible.
- **The freeze is a cutoff, not a clone**, so a deletion between freeze and re-run is undetectable
  (Method).
- **The compressed-to-compressed cost share is not measured** (Measurement 1).
- **Q2 cannot establish the premise is false**, only that it is unobserved here (Measurement 3).
- The `byte` arm is capped at 8 KiB; the first version of the probe was killed at 600 s with no output
  because 1 syscall per byte at 1 MiB is 32M syscalls.
- **This spike does not settle whether ascend needs the log.** That is a question about which
  questions handlers are asked, not about bytes.

## What follows from it

No mechanism was promoted and none was rejected. What the owner now has, having chosen to design on
measured numbers, is the four open questions answered to the limit of the evidence: **(a)** 12 of 14
kinds, with `tool.use.end` and `segment.start` needed by nothing; **(b)** ~1.33 MB/day raw against a
cap that never drops, so the decision is the drop policy and not the size; **(c)** per project, on the
measured concentration of secret-shaped text; **(d)** the per-record cap is not a constraint, since the
largest event is 5.7% of it.

The cost basis is ~29.3 MB raw / 6.22 MB gz per project per ~22 days, replacing an unsourced figure
that was 1.35× too small. **What is still not settled by any measurement here is whether ascend
*wants* the log** — the pressure the bead exists to relieve is unobserved (Measurement 3), so that
remains a judgement on a corrected number rather than a derived conclusion.

`asc-igg8`'s description is amended to record that its premise is unproven; the bead stays open and
its decision is the owner's.
