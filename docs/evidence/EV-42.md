# EV-42: do `git rebase` and `git cherry-pick` honour `merge=union`? (`asc-3ow4`, P3)

**Status**        Measured 2026-10-04 on **git 2.50.1 (Apple Git-155)**, macOS, on the same fixture
                  as EV-31/EV-40/EV-41. Command-line git only: no forge, no credentials, no browser.

                  **P3 of `asc-3ow4`'s pre-registration is REFUTED on this version.** P3 predicted a
                  conflict for both operations, reasoning from `gitattributes(5)`. Both merge clean at
                  5 records with both appends, on the base where the driver is declared — and both
                  still conflict on the control base, so the driver is what makes the difference.

                  This closes the last open prediction of `asc-3ow4`. The result had been recorded
                  once before as a footnote (`spike/git-layout/FINDINGS.md`: *"Rebase gave the same
                  result as merge in every one of the 24 pairs"*), but the prediction was never
                  exercised against this fixture and stayed *"untested, not confirmed"* through
                  EV-31, EV-40 and EV-41. It is confirmed here, with the fixture, the backend sweep
                  and the naive-resolution cost that the footnote did not carry.

**Question**      `asc-3ow4`'s P3, written 2026-09-28 before any non-CLI merge path was exercised:

                  > **P3 — REBASE-merge conflicts on the second PR.** git itself does not use merge
                  > drivers during rebase/cherry-pick (gitattributes(5)), so the driver cannot save
                  > it. This predicts a conflict even though the equivalent local merge is clean.

                  Two parts, and they are separable: (a) does a rebase or cherry-pick conflict where
                  the equivalent merge is clean, and (b) if it conflicts, does a naive one-sided
                  resolution lose an append silently? (b) is the shape this series hunts — well-formed
                  JSONL, no markers, an append gone.

## Method

Fixture `spike/git-layout/union-fixture.sh` unchanged: `base-union` declares
`records.jsonl merge=union`, `base-plain` is the same tree with `.gitattributes` removed, and
`a-*`/`b-*` each append one record from their own base. **The contrast this rests on is the
fixture's own** — on `base-union` command-line `git merge` is clean at 5 records, on `base-plain` it
conflicts — so both bases run the same operation and any difference isolates the driver, not the
layout.

Arm `spike/git-layout/union-rebase-arms.sh`, checked in because the claim is **version-dependent git
behaviour** with no other record of it: a later git could change either half. It clones the seed per
cell, runs `merge` / `rebase` / `cherry-pick` on both bases, and sweeps the three rebase backends
(`default`, `--merge`, `--apply`) on `base-union`.

**Readings are taken from `records.jsonl` on disk**, both appends reported by name. On a conflicted
cell the two unmerged stages are read with `git show :2:` and `:3:` — so the naive-resolution cost is
measured without touching the tree, and **both** stages are printed because `ours`/`theirs` are
**inverted under rebase**: stage 2 is the upstream commit being rebased onto and stage 3 is the
commit being replayed, the opposite of a merge.

## Measurement

```
git version: git version 2.50.1 (Apple Git-155)

=== base-union ===
  merge (exit 0)         merge=union         5 lines, ra0 present rb0 present markers none
  rebase (exit 0)        merge=union         5 lines, ra0 present rb0 present markers none
  cherry-pick (exit 0)   merge=union         5 lines, ra0 present rb0 present markers none

=== base-plain ===
  merge (exit 1)         merge=unspecified   8 lines, ra0 present rb0 present markers PRESENT
                         -> stage2 keeps ra0 present rb0 ABSENT | stage3 keeps ra0 ABSENT rb0 present
  rebase (exit 1)        merge=unspecified   8 lines, ra0 present rb0 present markers PRESENT
                         -> stage2 keeps ra0 ABSENT rb0 present | stage3 keeps ra0 present rb0 ABSENT
  cherry-pick (exit 1)   merge=unspecified   8 lines, ra0 present rb0 present markers PRESENT
                         -> stage2 keeps ra0 present rb0 ABSENT | stage3 keeps ra0 ABSENT rb0 present

=== rebase backends, base-union (the driver is backend-dependent in principle) ===
  rebase (exit 0)        merge=union         5 lines, ra0 present rb0 present markers none
  rebase --merge (exit 0) merge=union         5 lines, ra0 present rb0 present markers none
  rebase --apply (exit 0) merge=union         5 lines, ra0 present rb0 present markers none
```

**P3(a) refuted.** Every operation on `base-union` is clean at 5 records with both appends — rebase
and cherry-pick included. All three rebase backends agree. `gitattributes(5)`'s traditional statement
does not hold on git 2.50.1 for this attribute and this shape.

**The control holds, so the driver is doing the work.** On `base-plain` the identical three
operations conflict, 8 lines with markers. Nothing about the *operation* differs between the columns;
only `.gitattributes` does.

**P3(b) confirmed for the control, and it is the loss shape.** On every `base-plain` conflict a naive
one-sided resolution drops exactly one append — and because `ours`/`theirs` invert under rebase, the
cell that reads *"stage2 keeps rb0 present"* is the same loss as the merge cell's *"stage2 keeps rb0
ABSENT"*, seen from the other side. Both sides are printed for that reason: an earlier spelling of
this arm printed one side per arm and rendered the rebase cell as though nothing were lost.

**Not on `base-union`, because there is nothing to resolve.** The driver means no conflict arises, so
no resolution — naive or otherwise — is ever reached. That is the whole reason P3 mattered: a
conflict here would have put the loss shape one careless click away on a tree the layout decision
says is safe.

### Instrument notes

Three defects, all in this arm, all found before the numbers above were believed. The first was
caught by reading an exit code rather than an output, which is the only reason it is not a false
green.

- **`git cherry-pick -q` is not a flag.** It exits **129** (usage) and leaves the tree untouched —
  which reads exactly like a clean merge with no appends, since the working tree still holds the
  three base records. Measured on **both** bases before it was fixed: two "results" that were really
  two usage errors. Same class as EV-40's `[type="submit"]`.
- **A row silently vanished.** The backends block called `cell union rebase` for the default backend
  after the main table had already cloned to that path; `git clone` refuses a non-empty target, and
  the `|| return` dropped the row. The arm reported two backend cells where it ran three. Directories
  are now counter-named and a clone failure prints instead of returning quietly.
- **One side per conflict arm reads as "no loss".** See above — corrected to print both stages.

## Decision

**`asc-3ow4`'s P3 is refuted on git 2.50.1, and the last open prediction of that bead is closed.**

What follows for the layout decision, which is what the bead exists to serve:

- **Rebase and cherry-pick join merge as paths that honour the driver.** The set of git operations
  that silently drop an append on a `merge=union` tree is, on this version, **empty** — every
  operation measured either keeps both appends or conflicts loudly.
- **`asc-3ow4`'s P4 holds on all these cells too.** No failure here was silent: the control conflicts,
  and refuses loudly. Combined with the forge arms, **every git and forge path measured across
  EV-31/EV-40/EV-41/EV-42 either honours the driver or refuses loudly** — so the merge guard is still
  **not** promoted to CI on this evidence. The threshold for that is a path that ignores the driver
  *and* still merges.
- **The `gitattributes(5)` claim should not be repeated as fact.** Two of this bead's three
  pre-registered predictions (P2, P3) were refuted by measurement, both by reasoning from documented
  behaviour that the implementation does not follow.

**Still UNMEASURED, never `0`:** GitHub's own web conflict editor, GitHub Desktop and JetBrains — all
three are client surfaces, tracked separately; nothing in this record bears on them.

## Confidence

**High** on the result for git 2.50.1. Three operations × two bases, with the control conflicting
exactly where the union base is clean, so the driver is isolated rather than assumed; all three
rebase backends agree; and every reading is taken from the file on disk with both appends reported by
name.

**High** that the arm's own defects are fixed rather than merely worked around: the cherry-pick cell
now exits 0 on union and 1 on plain, the row count matches the cells run, and the conflict line prints
both stages.

**Medium on scope, stated plainly.** This is **one git version on one platform**, and it is exactly
the kind of behaviour that moves between versions: the merge backend became the default in git 2.26,
and `merge-ort` replaced `merge-recursive` afterwards. Apple's git is a vendor build. A different
version could plausibly answer differently, which is why the arm is checked in.

**Unmeasured:** whether the driver applies during a **rebase across a rollover** (the `one-union`
layout writes into numbered segments, and `spike/git-layout/FINDINGS.md` R1–R3 measured rollover
rebase clean, but not against this fixture), and whether `git pull --rebase` behaves the same — it is
a rebase, and was not run here.
