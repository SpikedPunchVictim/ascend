# EV-17: of the searches that return rows, how many are silent about text the corpus holds?

**Status**      PRE-REGISTERED. The Question, Method and Predictions below were written and hashed
                **before any measurement was taken** (`asc-nai`'s requirement, inherited from
                `asc-9an`: *"Name the question BEFORE running"*). The recorded hash and the exact
                bytes it covers are in *Pre-registration* at the foot of this document.

**Question**    `asc search <type> "<text>"` has two halves. The first is FTS over `evidence_text`.
                The second is the zero-result assist, which scans property values with `json_each`
                and reports the ones carrying the query terms. The assist is built only when the
                first half returns NOTHING:

                    // The assist is built from measurements taken on the zero-result path only. Two
                    // full-corpus counts and one `json_each` scan are affordable exactly because a
                    // caller who got rows never pays for them -- and a caller who got none is the
                    // only one who needs them.
                    const assist = rows.length > 0 ? undefined : buildAssist(...)

                That comment makes two claims of different kinds. The first is about COST ("never
                pays for them") and is measured. The second is about NEED ("a caller who got none
                is the only one who needs them") and is not -- and it is falsifiable: a caller who
                got rows may still need the property-value pass, because the terms can occur in a
                property on entries the FTS half does not hold. Four things were unknown:

                1. **The rate.** On a corpus earned from live workflows, of the searches that return
                   rows, what fraction ALSO match property values elsewhere? That fraction is where
                   the current output is silent about text the corpus demonstrably holds.
                2. **Whether the premise was ever true.** Does a rows > 0 *and* property-match case
                   exist on real data at all, or is the two-entry demonstration that found this an
                   artifact of having built it by hand?
                3. **The shape.** Is the rate driven by common words, or by rare technical terms?
                   This decides whether a single headline number means anything.
                4. **The cost of closing it.** Both halves are already measured on EV-15's corpus
                   (the `json_each` property scan at 0.7275 ms, `countSearchMatches` at 0.0221 ms),
                   so the cost claim can be checked rather than assumed.

                **Why this is not obviously the design.** It is coherent with the name: a
                ZERO-RESULT assist should not fire on results. What is not established is the
                consequence -- whether a term in a property is findable depends on whether an
                unrelated row happens to match the same query. The command's own docblock states
                the principle that makes this matter: *"a search that reported only `[]` would let a
                caller conclude the corpus lacks the term. So the zero-result path reports what was
                searched and where else the terms actually occur."* That reasoning is about what a
                caller would wrongly conclude. It applies at least as strongly when rows came back,
                because then the caller is not looking for a reason to doubt the answer.

**Method**      Two measurements, cheapest first.

                **The corpus is earned, not backfilled.** Real transcripts in `~/.claude/projects`
                (859 files) ingested with the real `asc ingest claude-code`. EV-15's own Limitations
                say its corpus was backfilled, that 4 of its 9 types held 0 entries, and that *"a
                corpus earned from live workflows may set `evidence_text` far more often"* -- which
                would move the common reason and change the balance. This record supplies the corpus
                EV-15 said it lacked. The transcripts are read-only and are never written to.

                **The query set is drawn from the corpus, by a rule fixed here.** For each type, take
                the distinct property values in the corpus, extract terms of 3 or more characters
                (3 is the search floor, measured in EV-15), deduplicate, and search each term against
                its own type. This measures the quantity that decides the question -- of the
                property-value terms a user might actually search for, how many are unreachable?

                **The classification is read off the real command, not inferred.** For each
                (type, term): run `asc search <type> <term> --json` and classify.

                | Outcome | Meaning |
                |---|---|
                | `rows == 0` | the assist fires and NAMES the property match. Visible. |
                | `rows > 0`, term in a property value on an entry NOT in the rows | **SILENT** -- text the corpus holds, unreachable by the query that should find it |
                | `rows > 0`, no property match elsewhere | plain result. Nothing withheld. |

                **The losing side is reported.** `TASKS.md` requires the arm that loses to be
                reported with its numbers. The visible fraction is reported beside the silent one, so
                the design's own choice is measured rather than merely indicted.

                **Cost is measured on this corpus too**, since EV-15's numbers came from a corpus
                with different `evidence_text` density and a different entry count.

**Predictions** Recorded before running, so a negative result is detectable rather than
                reinterpreted:

                | # | Prediction | Confidence |
                |---|---|---|
                | P1 | The SILENT case EXISTS on real data, not only in a hand-built fixture. | high -- the two-entry demonstration shows the mechanism is real; the open question is rate, not existence |
                | P2 | Among searches that return rows AND have a property match somewhere, the silent case is the MAJORITY (> 50%). | medium |
                | P3 | The rate is driven by common words. Removing the most common terms should drop it sharply, which would mean a single headline number is misleading and both must be reported. | medium |
                | P4 | Closing it costs under 1 ms per search, so if P2 holds the cost premise does not survive its own numbers. | high -- both components are already measured |
                | P5 | EV-15's own illustration (`cargo` against `verification_run`) is NOT in the silent case, because that type is an unconditional zero. If so, the record must say that the design was illustrated with the case where it works. | medium |

                **A negative result is a successful task.** If the silent case turns out to be rare
                -- say under 1% -- then the current design is right, the cost trade-off is correct,
                and `asc-nai` should be closed as designed-behaviour with the number as its record.
                That outcome is worth as much as the other, and it will be reported the same way.

## Measurement

### The corpus, earned rather than backfilled

859 transcript files under `~/.claude/projects` were ingested with the real `asc ingest claude-code`
-- 455,600 records, 0 malformed, 0 unreadable -- into a project at `/tmp/nai`. The transcripts were
read and never written to. The resulting store holds **1,574 entries**:

| type | entries | with `evidence_text` |
|---|---:|---:|
| tool_denial | 499 | 0 |
| verification_run | 497 | 0 |
| context_compaction | 471 | 0 |
| skill_activation | 87 | 0 |
| user_correction | 20 | **20** |
| **total** | **1,574** | **20 -- 1.3%** |

### A structural fact that bounds the whole question

**Four of the five types have no indexed content at all**, so for them `searchScope` reports
`indexed == 0`, every query returns `rows == 0`, the assist fires unconditionally, and the silent
case is *impossible*. That is not an inference: it is what the command reports. Against
`tool_denial`, a term the corpus holds 446 times gives

```
assist: { reason: "nothing-indexed", entries: 499, indexed: 0,
          values: [ { property: "tool_name", value: "Bash", entries: 446 } ] }
```

The silent case can therefore occur in **exactly one type**: the one whose values are prose. Verified
on a 25-term sample per zero-index type -- `rows == 0` in 100 of 100, as the structure requires.

This also disposes of EV-15's prediction that a live corpus "may set `evidence_text` far more often".
It does not. Measured 20 of 1,574 = **1.3%**, against the backfilled corpus's 20 of 1,491 = **1.3%**
-- the same count and the same rate. The mechanism is in the code, not the provenance:
`derive.ts:69` assigns evidence text to "the ONE type whose value is prose", and `derived-types.ts:130`
says it "holds what the user actually said and which no other type records." The density is a
property of the adapter's fixed derivation rules.

### The exhaustive arm: every term, in the one type where the outcome is unknown

102 distinct terms of 3 or more characters occur in `user_correction`'s property values. All 102 were
searched against their own type through the real binary. Results, read off the command rather than
inferred:

| outcome | count |
|---|---:|
| `rows == 0` -- the assist fires and names the property match | 95 |
| **SILENT** -- `rows > 0`, and a property holder is not among the rows | **7** |
| plain -- `rows > 0`, every property holder was among the rows | **0** |

**SILENT as a share of all searches: 7/102 = 6.86%.**
**SILENT as a share of searches that returned rows: 7/7 = 100.00%.**

All seven, with the property each term came from:

| term | property | rows returned | entries holding it | withheld |
|---|---|---:|---:|---:|
| `2026` | occurred_at | 1 | 20 | 19 |
| `users` | project | 1 | 20 | 19 |
| `<user>` | project | 1 | 20 | 19 |
| `projects` | project | 1 | 20 | 19 |
| `<project-G>` | project | 2 | 3 | 1 |
| `exp` | project | 3 | 2 | **2** |
| `bash` | tool_name | 1 | 1 | **1** |

### The two sharpest cases, driven by hand

`exp` is the clearest. Three rows come back and every one is a substring collision:

```
"... are **exp**osing...."     "...i is **exp**licitl..."     "...* We need **exp**l..."
```

Both entries whose project directory is actually named with an `exp` prefix are withheld, and no
assist appears. A search for a project's own name returns three irrelevant passages and none of the
entries from that project.

`bash` is the one that matters for this project. Searched against the type that holds the term:

```
$ asc search user_correction bash --json
  rows: 1   -- a correction whose PROSE QUOTES the word "Bash"
  no "assist" key at all. The correction whose tool_name IS "Bash" is withheld.
```

Searched against a type that indexes nothing at all:

```
$ asc search tool_denial bash --json
  rows: 0   assist.values: [{ "property": "tool_name", "value": "Bash", "entries": 446 }]
```

**The type that indexes nothing names the property match 446 times over. The type that indexes, and
that actually holds the term, says nothing.** The assist's availability is inversely related to how
close the query came to succeeding.

### The bead's constructed case, reproduced

`asc-nai` offered a two-entry case and flagged it as constructed. It reproduces verbatim. Two
`stuck_event` entries recorded through the real CLI into a throwaway project at `/tmp/nai2`:

```
A: --prop=error_text="DEPMOD_QQQ the module could not be resolved"
B: --evidence="dependency work: the module could not be resolved"

$ asc search stuck_event module
  id                                    score      snippet
  1f256513-bfae-4558-8499-86b4fe565035  -0.000001  ...the **module** cou...
```

One row, no assist, and entry A -- whose `error_text` is a literal substring match for the query --
is never mentioned. The mirror case shows what was lost: searching a term that happens to appear only
in A's property returns `rows == 0` and the assist names it exactly
(`error_text = "DEPMOD_QQQ the module could not be resolved"`, 1 entry). Both terms occur in the same
`error_text`; one finds it and the other does not.

This is the case the brief is built around. `stuck_event.error_text` says of itself that the exact
text "is what makes this findable by a later search", and `asc-4so.1` tightened `record_when` to tell
a recorder to preserve it. Here the entry is in the store, the term is a literal substring of it, and
`asc search` answers as though it does not exist.

### P4: the cost of closing it, on this corpus

Both components measured in-process against the real store, so no CLI startup is in the number:

| call | ms/call (n=200) |
|---|---:|
| `searchEntries` -- the FTS half the caller already pays for | 0.1210 |
| `searchScope` -- two `COUNT`s | 0.0376 |
| `propertyValueMatches` -- the `json_each` scan | 0.0852 |
| `countSearchMatches` -- one `COUNT` | 0.0488 |

Closing the silent case on the `rows > 0` path costs `searchScope + propertyValueMatches` =
**0.1228 ms**. That is **1.01x** the search itself: **the assist roughly doubles the query.**

So P4 is confirmed against its stated threshold (< 1 ms), but the threshold was the flattering
framing. The honest statement is the ratio, because the ratio is what survives a larger corpus and
the absolute number does not. EV-15 measured the same `json_each` scan at **0.7275 ms** on its own
corpus; this record measures **0.0852 ms** on a type of 20 entries. The two differ by roughly 8x and
both are correct for their corpus -- which is the scaling worry, visible in the project's own
numbers.

### Predictions, scored

| # | Prediction | Outcome |
|---|---|---|
| P1 | The SILENT case EXISTS on real data | **Confirmed.** 7 cases, on both the earned corpus and a recorded one. |
| P2 | Majority (> 50%) among searches that return rows AND have a property match | **Confirmed and exceeded -- 100%.** There were **zero** plain cases: in this type a search that returned rows never once returned all the holders. |
| P3 | The rate is driven by common words; removing the most common terms should drop it sharply | **Refuted as operationalized, confirmed in spirit.** See below. |
| P4 | Closing it costs under 1 ms | **Confirmed** (0.1228 ms) -- with the ratio correction above. |
| P5 | EV-15's `cargo`/`verification_run` illustration is NOT in the silent case | **Confirmed.** `verification_run` has `indexed == 0`, so `rows == 0` always and the assist always fires. EV-15 illustrated the boundary with the one case where it works. |

**P3, precisely.** The prediction's concern -- that a single headline number would mislead -- is
right, but its mechanism is wrong. The rate is not driven by how common a term is. It is driven by
whether the property value **overlaps natural-language prose**:

| property | terms it contributes | silent | rate |
|---|---:|---:|---:|
| session_id | 50 | 0 | **0%** |
| occurred_at | 39 | 1 | 2.6% |
| project | 10 | 5 | **50%** |
| tool_name | 3 | 1 | 33% |

`session_id` contributes the *most* terms of any property -- 50 of 102, all UUID fragments, the most
"common" values in the type -- and produces **zero** silent cases, because a UUID fragment never
appears in prose. `project` contributes 10 terms and is silent half the time, because
`/Users/.../projects/...` is made of words a sentence also uses. Removing common terms would not have
dropped the rate; removing *path fragments and bare tool names* would have. So both numbers must be
reported and neither is the headline: **6.86% of property-derived searches, and 100% of those that
returned rows.**

## Decision

**The pre-registered negative-result exit does not apply.** It was conditioned on the silent case
being rare -- "under 1% -- then the current design is right ... and `asc-nai` should be closed as
designed-behaviour with the number as its record." The measured rate is 6.86% overall and, more
sharply, **100% of the searches that returned rows withheld something.** The bead's own test was
"if it is rare, this is a footnote; if it is common, the silent answer is a real findability defect."
It is common.

**`asc-nai` is therefore confirmed as a real defect, not closed as designed behaviour.** Its scope is
narrower than the bead's framing and its severity is higher. Narrower: the silent case is confined to
**one of the five types**, because four have nothing indexed and can never exhibit it. Higher: within
that type it is not occasional -- there is not one measured search that returned rows and withheld
nothing.

**The fix is not decided here, and the measurement does not decide it.** The pre-registration
committed this record to measuring the rate and the cost, not to choosing a remedy, and `asc-nai`
said plainly: *"do not treat the fix as obvious."* What the numbers give the decision:

- The remedy is cheap in absolute terms (0.1228 ms) and expensive in relative terms (1.01x, doubling
  every search that today pays for one) -- so "always build the assist" is a real trade, not a free
  one, and the relative cost is the one that grows.
- The remedy changes the `--json` output contract, which `cli-best-practices` treats as versioned API
  and which is at `OUTPUT_CONTRACT_VERSION = 1`. That makes it expensive to reverse.
- A condition on the fix is available that the rate data supports: the defect is *total* among
  searches returning rows in the one type that indexes, so a remedy gated on "did this search return
  rows" is exactly the gate that never fires when it should.

Because the change touches a published output contract and is expensive to undo, the choice belongs
to the user rather than to this record. It is put to them with these numbers attached.

## Confidence

**High** that the silent case exists, that it is confined to the type with indexed content, and that
it is total among searches returning rows in that type. Every number above was read off the real
binary or the real store; none was inferred from the schema. The mechanism was confirmed twice over:
on a corpus of 859 earned transcripts, and by reproducing the bead's own constructed case through
`asc record`.

**Medium** on how the rate generalises beyond this corpus. It rests on 102 terms in a 20-entry type
-- 20 corrections out of 1,574 entries, which is what the adapter's rules produce today, not a
ceiling. A type with richer prose would move the rate; whether up or down is not measured.

## Limitations

- **The query set is property-derived, not user-authored.** The 102 terms are drawn from
  `user_correction`'s property values by the pre-registered rule. A human searches with words they
  already believe exist; these are drawn from what the store holds. That biases the sample *toward*
  terms that exist in properties, which is the quantity the question is about -- but it is a
  different distribution from a user's, and the 6.86% must not be read as "6.86% of real searches".
- **One type, 20 entries, one corpus.** The silent rate is measured where it can occur, which is a
  single type of 20 entries. Nothing here measures a large indexed type, because the corpus has none.
- **The cost figures are one corpus and one machine.** `searchEntries` at 0.1210 ms and the assist
  increment at 0.1228 ms both scale with corpus size; EV-15's 0.7275 ms for the same `json_each` call
  shows the spread. The ratio is more portable than either absolute number, and neither is a
  prediction for a large store.
- **The `--limit` bound.** Searches ran with `--limit 200`. `user_correction` holds 20 entries, so no
  result was truncated. In a type large enough to truncate, "a holder not among the rows" could be
  produced by the limit rather than by the FTS boundary -- this corpus cannot produce that case, and
  the classification would need the limit accounted for before the rate transfers.
- **The constructed case used a type this corpus does not contain.** `/tmp/nai2` is a throwaway
  project with two hand-recorded `stuck_event` entries. It reproduces the bead's case exactly, but it
  is a constructed demonstration of the mechanism, not a measurement of its rate. The rate comes from
  `/tmp/nai` alone.
- **Not measured: whether `asc search` is used in practice at all**, or by whom. The defect is real
  whenever the command is used; its impact depends on adoption, and nothing here measures adoption.

## Addendum: the same query set, after the fix

`asc-nai` was confirmed by this measurement and the remedy chosen was **always build the assist**
(the property pass now runs on every search, not only on a zero result). This addendum re-runs the
identical query set against the fixed binary. It was written after the fix and below the seal, so
nothing above it moved.

**The classification had to change, and the reason is worth stating.** The pre-fix rule called a
search SILENT when rows came back and a property holder was not among them. That rule **cannot** be
reused to check the fix: the FTS half is a full-text search, so it is *supposed* to return only the
entries whose evidence matches. The omission from the row list was never the defect. The defect was
that nothing said the omission had happened. So the post-fix question is the one a caller actually
asks:

    UNREPORTED -- rows came back AND no reported property value contains the term.

That is strictly stronger than "the `assist` key is present", because an assist that appeared and
named nothing would leave the term exactly as unreachable as before.

| | before | after |
|---|---:|---:|
| terms searched | 102 | 102 |
| `rows == 0` -- assist names the reason | 95 | 95 |
| `rows > 0` | 7 | 7 |
| of which UNREPORTED | **7** | **0** |
| UNREPORTED as a share of searches returning rows | 100.00% | **0.00%** |

The FTS half is untouched by the fix, so the row counts are identical -- 95 and 7, the same seven
searches. What changed is that all seven now report where else their terms occur.

Driven by hand on both corpora that exhibited the defect, through the real binary:

```
$ asc search user_correction bash --json
  rows: 1
  assist: { reason: "rows-returned", entries: 20, indexed: 20,
            values: [ { property: "tool_name", value: "Bash", entries: 1 } ] }

$ asc search stuck_event module --json          # asc-nai's own constructed case
  rows: 1
  assist: { reason: "rows-returned", entries: 2, indexed: 1,
            values: [ { property: "error_text",
                        value: "DEPMOD_QQQ the module could not be resolved", entries: 1 } ] }
```

Both were silent before. The second is the case the brief is built around: `stuck_event.error_text`
is where the verbatim failure text goes, and it now says so on a search that already returned a row.

**The four guards were mutation-tested, and all four fired.** The project's invariant is that a check
must be shown to fail before it is trusted to pass. Each of these restores a piece of the pre-fix
behaviour and each is caught:

| mutation | caught by |
|---|---|
| restore the `rows.length > 0 ? undefined : ...` gate at the call site | `search-cli.test.ts` > "offers the property values a RESULT SET does not cover" |
| drop the `rows-returned` case from `assistReason` | `search-assist.test.ts` > "names returned rows ahead of every zero-result code" |
| print the `no matches.` lead line on every path | `search-assist.test.ts` > "does NOT say \"no matches\" when rows came back" |
| drop the completeness line when rows came back | `search-assist.test.ts` > "says the result is complete when rows came back" |

Two things about that round are recorded because they are how a mutation round lies. **A mutation has
to be the whole pre-fix state**: restoring the gate alone does not compile, because the output line it
fed was conditional too (`exactOptionalPropertyTypes` rejects `assist: SearchAssist | undefined`), so
the one-line version produced a type error rather than a behaviour. And **a round that throws must
still restore**: the first run crashed inside the build and left a mutant in the working tree, which
would have made every later round a measurement of mutated source. The run now restores in a
`finally` and verifies both files byte-identical by hash at the end.

**Limitations of this addendum.** It measures that the term is *reported*, not that a caller reaches
it -- whether a model reading the assist goes on to use it is the adoption question
`empirical-planning` P5 separates from availability, and it is not measured here. It also runs only
against the earned corpus at `/tmp/nai` and the two-entry project at `/tmp/nai2`; the four zero-index
types are not re-measured because the fix cannot change them, `rows == 0` there by construction.
