# EV-32: what does it cost to rebuild a store's derived index from JSONL, at real scale?

**Status**        Measured 2026-09-28 for `asc-i5tj`. **The question was named before measuring, but no
                  numeric predictions were registered in advance** — so this is a measurement, not a
                  test of a hypothesis, and it is recorded as such rather than dressed up as one. One
                  real corpus and one synthetic scale point; n is small and the second is not real
                  data. The JSONL store itself does not exist yet, so the rebuild was timed through
                  the *nearest existing code path* (`asc import`), which is stated below as a proxy
                  with a known bias rather than treated as the real thing.

**Question**      The owner decision for `asc-i5tj` puts records in git as JSONL behind a
                  storage-neutral read layer, with **a derived, rebuildable index**. "Derived" and
                  "rebuildable" are cheap words to write and expensive to get wrong: they decide
                  whether the index is rebuilt on every open, kept persistent with a staleness check,
                  or updated incrementally per record. Those are three materially different builds.
                  So: how long does a full rebuild take at this project's real size, how does that
                  scale, and what does a single write cost at the same size?

## Method

**The rebuild is already implemented, under another name.** `asc import` rehydrates an entire store
from the `asc export` corpus — type definitions, entries, schemes, annotations — through
`recordEntry`, `registerScheme`, `recordAnnotations` inside one transaction. That is the same work a
derived index build must do, so it can be timed today without writing any of the new store.

**The corpus is this project's own store**, not a fixture: `asc export` emitted 10,240 lines /
7.77 MB — 16 `type`, 6,329 `entry`, 7 `scheme`, 3,888 `annotation`.

**A second point at 10×**, because one size is a home-field measurement. The corpus was replicated
10× with each entry given a distinct sha256-derived id, its `recorded_at` shifted 1–10 days earlier
(so copies interleave in time rather than appending in a block), and its `evidence_text` tagged with
the copy number. Types and schemes are emitted once — they are content-addressed and must not
duplicate. Result: 102,193 lines / 71 MB, 63,290 entries. **This is synthetic replication, not real
data**, so it exercises the size and validation path but not the distribution of a genuinely larger
corpus.

Every rebuild ran against a **fresh, empty `.ascend/`**, wall-clock timed with `/usr/bin/time -p`.
Writes were timed five times each against the *already-built* stores.

## Results

Every number below is verbatim tool output.

```
=== export (serialize 6,329 entries to JSONL) ===
real 0.656         10,240 lines / 7.77 MB

=== cold rebuild #1 — 6,329 entries, 7.77 MB JSONL in ===
real 3.02          -> 22,073,344 B store

=== cold rebuild #2 — 63,290 entries, 71 MB JSONL in ===
real 40.27         -> 205,922,304 B store

=== single write, end to end, already-built store ===
21 MB store:   0.25 0.19 0.18 0.19 0.19 s
208 MB store:  0.19 0.18 0.21 0.19 0.19 s
```

Derived (arithmetic on the above, not separately measured):

| quantity | 6.3k entries | 63k entries | ratio |
|---|---|---|---|
| cold rebuild | 3.02 s | 40.27 s | **13.3×** time for **10×** records |
| per-record | 0.477 ms | 0.636 ms | 1.33× |
| store bytes on disk | 22.1 MB | 205.9 MB | 9.3× |

**Fingerprint cost**, because a persistent index needs to know when it is stale:

```
sha256 of 7.77 MB JSONL:  real 0.05
sha256 of 71 MB JSONL:    real 0.24
```

**Record sizes**, because the rollover rule rolls at *5,000 records or ~20 MB* and which binds first
depends on them:

```
type        n=16     mean=3347B p50=2947B p95=10142B p99=10142B max=10142B
entry       n=6329   mean=840B  p50=758B  p95=1101B  p99=2697B  max=9046B
scheme      n=7      mean=365B  p50=282B  p95=672B   p99=672B   max=672B
annotation  n=3888   mean=614B  p50=668B  p95=725B   p99=725B   max=1167B

5,000 records at mean entry size = 4,101 KiB
20 MiB of entries = 24,970 records at mean size
20 MiB binds before 5,000 records only if mean record > 4,194 B; p99 is 2,697 B, max is 9,046 B
```

## What the numbers decide

1. **Rebuild-on-open is out.** 3.02 s is not a per-command cost, and 40.27 s is far past it. The
   index must persist and be rebuilt only when its inputs change.
2. **A content-hash fingerprint is affordable, so no mtime heuristic.** Hashing the whole JSONL set
   costs 0.05 s at 7.8 MB and 0.24 s at 71 MB. That is cheap enough to do on every open — which
   matters because **mtime is the wrong signal here**: `git checkout` and `git switch` stamp files
   with the *current* time even when content returns to a state the index already holds, so an
   mtime-based check forces a spurious multi-second rebuild on every branch switch. A content hash
   answers that case correctly for 50 ms.
3. **No incremental machinery.** Because the rebuild is wholesale-cheap, the design is
   wholesale-or-nothing behind a fingerprint: no partial rebuilds, no per-record index bookkeeping,
   no dirty-region tracking.
4. **The write path pays nothing.** 0.19 s end-to-end at *both* 21 MB and 208 MB — a single insert
   into a 10× store is indistinguishable from one into a 1× store, i.e. below process startup. So a
   write is "append one JSONL line, apply that one record to the index", and the index-apply cost is
   not measurable at this scale.
5. **The 20 MB rollover cap is near-dead code at measured sizes.** Entries average 840 B, so 5,000
   records is 4.1 MiB — the byte cap would need a mean record above 4,194 B to bind first, and the
   p99 is 2,697 B. The record-count threshold binds first by roughly 5×. This belongs to `asc-8uzh`.

## What this does NOT measure — and one reason to distrust it as a ceiling

- **The proxy is not the real code path.** `asc import` validates every record, restores schemes, and
  re-registers views — plausibly *more* work than a from-scratch index build that reads lines it
  trusts. So 3.02 s is likely an **upper bound**, but "likely" is not measured, and the real build
  path must be re-timed once it exists. Recorded now because it is enough to choose the architecture,
  and choosing the architecture is what blocks the work.
- **The 10× point is synthetic.** It is one real corpus replicated, so it measures size scaling, not
  a real large corpus's shape. A genuine second project's store would be the honest n=2.
- **Warm cache, single run each.** The rebuilds were not repeated or run cold-cache; 40.27 s carries
  18.58 s of `sys` time (I/O to write a 206 MB file), which a cold page cache would worsen.
- **Nothing here measures the read-time contradiction check** (`asc-2ezs`) or the merge guard
  (`asc-98e1`), both of which add work to paths not yet built.
- **The rollover arithmetic assumes one entry per record.** Annotations and types are separate files
  at their own sizes; only the `entries/` tree was costed.
