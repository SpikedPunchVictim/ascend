# EV-54: do three event-stream detectors yield betterments with a stated number?

**Status**      Measured 2026-10-13 for `asc-m54z`. The four predictions were written into the bead's
                notes before the script existed. They were not sealed by sha256, so this is weaker
                than `EV-52`'s pre-registration. Everything under "Refinements" was added after the
                first pass was read and is exploratory.

**Question**    `EV-53` found the derived tables were the limit: no denominators, no command text.
                If three detectors read the adapter's event stream instead, joined to the size of
                each tool result, does each produce at least one betterment that states a number
                and rests on 20 or more sessions?

## Method

One scratch script, read-only on `~/.claude/projects`, over every non-ephemeral transcript. It
feeds each record to `createNormalizer()` and keeps `file.read`, `file.changed`, `command.run`,
`segment.start` and `tool.use.start`. From the raw record it also takes what the event stream does
not carry: the UTF-8 byte length of each `tool_result`, each `Read` call's `offset` and `limit`,
each Bash command's text, and the size of each `attachment` record.

- **Context tax.** Bytes injected per attachment source, per instruction file, and per skill
  listing; bytes returned per tool and per first command of a Bash call.
- **Repeat reads.** A `file.read` is a strict repeat when the same path, with the same `offset`
  and `limit`, was read earlier in the same stream and compaction segment with no `file.changed`
  to that path since.
- **Repeated command sequences.** 3-grams of `command.run` tokens (the head, plus the subcommand
  for `git`, `pnpm`, `bd` and similar) within a stream, counted by distinct sessions.

**Bytes are measured. Tokens are not.** Any token figure below is bytes divided by 4 and is an
estimate. Injected content is usually served from the prompt cache, so its bytes say how much of
the context window it holds, not what it cost.

## Predictions

- **P1.** At least 15% of `file.read` events are strict repeats. *Falsifier:* under 15%.
- **P2.** The largest hook-injected source by total bytes is the beads SessionStart hook, and Bash
  is the tool with the most result bytes. *Falsifier:* either is not first.
- **P3.** At least one 3-gram with two or more distinct tokens recurs in 20 or more sessions.
  *Falsifier:* none does.
- **P4.** Each detector yields at least one betterment that states a number and rests on 20 or
  more sessions. *Falsifier:* any detector yields none.

## What the detectors found

**Context tax found three things, each with a number.**

1. **Skill listings.** 2,266 listings hold 61,122,335 bytes, 26,974 a listing, naming 136 skills on
   average. 540 distinct skills were listed and 14 were ever invoked through the `Skill` tool.
   This rests on 450 sessions.
2. **Project instruction files.** grizzly-exp's `CLAUDE.md` is 38,533 bytes a load and was loaded
   614 times; grizzly-sv's is 47,594 over 402 loads and grizzly-pl's 48,152 over 389. A load
   happens per stream, so every subagent pays it. The session counts (11, 1 and 2) are under
   `MIN_N`, so by session this is an anecdote; by load it is not.
3. **The beads hook does not arrive.** `bd prime` printed a median of about 48KB at SessionStart.
   In 309 deliveries the harness stored it to a file and gave the model the first 2KB. Eight tool
   calls in six transcripts ever opened one of those files. The project's persistent memories sit
   past the 2KB mark. Nobody was looking for this; the detector was sizing hooks.

Smaller: 1,848 `--help` calls, 3,129,902 bytes, across 855 stream segments in 34 sessions.
`bd create --help` ran 51 times in 44 segments and `asc record --help` 42 times in 41, which is
about once per segment: the flags are looked up again after each compaction.

**Repeat reads is a clean null.** Under either tool, a file is almost never re-read unchanged
within a segment.

**Sequences found no script to write.** At the shell-segment level the grams are plumbing. Per
call with plumbing removed, seven 3-grams reach 20 sessions and all are `git add`, `git commit`,
`git log`, `git status` in some order. The most widespread exact command appears in 7 sessions.

## Decision

**One detector of three is worth building, and it was the cheapest.** Sizing what is injected
into every stream produced three betterments from one pass with no statistics at all. The two
detectors that looked for repeated behaviour found that the behaviour is not repeated at the
grain they measured.

For the betterment tool this narrows the first version: measure standing costs (instructions,
listings, hooks, help look-ups) before hunting for behavioural patterns. It also shows the event
stream was not enough alone. Every finding here needed a size, and sizes are in the raw record.

## Confidence

**High** for the counts: whole populations, zero malformed lines, zero read failures.

**Medium** for "14 of 540 skills are used". A skill the user typed as a slash command may not pass
through the `Skill` tool, and the 540 are names seen across every project and plugin version, not
the number installed today.

**Low** for any saving. No betterment was applied, so nothing here is graded, and bytes are not
cost. Whether the unread beads memories changed any outcome is not measured.

**Limitations.** One user, one machine. 454 sessions exist by file, and only 88 main streams hold
a tool call of the kept kinds; the rest are short headless runs that still pay the listing and
instruction load. A Bash result is attributed to the call's first command only. The refinements
(instruction files, skills used, `--help`, per-call grams, the hook follow-up) were chosen after
the first pass was read.
