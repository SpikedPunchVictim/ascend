# EV-26: is the model per stream in the transcript-derived log, and can it stratify the comparison it was built for?

**Status**      Measured 2026-09-26 for `asc-6ola.10`, `derive_version` 3. The event is built and
                green, and it reads the model and harness version off the real corpus end to end.
                **Two of the three figures the approved plan carried did not reproduce**, and the
                third is confirmed — see Predictions. The stratification the bead exists for
                **cannot be made from this project's corpus**, for a reason that is about where
                the data lives rather than about the event.

**Question**    For `asc-6ola.10`: *is the model active per stream in the transcript-derived log,
                so that a holdout comparison can be stratified by it?* The bead names the purpose
                explicitly -- "*nothing on its own. It is the stratification key for every holdout
                comparison, because compliance differed by model (5/8 haiku vs 1/3 sonnet,
                `asc-6ola.4`, anecdotes)*" -- and claims the data is *"Not in the transcript-derived
                log; data arrives with live capture."*

## Method

Three measurements, all read-only over `~/.claude/projects`, all on 2026-09-26, and the first
repeated after the code was written so the numbers come from the shipped path rather than from a
sketch of it:

1. **The field exists.** Streamed this project's 87 transcripts and counted, per assistant
   record, whether `message.model` and a top-level `version` are present, and what values they
   take.
2. **What the rule emits.** The normalizer change in Stage 3, driven over the same corpus through
   `createNormalizer` / `streamCorpus` from `packages/adapter-claude-code/dist/index.js` — the
   production path, `derive_version` 3. Scratch scripts in the gitignored `spike/tmp/`, named in
   the record so the numbers can be re-checked.
3. **Where the models are.** The same sweep over **1,231 transcripts across every project**, split
   by main/subagent transcript and by whether the project label is one `isEphemeralProject`
   filters (`packages/adapter-claude-code/src/ephemeral.ts:79`).

Horizon for the project figure: 87 streams, 87,147 records, 112,378 events,
2026-09-12T01:07:55.847Z → 2026-09-26T10:02:14.716Z, `derive_version` 3, counters
`unpairedResults` 0, `unfinishedCalls` 1, `unmatchedNotifications` 55, `syntheticModelRecords` 12.
The project directory is written below as `-Users-<user>-projects-ascend`; the real name is
redacted, the measurements are not.

**No PREREG was written to the bead before these counts.** The plan registered a method and
carried three figures from an earlier design pass, but it did not register predictions I had
measured myself, and the counts were already running when that became clear. Recorded as a
process miss rather than dressed up: the Predictions section below marks each carried figure as
**carried, not pre-registered by the measurer**, and none of them is treated as a prediction that
was "hit".

**A stream's model changing mid-stream is rare: 7 of 1,231 (0.57%)**, split 1 main / 6 sub. A
harness version changing mid-stream is **never** observed in 1,231 streams, so the version
trigger is carried on the strength of the unit test alone and this record says that plainly.

**The distinction that matters, and the one the carried figure was probably reaching for:** 23 of
190 sessions hold more than one model across their files (12 hold none, 155 hold one, 13 hold
two, 10 hold three) — because a session's subagents routinely run on a different model than its
main stream. At the **session** level the model is genuinely ambiguous; at the **stream** level it
never changes (7/1,231). So per stream is not merely a convenient choice, it is the level at which
"which model served this" has one answer.

And where the models live — the measurement that decides whether the stratification is possible:

```

  "other": 239777, "otherEphemeral": 355, "otherOutside": 239422 }
```

**1,051 of the corpus's 1,080 `claude-haiku-4-5-20251001` assistant records (97.3%) sit under
ephemeral OS-temp-rooted project directories.** Those are the directories `isEphemeralProject`
excludes and `streamCorpus` skips unless `includeEphemeral` is set
(`packages/adapter-claude-code/src/reader.ts:247`); `asc handlers check` names exactly one project
and does not pool. **This project's 87 streams contain no haiku record at all.**

So: the event is the right stratification key and it is now in the log, but **the comparison
`asc-6ola.10` exists for cannot be made from this project's corpus** — the arm that differed lives
in other projects, and 97.3% of it lives in directories a default sweep will not walk. That is a
finding about the comparison, not about the event, and it is filed (`asc-pps4`) rather than
worked around.

## Limits

- **One operator, one machine.** The 1,231-transcript figure is one person's whole Claude Code
  history; the ephemeral share is a property of how that person's scratch work is laid out, and
  nothing here bounds it for anyone else.
- **The corpus is live.** `records` moved 86,556 → 87,147 and `events` 111,730 → 112,378 between
  the `.9` run and this one; `streams` was 87 in both.
- **The model-change branch has 7 observations corpus-wide and 0 in this project.** Under
  `MIN_N` (20, `packages/analysis/src/proportion.ts:50`), so "0.57% of streams change model" is
  named as an anecdote, never a rate.
- **`harness_version` changes are never observed mid-stream.** Asserted in the real-corpus test as
  "every context event carries one" (1,226/1,226), which is coverage of the field, not of the
  trigger.
- **The 12 `<synthetic>` assistant records** in this project are harness-injected and skipped; the
  count is a counter, not a claim that 12 is a meaningful number.
- **The two carried figures I could not reproduce are not explained here.** Their denominators
  match and their numerators do not, and I did not determine the method that produced them. Saying
  so is the record; guessing a reconciliation would not be.
- **`<synthetic>` is handled as a model value, not as a record type.** The guard reads
  `message.model`, so a future harness spelling it differently would be carried through as a
  model name rather than skipped. Nothing measures that.

## Decision

**The `model.context` event is accepted and ships at `derive_version` 3.** It emits once per
stream and again on a change, `model` and `previous_model` are strings rather than enums (the same
`VOCABULARY_IS_NOT_OURS` argument as `agent_type`, with a measured instance: one model is spelled
`deepseek-v4.1-flash` here and `deepseek-v4.1-flash:cloud` on `agent.spawn.model`), and the
`<synthetic>` skip is counted rather than silent. Each of its four behaviour paths — the synthetic
guard, `previous_model`, the per-stream reset, and the carried-forward-model guard — is killed by
a named test under mutation. That last one **survived the first mutation pass and had no test**;
the two cases it exposed were added, and it is recorded here because a mutation that survives is
the only reason a guard is known to be load-bearing.

**The bead's "emitted per segment" is corrected, not reinterpreted.** Compaction boundaries are in
the transcript (`derive.ts:851`) but are not event kinds, so a segment is not matchable. The event
emits **per stream and per model change**; a `segment` marker is filed as its own bead
(`asc-73cb`).

**The bead's premise that the model is absent from the transcript-derived log is false**, and the
hook sources it named are not needed for the model. `InstructionsLoaded` / `Pre/PostModelSwitch`
remain unmeasured and forward-looking only — they cannot stratify any historical comparison, which
is why deriving from the transcript was the right call and why they are a separate bead.

**The stratification this record was supposed to enable is not available for this project.** That
closes `.10` as "the key is in the log; the comparison is not reachable from here", not as
"delivered".
