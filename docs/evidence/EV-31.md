# EV-31: does a forge's server-side PR merge honour `merge=union`?

**Status**        Measured 2026-09-28 for `asc-3ow4`, on **two servers: a local Forgejo 10.0.3 and
                  GitHub** (`SpikedPunchVictim/asc-union-probe-tmp`, private, throwaway). **P1 holds
                  on both. P2 is refuted on both. P3 was never reached on either. P4 holds on both.**
                  A fourth finding came out of the instrument rather than the servers: **GitHub's
                  `mergeable` flag is a false green when read once**, and reading it that way briefly
                  produced a wrong answer here. The web conflict editor, GitHub Desktop, JetBrains and
                  VS Code remain UNMEASURED — never 0.

                  **Follow-up (`EV-40.md`, 2026-10-03):** the web conflict editor was subsequently
                  measured and found **absent** in Forgejo 10.0.3 — the route 404s, the PR page
                  offers no resolution control, and the binary has no handler for one. Absent, not
                  merely unmeasured. GitHub Desktop, JetBrains and VS Code remain unmeasured.

**Question**      The layout decision (spike/git-layout/FINDINGS.md:215-235) puts records in git as
                  append-only JSONL with `records.jsonl merge=union`. Only command-line git was ever
                  tested. If a client ignores the driver, two appending PRs both add lines at the same
                  place, and a naive conflict resolution loses records. This asks which non-CLI merge
                  paths honour the driver, and for each: does it merge clean with 0 records lost?

## Method

Fixture `spike/git-layout/union-fixture.sh`, arms `union-forge-arms.mjs` (Forgejo REST) and
`union-github-arms.mjs` (GitHub git-data API via `gh api` — no `git push`, so it does not depend on
the push credential). Three records on `main` (`r0`, `r1`, `r2`); branch `a` appends `{"id":"ra0"}`,
branch `b` appends `{"id":"rb0"}`; two PRs, a then b, both onto `main`. Success: `main` holds 5
records, both appends present, no markers, no duplicates.

**Two bases, because "the second PR conflicted" means nothing without a control.** `base-union`
carries `.gitattributes` with `records.jsonl merge=union`; `base-plain` is *the same tree with
`.gitattributes` removed*. Verified on the remote by sha rather than assumed. The command-line
baseline on those exact two bases, from the fixture script itself:

```
--- LOCAL ARM (command-line git): the same two merges, union first then the control
  base-union (merge=union): clean, 5 records: {"id":"r0"}{"id":"r1"}{"id":"r2"}{"id":"ra0"}{"id":"rb0"}
  base-plain (merge=unspecified): CONFLICT
```

So the bases differ under git, and the driver is what differs them. Six cells per server:
`{union, plain} × {merge, squash, rebase}`, each independent — open PRs closed, `main` reset to the
base commit, both head branches re-pointed. **`records.jsonl` is read back from the server after the
merge**, never inferred from the merge command's own report.

**A conflict-free control PR on each server**, because a refusal is uninformative if the repo cannot
merge at all: a branch adding `extra.txt`, against a `main` advanced by an empty commit so the PR is
not a fast-forward. On both servers it merges cleanly — so the refusals below are about the
`records.jsonl` overlap, not about the repository.

## Results

**GitHub** — verbatim summary:

```
base   strategy  PRa      PRb      rb0 on main  mergeable/state samples          silent loss
union  merge     MERGED   REFUSED  absent       true/clean null/unknown false/dirty false/dirty false/dirty none
union  squash    MERGED   REFUSED  absent       true/clean null/unknown false/dirty false/dirty false/dirty none
union  rebase    MERGED   REFUSED  absent       true/clean null/unknown null/unknown false/dirty false/dirty none
plain  merge     MERGED   REFUSED  absent       true/clean null/unknown null/unknown false/dirty false/dirty none
plain  squash    MERGED   REFUSED  absent       true/clean null/unknown false/dirty false/dirty false/dirty none
plain  rebase    MERGED   REFUSED  absent       true/clean null/unknown false/dirty false/dirty false/dirty none
```

Every cell: PR a merged, PR b refused with `Pull Request has merge conflicts`, `main` left at 4
records (`ra0 present, rb0 ABSENT, markers none, unparseable lines 0`). **The union base and the
plain base are indistinguishable.**

**Forgejo** — verbatim summary: the same six rows, PR b refused with HTTP 405 `Please try again
later`, `mergeable=false`, `main` left at 4 records with the same `ra0 present, rb0 ABSENT, markers
none, unparseable lines 0`. Also indistinguishable between bases.

## The finding that came out of the instrument

**GitHub's `mergeable` must not be read once.** In the first GitHub run, reading the first non-null
value produced `false`, `false` and `true` for three cells whose inputs were byte-identical, and
`true/clean` for a union-base PR that the merge endpoint refused moments later for conflicts. Reading
the flag repeatedly instead shows a consistent progression in all six cells:

```
true/clean  ->  null/unknown  ->  false/dirty  (settled)
```

The first non-null read is a **stale** value carried over from before the base moved, and the truth
arrives one to three samples later. A single read is a false green — it reports a PR as mergeable
immediately before the server refuses to merge it. This is the same class as the two harness defects
below, and it is the reason the GitHub table above samples rather than reads.

## Predictions against results

- **P1 — "the merge button conflicts on the second PR; server-side merge does not run the repository's
  merge drivers" — HOLDS on both servers.** Neither honours the driver, and the union base behaves
  exactly like the control base.
- **P2 — "squash is clean and loses nothing" — REFUTED on both servers, and the refutation is the
  useful part.** A squash applies a patch, and that patch would apply here; it is refused anyway. The
  mergeability gate is a 3-way merge test against the base branch and it runs **before** a strategy is
  chosen, so it blocks every strategy equally. Strategy selection cannot rescue a PR the gate has
  already judged.
- **P3 — "rebase conflicts because git does not use merge drivers during rebase" — NOT REACHED on
  either server.** The gate refused before any strategy ran, so `gitattributes(5)` was never
  exercised. This prediction remains untested, not confirmed by a coincidence of outcome.
- **P4 — "no arm silently loses a record; each failure refuses loudly" — HOLDS on all twelve cells.**
  No markers, no unparseable line, no absent record accompanying a successful merge. Every failure was
  a refusal and the record stayed on its branch.
- **P5 — still unmeasured:** the web conflict editor (needs a browser), GitHub Desktop, JetBrains, VS
  Code (none installed / not reachable headless). UNMEASURED, never 0.

## Consequence for the decision

The owner decision requires "a check that GitHub's merge button and common GUI clients honour
`merge=union`". That check now has an answer for both servers tested: **neither honours it, and the
refusal is total — all three strategies, on the base that git itself merges clean.**

Two things follow, and the second is the one worth carrying:

- The merge guard cannot be dropped on the strength of the driver being present in the repository.
- **The failure mode measured is a refusal, not corruption**, so the guard's job is narrower than the
  layout decision assumed. "A naive resolution loses records" did not happen on any path measured
  here — but the measured refusals make hand-resolution in the web editor the *only* way these PRs
  can land, and that is precisely the unmeasured path. Worse, the guard as scoped in `asc-98e1`
  (conflict markers and unparseable lines) would not catch it: a naive in-editor resolution that
  picks one side produces **well-formed JSONL with one side's appends silently gone** — 4 records,
  every line parsing, no markers. Catching that requires comparing id sets, which is why `asc-98e1`
  naming "lost ids" already is the load-bearing half of that guard.

## Instrument defects found, because each produced a false reading first

- **`union-fixture.sh` created the second branch from the first.** `git checkout -b` starts from the
  current HEAD, so `b-<base>` was built on top of `a-<base>` and already contained `ra0`; the second
  merge became a fast-forward and the **control** base reported clean, erasing the contrast it exists
  to provide. Fixed by checking out the base before each side.
- **`git merge -q --abort` is invalid** (`fatal: --abort expects no arguments`) and was wrapped in
  `2>/dev/null || true`, so the script exited 1 with the fixture left conflicted and said nothing.
- **The silent-loss check was first written gated on `base === 'union'`**, disabling the instrument on
  the control. It now runs on every cell and accumulates flags so one failure cannot mask another.
- **GitHub's `mergeable` read once** — above.
